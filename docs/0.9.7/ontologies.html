Ontologies

An ontology is the symbolic half of the Oxid-DB model: a shared vocabulary of meaning made of classes, individuals, and the logical rules that connect them. This page explains what an ontology is and how you build one over the HTTP API and the SDKs.

New in 0.9.7 Version 0.9.7 lets you author a role hierarchy live: POST /actions/add-axiom gains the kind "subproperty", so a sub-property edge no longer needs a file import. Ontology import also grows: POST /import/owl now accepts OWL Functional Syntax (.ofn), OBO (.obo), Manchester (.omn), Turtle (.ttl), and N-Triples (.nt) alongside OWL/XML, all mapped through the same EL⊥ fragment. See the Changelog for the full 0.9.6 → 0.9.7 difference.

What is an ontology?

An ontology is a formal description of the concepts in your domain and the relationships between them. If you have used a relational database, you already know a schema: tables, columns, foreign keys. An ontology does the same job of describing your data, and then goes one step further. It records meaning, not just structure, in a form the database can reason over.

It is built from three kinds of thing:

  • Classes: categories of things, like Beer or Wine. (A relational schema would call these tables.)
  • Individuals: the concrete instances that belong to a class, like Heineken or Guinness. (A schema would call these rows.)
  • Axioms: logical statements about the classes and individuals, like "every Pilsner is a Beer" or "nothing is both a Beer and a Wine". This is the part a plain schema has no equivalent for.

The difference from a schema is that these relationships carry logical weight. When you declare Pilsner is a subclass of Beer, you are not just filing it in a folder: you are stating a rule the reasoner uses to draw new conclusions automatically. Assert that Heineken is a Pilsner and the database will infer, without you writing it down, that Heineken is also a Beer.

Where to find existing ontologies

You do not have to build an ontology from scratch. Thousands of high-quality ontologies are already published for free, and Oxid-DB can import an OWL file directly. Starting from a community ontology gives you a vetted vocabulary and, very often, a ready-made class hierarchy for the reasoner to work over.

Pick an import-compatible serialization Oxid-DB's /import/owl accepts OWL functional syntax (.ofn), OWL/XML (.owx), Turtle (.ttl), and the other formats listed under Importing an existing ontology. Some repositories serve RDF/XML by default, which is not accepted: download an alternative serialization where offered, or convert the file (for example in Protégé) before importing.

Everything is a Term

Under the hood, every name that enters Oxid-DB (a class, an individual, a property, even a literal value) is interned into a dictionary and represented by a single small integer called a Term (a u32). All of the engine's internal data structures work on Terms, never on strings, so comparisons are integer comparisons.

This is more than a performance trick. Because the ontology, the vector index, the document store, and the KGE layer all share the same Term dictionary, an individual, its embedding, its document, and its learned link-prediction entity that all denote the same real-world thing are literally the same u32. There is no separate ID space to join across, and no seam to keep in sync between the symbolic and neural halves of the system. When a reasoner-computed class extent is handed to a vector search as a candidate set, it is already the right kind of identifier, with no translation step.

Class vs. individual is not a type tag Whether a Term names a class or an individual is not baked into the Term itself: it is membership in the ontology's class set or individual set, maintained as you add axioms. The same identifier space serves both.

Classes and subclasses

Classes are your categories. You connect them with subclass axioms (the IS-A relationship, written ⊑ in description logic) to form a hierarchy. Declaring Pilsner ⊑ Beer says "every Pilsner is a Beer".

Let's build the beverage hierarchy used throughout these docs. We have a top category Beer, with two more specific kinds beneath it (Pilsner and Stout), plus a separate Wine category:

curl -s -X POST https://85cfad134a4a.oxid-db.com/subclass \
  -H 'Content-Type: application/json' \
  -d '{"sub":"Pilsner","sup":"Beer"}'
with OxidDB("https://85cfad134a4a.oxid-db.com") as db:
    db.add_subclass("Pilsner", "Beer")
    db.add_subclass("Stout", "Beer")
// Pilsner ⊑ Beer, Stout ⊑ Beer  (sub is the child, sup the parent)
await db.addSubclass({ sub: "Pilsner", sup: "Beer" });
await db.addSubclass({ sub: "Stout", sup: "Beer" });
for _, sc := range []oxid.SubclassRequest{
	{Sub: "Pilsner", Sup: "Beer"},
	{Sub: "Stout", Sup: "Beer"},
} {
	if err := client.AddSubclass(ctx, sc); err != nil {
		log.Fatalf("subclass %s ⊑ %s: %v", sc.Sub, sc.Sup, err)
	}
}
// Pilsner ⊑ Beer  (sub, sup)
oxid.addSubclass(new Mutation.SubclassRequest("Pilsner", "Beer"));
oxid.addSubclass(new Mutation.SubclassRequest("Stout", "Beer"));
use OxidDb\Client\Model\SubclassRequest;

$oxid->addSubclass(new SubclassRequest('Beer', 'Beverage'));    // Beer ⊑ Beverage
$oxid->addSubclass(new SubclassRequest('Pilsner', 'Beer'));     // Pilsner ⊑ Beer
// Pilsner ⊑ Beer, Stout ⊑ Beer
await oxid.AddSubclassAsync(new SubclassRequest("Pilsner", "Beer"));
await oxid.AddSubclassAsync(new SubclassRequest("Stout", "Beer"));

The sub field is the child, sup the parent: {"sub":"Pilsner","sup":"Beer"} reads "Pilsner is a subclass of Beer". You don't have to create Beer as a class first: naming it in an axiom introduces it. Adding the axiom returns {"ok": true}.

Subclass is transitive. If you later add Beer ⊑ Beverage, then a Pilsner is entailed to be a Beverage too, even though you never said so directly. This is why an OxQL query for ?x IS-A Beer returns members of Pilsner and Stout as well: class membership follows the whole hierarchy. The mechanics of that closure live on the Reasoning page.

Disjointness

A subclass axiom says two classes overlap. A disjointness axiom says the opposite: two classes can share no members. In the beverage domain, nothing is both a Beer and a Wine:

curl -s -X POST https://85cfad134a4a.oxid-db.com/disjoint \
  -H 'Content-Type: application/json' \
  -d '{"a":"Beer","b":"Wine"}'
with OxidDB("https://85cfad134a4a.oxid-db.com") as db:
    db.add_disjoint("Beer", "Wine")
// Nothing is both a Beer and a Wine.
await db.addDisjoint({ a: "Beer", b: "Wine" });
// Beer and Wine are disjoint: nothing can be both.
if err := client.AddDisjoint(ctx, oxid.DisjointRequest{A: "Beer", B: "Wine"}); err != nil {
	log.Fatalf("disjoint: %v", err)
}
// Beer and Wine are disjoint
oxid.addDisjoint(new Mutation.DisjointRequest("Beer", "Wine"));
use OxidDb\Client\Model\DisjointRequest;

$oxid->addDisjoint(new DisjointRequest('Beer', 'Wine'));   // POST /disjoint: Beer ⊓ Wine = ⊥
// A beverage cannot be both a Beer and a Wine.
await oxid.AddDisjointAsync(new DisjointRequest("Beer", "Wine"));

Note the field names are a and b: the order does not matter, disjointness is symmetric. Internally the axiom is encoded as Beer ⊓ Wine ⊑ ⊥: "the things that are both Beer and Wine are exactly the things in the empty class (⊥, owl:Nothing)".

Why bother? Disjointness is what turns the reasoner into a data-integrity guard. Suppose Stout ⊑ Beer and some grape variety Merlot ⊑ Wine. If a bad import asserts that one individual is both a Stout and a Merlot, it is transitively both a Beer and a Wine, which the disjointness axiom forbids. The reasoner detects the contradiction and reports the ontology as inconsistent, rather than silently accepting the bad fact. That check, and the difference between an inconsistent ontology and an incoherent one (a class that can never have members), is covered under consistency & disjointness on the Reasoning page.

Individuals

Classes describe categories; individuals are the concrete entities that belong to them. You create an individual by inserting it with the class it is a member of. An individual can also carry a vector (an embedding) and, through the compound-write endpoint, data properties, so the same entity is visible to both the reasoner and vector search.

Here we insert Heineken as a Pilsner, giving it a 4-dimensional toy vector so it lands in the default vector collection too:

curl -s -X POST https://85cfad134a4a.oxid-db.com/insert \
  -H 'Content-Type: application/json' \
  -d '{"iri":"Heineken","class":"Lager","vector":[0.6,0.3,0.1,0.6]}'
with OxidDB("https://85cfad134a4a.oxid-db.com") as db:
    res = db.insert("Heineken", "Pilsner", vector=[0.4, 0.2, 0.1, 0.4])
    # res: {"iri": "Heineken", ...}
// Identity is `individual` (or alias `iri`); membership is `class` (or `classes[]`).
await db.insert({ individual: "Heineken", class: "Pilsner", vector: [0.4, 0.2, 0.1, 0.4] });
await db.insert({ iri: "Guinness", class: "Stout", vector: [0.9, 0.3, 0.0, 0.7] });
res, err := client.Insert(ctx, oxid.InsertRequest{
	Individual: "PilsnerUrquell",
	Class:      "Pilsner",
	Vector:     []float64{0.9, 0.1, 0.0, 0.2}, // 4-dim
})
if err != nil {
	log.Fatalf("insert: %v", err)
}
_ = res
// Simple: individual + single class (no vector)
oxid.insert(Mutation.InsertRequest.of("Heineken", "Pilsner"));

// Full form: individual + class + 4-dim vector into a named collection
oxid.insert(new Mutation.InsertRequest(
        "Guinness", null, "Stout", null, null,
        new double[] {0.1, 0.2, 0.3, 0.4}, "beverages"));
use OxidDb\Client\Model\InsertRequest;

$res = $oxid->insert(new InsertRequest(
    'Heineken',
    'Pilsner',
    vector: [0.6, 0.3, 0.1, 0.6],
    collection: 'demo_beers',
));
echo $res->ok ? "inserted\n" : "failed\n";
// Positional (single class): emits {"individual","class",...}
OkResponse ok = await oxid.InsertAsync(new InsertRequest(
    "Heineken", "Pilsner",
    Vector: new[] { 0.9, 0.1, 0.5, 0.2 }));

// Multi-class via the aliases: emits {"iri","classes":[...]}
await oxid.InsertAsync(new InsertRequest(
    Individual: null, Class: null,
    Iri: "Guinness", Classes: new List<string> { "Stout" },
    Vector: new[] { 0.1, 0.8, 0.3, 0.4 }));

The identity field on the wire is iri (the legacy alias individual also deserializes). Set class for a single class or classes for several, not both. You state only what you know: asserting Heineken : Pilsner stores exactly that one fact, plus the optional vector. After classification, the reasoner fills in the rest: Heineken is inferred to be a Beer (and any further superclasses) because Pilsner ⊑ Beer.

/insert is deliberately narrow POST /insert writes exactly an IRI, its class(es), and an optional vector or text. If you send properties, label, or annotations it returns a loud 400 and points you at POST /entities, the compound-write endpoint that stores classes, data/object properties, and a vector in one transaction.

Equivalence & other axioms

Subclass, disjointness, and class assertion cover the great majority of real modelling. The native model supports a few more axiom shapes, and (because Oxid-DB targets a tractable logic) deliberately leaves some rich OWL constructs out. It is worth knowing exactly where the line is.

What the native ontology model represents (its class-expression language) is exactly five shapes: a named class, ⊤ (owl:Thing, the class of everything), ⊥ (owl:Nothing, the empty class), conjunction ⊓ ("things that are both A and B"), and existential restriction ∃r.C ("things related by r to some C"). Everything you assert is built from those.

AxiomSupported?Notes
SubClassOf (A ⊑ B)YesThe IS-A backbone; transitive.
DisjointClassesYesEncoded pairwise as A ⊓ B ⊑ ⊥.
EquivalentClasses (A ≡ B)Yes, desugaredStored as two SubClassOf edges (A ⊑ B and B ⊑ A); there is no separate equivalence relation at the storage layer.
Class / property assertions (ABox)YesIndividuals typed into classes; object- and data-property facts.
Sub-property (SubObjectPropertyOf, single)YesRole hierarchy is reasoned via the reasoner's CR7 rule. Authorable live via POST /actions/add-axiom kind "subproperty".
Length-2 property chains / transitivityYesReasoned by default via CR8 as of 0.9.7 (r∘s ⊑ t; Trans(r) desugars to r∘r ⊑ r). Opt out with OXD_REASONER_ROLE_CHAINS=0.
Length-3+ property chainsNoChains of length 3 or longer are stored but inert, still fenced off. Flagged loudly on import, never silently dropped.
ObjectPropertyDomainYesReasoned as ∃r.⊤ ⊑ C as of 0.9.7. Role range restrictions remain excluded.
Union, complement/negation, universal (∀), cardinality, nominals (oneOf)NoOutside the EL profile; collapsed or dropped at import time (and counted).

On equivalence and "defined classes": because A ≡ B is just stored as two subclass edges, simple equivalences work well. Fully defined classes (where a class is declared equivalent to a complex expression, e.g. "a Stout is exactly a Beer that is dark and roasted") are where the honesty caveat lives. The reasoner's normalizer handles many such definitions, but the completeness audit records residual gaps in complex definitional equivalence and some ABox rules. Model with subclass and disjointness where you can; treat complex defined-class inference as best-effort rather than guaranteed, and see the Reasoning page for exactly which inferences you get.

EL⊥, not full OWL 2 Oxid-DB's reasoner is OWL 2 EL with ⊥: a tractable (PTIME) subset of OWL 2, not the full language. This is a deliberate trade: guaranteed fast classification in exchange for omitting constructs like negation, universal restrictions, and cardinality. For catalogs, taxonomies, and terminologies it is more than enough; if you need those richer constructs, know that they are collapsed on import.

Adding a role hierarchy (sub-property) axiom

Subclass and disjointness have their own endpoints (/subclass, /disjoint). Richer axioms go through the governed POST /actions/add-axiom, which as of 0.9.7 accepts a "subproperty" kind (a length-1 role hierarchy edge) alongside the existing "subclass", "disjoint", and "equivalent" kinds. A sub-property edge is reasoned by the reasoner’s CR7 rule, so a fact asserted along the sub-property counts along its super-property.

json
{ "kind": "subproperty", "sub": "https://ex.org/prop/brewedBy", "sup": "https://ex.org/prop/producedBy" }

Because it is a governed write, the axiom commits only if the ontology stays coherent; otherwise the endpoint returns the EL⊥ verdict without mutating anything. Role chains are not authorable through this action, author chain axioms via file import. The same capability is mirrored in the SDKs (Node AddAxiomRequest with kind "subproperty"; PHP AddAxiomRequest::subproperty($sub, $sup)) and the MCP add_axiom tool, and role axioms now round-trip through OKF export under the x-oxid-role-axioms key.

Importing an existing ontology

You rarely start from a blank slate. If you already have an ontology as an OWL file, or your data as a CSV, you can load it in one call rather than asserting axiom by axiom.

From OWL

POST /import/owl takes the raw ontology bytes as the request body. As of 0.9.7 it reads six syntaxes: OWL/XML (.owl/.owx/.xml), OWL Functional Syntax (.ofn), OBO 1.4 (.obo, the bio-ontology format behind GO, DOID, and Uberon), OWL Manchester Syntax (.omn), RDF Turtle (.ttl), and N-Triples (.nt). The server detects the format by file extension, then by sniffing the content; pass ?format= to force it (owx | owl | xml, ofn, obo, omn, ttl, nt). An unknown ?format= value returns a 400. Every format flows through the same EL⊥ mapping, so the response reports what was added (classes, individuals, axioms, edges) plus anything skipped, with warnings.

RDF/XML is not accepted /import/owl rejects RDF/XML with a 400. Use one of the supported syntaxes: OWL/XML (owx), Functional (ofn), OBO, Manchester (omn), Turtle (ttl), or N-Triples (nt). Some of the SDK snippets below pass an RDF/XML string for brevity; substitute a supported serialization when you run them against a live server.
# Raw OWL bytes as the body. RDF/XML is NOT accepted: use owx/ofn/obo/omn/ttl/nt.
curl -s -X POST 'https://85cfad134a4a.oxid-db.com/import/owl?format=owx' \
  -H 'Content-Type: application/octet-stream' \
  --data-binary @beverages.owx
with OxidDB("https://85cfad134a4a.oxid-db.com") as db:
    owl = open("beverages.owx").read()
    res = db.import_owl(owl)
    # res: {"ok": true, "classes_added": .., "individuals_added": .., ...}
import { readFile } from "node:fs/promises";

const owl = await readFile("beverages.owl", "utf8");
const res = await db.importOwl(owl);
console.log(res.ok, res.classes_added, res.axioms_added);
owl := `<?xml version="1.0"?>
<rdf:RDF xmlns:rdf="http://www.w3.org/1999/02/22-rdf-syntax-ns#"
         xmlns:owl="http://www.w3.org/2002/07/owl#">
  <owl:Class rdf:about="Beer"/>
  <owl:Class rdf:about="Pilsner">
    <rdfs:subClassOf rdf:resource="Beer"/>
  </owl:Class>
</rdf:RDF>`

res, err := client.ImportOWL(ctx, owl)
if err != nil {
	log.Fatalf("import owl: %v", err)
}
log.Printf("ok=%v classes_added=%d axioms_added=%d warnings=%v",
	res.Ok, res.ClassesAdded, res.AxiomsAdded, res.Warnings)
String owlRdfXml = """
    <rdf:RDF xmlns:rdf="http://www.w3.org/1999/02/22-rdf-syntax-ns#"
             xmlns:owl="http://www.w3.org/2002/07/owl#">
      <owl:Class rdf:about="Beer"/>
      <owl:Class rdf:about="Pilsner"><rdfs:subClassOf rdf:resource="Beer"/></owl:Class>
    </rdf:RDF>
    """;
Ops.ImportResponse res = oxid.importOwl(owlRdfXml);
System.out.println(res.classesAdded() + " classes, " + res.axiomsAdded() + " axioms");
$owl = file_get_contents('beverages.owl');       // raw RDF/XML string
$res = $oxid->importOwl($owl);
printf("ok=%s classes=%d individuals=%d axioms=%d\n",
    $res->ok ? 'true' : 'false',
    $res->classesAdded, $res->individualsAdded, $res->axiomsAdded);
string owl = await File.ReadAllTextAsync("beverages.owl"); // RDF/XML
ImportResponse res = await oxid.ImportOwlAsync(owl);
Console.WriteLine($"classes+={res.ClassesAdded} individuals+={res.IndividualsAdded} " +
                  $"axioms+={res.AxiomsAdded}");

Axioms outside the EL profile are collapsed or skipped during import, and every skip is counted and surfaced in the warnings list, never dropped silently.

From CSV

POST /import/csv takes raw CSV text and is the quickest way to seed a small ontology from a spreadsheet, for example an iri,class table that types individuals into classes:

curl -s -X POST https://85cfad134a4a.oxid-db.com/import/csv \
  -H 'Content-Type: text/csv; charset=utf-8' \
  --data-binary $'iri,class\nHeineken,Pilsner\nGuinness,Stout\n'
with OxidDB("https://85cfad134a4a.oxid-db.com") as db:
    csv = "iri,class\nHeineken,Pilsner\nGuinness,Stout\n"
    res = db.import_csv(csv)
    # res: {"ok": true, "classes_added": .., "individuals_added": .., ...}
const csv =
  "subject,predicate,object\n" +
  "Pilsner,subClassOf,Beer\n" +
  "Stout,subClassOf,Beer\n";
const res = await db.importCsv(csv);
console.log(res.ok, res.classes_added, res.axioms_added);
csv := "individual,class,abv\n" +
	"PilsnerUrquell,Pilsner,4.4\n" +
	"Guinness,Stout,4.2\n" +
	"Chardonnay,Wine,13.5\n"

res, err := client.ImportCSV(ctx, csv)
if err != nil {
	log.Fatalf("import csv: %v", err)
}
log.Printf("ok=%v classes_added=%d individuals_added=%d",
	res.Ok, res.ClassesAdded, res.IndividualsAdded)
String csv = String.join("\n",
        "individual,class,abv",
        "Heineken,Pilsner,5.0",
        "Guinness,Stout,4.2",
        "Cabernet,Wine,13.5");
Ops.ImportResponse res = oxid.importCsv(csv);
System.out.println(res.individualsAdded() + " individuals imported");
$csv = <<<CSV
individual,class
Heineken,Pilsner
Guinness,Stout
Merlot,Wine
CSV;

$res = $oxid->importCsv($csv);
printf("ok=%s classes=%d individuals=%d axioms=%d\n",
    $res->ok ? 'true' : 'false',
    $res->classesAdded, $res->individualsAdded, $res->axiomsAdded);
string csv =
    "individual,class\n" +
    "Heineken,Pilsner\n" +
    "Guinness,Stout\n";
ImportResponse res = await oxid.ImportCsvAsync(csv);
Console.WriteLine($"individuals+={res.IndividualsAdded} axioms+={res.AxiomsAdded}");
