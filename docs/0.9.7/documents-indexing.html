Indexing & Schema

How collections are shaped and indexed for fast queries: schema-free JSON documents with secondary indexes on one side, a declared vector configuration on the other, and read-only endpoints to inspect both.

Oxid-DB has two kinds of collection, and this page covers the shape and indexing of each. A document collection holds schema-free JSON. You never declare its fields up front. A vector collection is the opposite: it fixes a vector configuration (dimensions + metric) at creation and every vector you add must match it. They meet through the ontology bridge, where a document collection is bound to a class and (optionally) a vector collection, so the same identity carries facts, fields, and an embedding. This page is about the shaping and indexing; the bridge itself is the next page.

New in 0.9.7 A collection with a GeoPoint field can take an opt-in spatial (grid) index. Like the B-tree field indexes, it only makes a query faster: it narrows a radius or distance query to a candidate superset and never changes the answer. See The spatial (grid) index below, and the Changelog for the full 0.9.6 → 0.9.7 difference.

Collection schema

Document collections are schema-free. You never run a migration or declare columns. You just insert JSON, and heterogeneous documents can live side by side in one collection. Internally each document is a list of (field, value) pairs sorted by field key, and every value is one of ten typed variants (null, bool, int, float, string, binary, array, nested object, timestamp, vector), nested up to 16 levels deep. Field names are interned in a separate field dictionary, so a collection with wildly varying field cardinality never pollutes the ontology's identity space.

Being schema-free does not mean Oxid-DB is blind to shape. As documents arrive it records the distinct structural schemas it observes: which field paths exist, their types, and how often each shape occurs. A read-only endpoint reports what it has seen. GET /collections/{name}/schema returns each distinct schema with a frequency count and, for each, the sorted fields (dotted path plus inferred type):

json
// GET /collections/people/schema
{
  "collection": "people",
  "distinct_schemas": 2,
  "schemas": [
    {
      "fields": [
        { "path": "name",  "type": "String" },
        { "path": "score", "type": "Int" }
      ],
      "frequency": 1
    },
    {
      "fields": [
        { "path": "name",    "type": "String" },
        { "path": "score",   "type": "Int" },
        { "path": "manager", "type": "String" }
      ],
      "frequency": 2
    }
  ]
}

Here two documents carry a manager field and one does not, reported as two related schemas with their frequencies, not treated as an error. The type string is the field-value variant name (String, Int, Float, Bool, and so on). This is computed on demand at read time; there is no batch "analyse" step to run.

The vector configuration

A vector collection, by contrast, is declared. It fixes two things up front: the number of dimensions and the distance metric. Every vector you later add must have exactly that many dimensions. The wire field is dimensions (not dim) and the metric defaults to cosine when omitted (the four choices are cosine, l2, ip, manhattan; see Vector Search). Re-creating a collection with the same shape returns 409, so create-if-absent is a caught-and-ignored 409.

curl -s -X POST https://85cfad134a4a.oxid-db.com/collections \
  -H 'Content-Type: application/json' \
  -d '{"name":"beers","dimensions":384,"metric":"cosine","quantization":"none"}'
with OxidDB("https://85cfad134a4a.oxid-db.com") as db:
    db.create_collection("beers", dim=4, metric="cosine")
    # creating the same shape again returns 409 - catch OxidHttpError, ignore 409
// Field is `dimensions` (not `dim`).
await db.createCollection({ name: "beers", dimensions: 4, metric: "cosine" });

const list = await db.collections();
console.log(list.collections.map((c) => `${c.name}/${c.dimensions}`));
// The field is `Dimensions` (not `dim`). Metric: cosine | l2 | ip | manhattan.
if err := client.CreateCollection(ctx, oxid.CreateCollectionRequest{
	Name:       "beverages",
	Dimensions: 4,        // 4-dim vectors
	Metric:     "cosine",
}); err != nil {
	log.Fatalf("create collection: %v", err)
}
// 4-dim vector collection for beverage embeddings (field is `dimensions`, not `dim`)
oxid.createCollection(Collections.CreateCollectionRequest.of("beverages", 4));
use OxidDb\Client\Model\CreateCollectionRequest;

// The field is `dimensions`, not `dim`.
$oxid->createCollection(new CreateCollectionRequest('demo_beers', 4, 'cosine'));
// A 4-dim collection for beverage vectors (wire key is `dimensions`, not `dim`).
await oxid.CreateCollectionAsync(new CreateCollectionRequest("beers", 4));

// With an explicit metric:
await oxid.CreateCollectionAsync(new CreateCollectionRequest("beers", 4, Metric: "cosine"));
Two schema surfaces, two answers A document collection is schema-free. /collections/{name}/schema reports the shapes it has observed. A vector collection is schema-declared. Its shape lives in the collection listing (GET /collections returns name, dimensions, metric, quantization, cold_f32, default, vectors).

Secondary indexes

A secondary index accelerates document-mode predicates (the ?x.field <op> value stages you write after FROM). Without one, a predicate scans every document in the collection, always correct, but linear. With one, the engine resolves the predicate by walking a sorted structure instead. Indexes are backed by an ordered B-tree map keyed on the field value, so a single index serves both equality and range queries, plus sorted iteration:

PredicateWith a field index
?x.abv = 5.0Point lookup: jump straight to the matching ids.
?x.abv > v / < / >= / <=Range scan over the sorted keys.
?x.abv != vUnion of the below-and-above ranges.

The query engine uses a field index automatically whenever one exists for a predicate, and scans otherwise. The result is identical either way, only the speed differs. Indexes are created explicitly over HTTP; there is no blind auto-indexing, because every index costs write time and memory. You choose which fields earn one.

Indexes are derived, never the source of truth An index is rebuilt from the stored documents. Its definition is persisted and survives a restart, but its contents are always reconstructed from the document bytes, never written out as a separate copy. Losing or skipping an index can only cost speed, never data.

Creating an index

POST /collections/{name}/indexes builds an index over the existing documents and returns its cardinality. Send {"field":"abv"} for a single-field index, or {"name":"geo","fields":["country","city"]} for a compound one over an ordered tuple of fields.

bash
# single-field index on the `abv` field of the beers collection
curl -s -X POST https://85cfad134a4a.oxid-db.com/collections/beers/indexes \
  -H 'Content-Type: application/json' \
  -d '{"field":"abv"}'
# → {"ok":true,"field":"abv","cardinality":42}

# compound index over (country, city)
curl -s -X POST https://85cfad134a4a.oxid-db.com/collections/beers/indexes \
  -H 'Content-Type: application/json' \
  -d '{"name":"origin","fields":["country","city"]}'
# → {"ok":true,"name":"origin","fields":["country","city"],"cardinality":58}

A compound index follows the standard prefix rule: an index on (country, city) accelerates queries on country alone or on (country, city) together, but not on city by itself, because city is not a leading column.

Inspecting indexes

GET /collections/{name}/indexes lists both kinds. A single-field entry carries the dotted field_path and its cardinality; a compound entry carries its name, its ordered field_paths, and cardinality. A collection with none looks like this:

json
// GET /collections/people/indexes  - none defined yet
{
  "collection": "people",
  "field_indexes": [],
  "compound_indexes": []
}

And once you have created the two indexes above:

json
// GET /collections/beers/indexes
{
  "collection": "beers",
  "field_indexes": [
    { "field_path": "abv", "cardinality": 42 }
  ],
  "compound_indexes": [
    { "name": "origin", "field_paths": ["country", "city"], "cardinality": 58 }
  ]
}

DELETE /collections/{name}/indexes/{id} drops an index. Pass a compound index's name, or a single-field index's dotted field path (e.g. abv). It returns 204 on success, 404 if there is no such index.

The spatial (grid) index New in 0.9.7

A GeoPoint field (the {"$geo":{"lat":…,"lon":…}} value type introduced in 0.9.7) can be accelerated with an opt-in spatial index. It is an equirectangular grid laid over the field's coordinates. A radius (WITHIN) or distance (SORT DISTANCE) query first asks the grid for the set of cells that could contain matches, then refines every candidate in that superset with an exact Haversine distance. The grid is a fast pre-filter; the Haversine pass is what decides the final answer.

Superset invariant: only faster, never different The grid can only ever produce a candidate superset of what is in range, and the Haversine refinement then trims it to the exact result. So the index cannot change a query's answer, it can only make it faster. A geo query works perfectly well without the index too: it simply falls back to a full scan (still exact). The index is a performance optimisation for large collections, not a correctness requirement.

Like every other index on this page, the spatial index is derived, not the source of truth. Its definition is persisted (on-disk format version 12) and survives a restart, but its contents are rebuilt from the stored GeoPoints when the database loads. Losing or skipping it can only cost speed, never data. Because it is opt-in, a fresh collection has no spatial index until you create one; small collections may never need one, since the full-scan fallback is already exact. For how radius and distance queries are written in OxQL, see Querying Documents.

Collection stats

Before you decide what to index, look at what you have. GET /collections/{name}/stats returns per-field statistics (the same numbers the planner uses to order predicates) computed on demand:

json
// GET /collections/people/stats
{
  "collection": "people",
  "fields": [
    { "field_path": "name",    "cardinality": 3, "density": 1.0,               "null_count": 0, "total_docs": 3 },
    { "field_path": "score",   "cardinality": 3, "density": 1.0,               "null_count": 0, "total_docs": 3 },
    { "field_path": "manager", "cardinality": 1, "density": 0.6666666865348816, "null_count": 0, "total_docs": 3 }
  ]
}
FieldWhat it means
cardinalityHow many distinct values the field has. High cardinality relative to total_docs means the field is selective, a good index candidate.
densityThe fraction of documents that carry the field at all (present ÷ total_docs). Above, manager appears in 2 of 3 documents, so density ≈ 0.667. A sparse field is a weaker index candidate.
null_countHow many documents set the field explicitly to null (distinct from simply not having the field).
total_docsThe document count the other numbers are measured against.

When to index / performance

Indexes trade write throughput and memory for read speed, so add them deliberately:

Index fields you filter or range on
An index pays off for the =, !=, and < > <= >= predicates you run repeatedly. A field you only ever project or return does not need one.
Prefer selective, dense fields
Use /stats: high cardinality (many distinct values) plus high density (present on most documents) makes the best index. Indexing a near-constant field buys little.
Compound indexes: put the most-filtered field first
Order the tuple by the prefix rule. The leading column must be one you query on its own. (country, city) serves country and (country, city), not city alone.
Bulk-load first, index after
Building an index over an already-loaded collection is one pass. Maintaining an index during a large bulk import pays the maintenance cost on every row. Load the data, then create the index.
Don't over-index
Every index consumes memory and slows every write to that collection. Index the handful of fields your hot queries actually touch.

What indexing does NOT do yet

Be aware of the honest edges before you design around them:

Presence and array-membership always scan The EXISTS ?x.field and ?x.field CONTAINS value stages are not served by an index in this build. They scan the collection. Field indexes cover value equality and ranges only.
No automatic index creation The engine tracks how often a field is queried and can recommend indexes worth their cost, but it never creates them for you. You create every index explicitly. An adaptive-storage manager that would self-materialise hot fields exists in the engine but is not wired into the running server in this build, so treat it as a future capability rather than a knob you can turn today.

Two more limits worth stating plainly: a single /query materialises its full result set in RAM (subject to the configured row cap), so an index speeds a query but does not stream unbounded results; and the vector index itself is separate from these document indexes. It is always HNSW (the only usable vector index type), configured through the vector collection, and covered on the Vector Search page.
