Scoring & Ranking

How Oxid-DB turns "which of these is the best match?" into a number and, just as important, what order those matches come back in over the wire. This page covers the score field, the ordering the HTTP /query path actually guarantees, the one big SORT gotcha, how hybrid queries rank, and how to page results with LIMIT.

What a score means

Every vector metric in Oxid-DB reduces two embeddings to a single distance, and the convention is uniform: lower distance means more similar. There are four metrics, chosen per collection at creation time (default cosine):

MetricWire nameMeasures
Cosine defaultcosineDirection only (magnitude ignored); vectors normalized before search. The standard choice for text/sentence embeddings.
Euclidean (squared)l2Straight-line distance, squared (no final square root). Same ranking as true Euclidean; absolute numbers differ from engines that root it.
Inner productipNegated dot product, so "lower = more similar" still holds. For pre-normalized or deliberately-magnitude-carrying vectors.
Manhattan / L1manhattanSum of absolute per-dimension differences. Less dominated by a single outlier dimension than L2.

When a query includes a vector stage (NEAR), each result row carries a score. In the /query response and the /individuals/{iri}/similar response the score is presented as a similarity where higher is better. For the by-reference similar endpoint it is exactly 1.0 − distance, rounded to three decimals, and the query entity itself is excluded from its own neighbours.

Run a NEAR query and look at the two fields that matter: iri (always present) and score (present on vector/hybrid rows):

curl -s -X POST https://85cfad134a4a.oxid-db.com/query \
  -H 'Content-Type: application/json' \
  -d '{"query":"FIND ?x WHERE ?x IS-A Beer AND NEAR ?x TO [0.9,0.1,0.5,0.7] LIMIT 5"}'
with OxidDB("https://85cfad134a4a.oxid-db.com") as db:
    # literal query vector (dims must match the collection)
    hits = db.query("FIND ?x WHERE NEAR ?x TO [0.4, 0.2, 0.1, 0.4] LIMIT 5")
    for h in hits.get("results", []):
        print(h["iri"], h.get("score"))

    # nearest neighbours of an existing individual
    sim = db.individual_similar("Heineken", k=3, collection="default")
    print([h["iri"] for h in sim.get("results", [])])
// 1) OxQL NEAR over /query - hybrid-capable (combine with IS-A). Rows carry `score`.
const near = await db.query({
  query: "FIND ?x WHERE ?x IS-A Beer AND NEAR ?x TO [0.9, 0.1, 0.5, 0.7] LIMIT 5",
});
for (const hit of near.results) console.log(hit.iri, hit.score);

// 2) By reference individual - top-k neighbors of an existing IRI.
const sim = await db.individualSimilar("Guinness", { k: 3, collection: "default" });
for (const hit of sim.results) console.log(hit.iri, hit.score);
// Hybrid: Beers nearest a 4-dim probe vector, top 5.
oxql := oxid.NewQueryBuilder().
	Find("x").
	IsA("Beer").
	Near([]float64{0.9, 0.1, 0.0, 0.2}).
	Limit(5).
	ToOxql()
res, err := client.Query(ctx, oxid.QueryRequest{Query: oxql})
if err != nil {
	log.Fatalf("vector search: %v", err)
}
for _, hit := range res.Results {
	if hit.Score != nil {
		log.Printf("%s score=%.4f", hit.IRI, *hit.Score)
	}
}
// By raw vector - via OxQL NEAR; each row exposes iri() and score()
String oxql = new QueryBuilder()
        .find("x").isA("Beer")
        .near(new double[] {0.9, 0.1, 0.5, 0.2})
        .limit(5)
        .toOxql();
Query.QueryResponse hits = oxid.query(Query.QueryRequest.of(oxql));
for (Query.QueryHit hit : hits.results()) {
    System.out.println(hit.iri() + " " + hit.score());
}
use OxidDb\Client\Model\QueryRequest;

// OxQL NEAR over POST /query - literal query vector, hybrid-capable.
$near = $oxid->query(new QueryRequest(
    'FIND ?x WHERE ?x IS-A Beer AND NEAR ?x TO [0.9, 0.1, 0.5, 0.2] LIMIT 5'
));
foreach ($near->results as $hit) {
    printf("  %s  score=%s\n", $hit->iri, $hit->score);
}
// Hybrid: a Beer near this 4-dim probe vector, top 5.
string oxql = new QueryBuilder()
    .Find("x").IsA("Beer").Near(new[] { 0.9, 0.1, 0.5, 0.2 }).Limit(5)
    .ToOxql();
QueryResponse hits = await oxid.QueryAsync(new QueryRequest(oxql));
foreach (QueryHit hit in hits.Results)
{
    Console.WriteLine($"{hit.Iri}  score={hit.Score}");
}

A NEAR/hybrid row looks like this on the wire (the fixture query_response_basic.json shows the IRI-only shape; a vector stage adds score):

json
{
  "results": [
    { "iri": "Heineken",  "score": 0.991 },
    { "iri": "BudLight",  "score": 0.990 }
  ],
  "total_count": 2,
  "next_cursor": "eyJ0ZXJtIjoi..."
}

Two more optional fields can appear on a row: fields (an object) is added when the query uses PROJECT to return selected document fields, and elapsed_micros may appear at the top level (clients ignore it). A pure ontology query (no NEAR) returns IRI-only rows with no score at all.

Note total_count is the number of rows in this page, not the total number of matches across all pages. Don't treat it as a corpus-wide count.

Result ordering

Because your first instinct is usually "sort it in the query," it's worth being blunt about what the HTTP /query path actually guarantees for row order:

Pure ontology results (e.g. IS-A, relation filters, no NEAR)
Rows have no score and are returned in IRI order (a stable, deterministic ordering by the interned term). This is what the SDK contract pins its comparisons against.
Vector / hybrid results (any query with a NEAR stage)
Rows are ordered by score, then IRI: best similarity first, with IRI as the deterministic tie-break so equal-score rows never shuffle between calls.

That is the whole contract: IRI order, or score-then-IRI order for vector/hybrid queries. There is no third ordering. In particular, an OxQL SORT clause does not change it, which is the gotcha below.

The SORT gotcha

SORT is a no-op over HTTP OxQL accepts a SORT <field> [ASC|DESC] clause and it parses cleanly, but it does not order the JSON returned by POST /query. The wire order is IRI (or score-then-IRI for NEAR/hybrid), full stop. Adding SORT abv DESC to a query will not give you results sorted by abv over HTTP. To order by an arbitrary field, sort the returned rows client-side, or rely on the built-in score / NEAR ranking. This is the single biggest surprise on this page; see the sdk/_contract/README.md ordering contract.

Here is a query that looks like it sorts, and what actually happens:

oxql
FIND ?x FROM beers WHERE ?x.abv > 0.5 PROJECT name, abv SORT abv DESC LIMIT 10
-- Parses fine. The `abv DESC` ordering is NOT applied to the HTTP response.
-- Rows still come back in IRI order; re-sort by row.fields.abv in your app.

Hybrid ranking

A hybrid query pairs a logical filter (an ontology constraint like IS-A Beer) with a vector stage (NEAR ?x TO […]). The two play distinct roles, and understanding the split is the key to reading the results:

Symbolic The reasoner filters

The IS-A stage resolves to a class extent: the set of individuals that are members of the class or any of its subclasses, transitively, via the reasoner's classification closure. This is a hard in/out decision: a candidate is either in the extent or it isn't. It does not contribute to the score.

Neural The vector ranks

Within the filtered candidates, the NEAR stage supplies the ordering: the score on each row. So the reasoner decides who is eligible, and vector similarity decides the order among the eligible.

Concretely, FIND ?x WHERE ?x IS-A Beer AND NEAR ?x TO [0.9,0.1,0.5,0.7] LIMIT 5 returns the five members of Beer (including Pilsner, Stout, etc. by inference) that are closest to the probe vector, ordered by score. The engine pushes the class bitset directly into the HNSW traversal so a rare class doesn't collapse recall; see Hybrid Queries for the filter-during-traversal mechanics.

When a single query touches multiple vector collections, their lists are merged with Reciprocal Rank Fusion (RRF, k = 60), which fuses on rank position rather than raw distance, so a cosine "0.08" and an L2-squared "0.08" never have to be made comparable. The fused score is then the RRF score, not a distance. A single-collection NEAR keeps its raw similarity.

No weighted logical+vector blend Oxid-DB does not combine the logical and vector signals into one tunable number. The logical side is a hard filter (in/out of the class extent); the vector side supplies the ordering; RRF only ever fuses several vector lists, and its k = 60 is intentionally not configurable. If you genuinely need per-signal weighting, compute it in your application over the distances, RRF scores, and consistency verdict Oxid returns.

LIMIT & pagination

Every /query call returns one page. If you omit LIMIT, the default page size is 10 rows. An explicit LIMIT above the server's max_query_rows cap (default 100000) is rejected with a 400 and an error body, not an empty results array, so a single call can't materialize an unbounded result. Check the HTTP status: a client that reads only results would misread the rejection as zero matches rather than "lower the LIMIT or page."

There are two ways to walk a full result set, both over POST /query:

MechanismHowWhen
OFFSET / LIMITKeep the same query, increment OFFSET by LIMIT until results is empty (or shorter than LIMIT). Selects the true top-N over the full candidate set each call.The always-correct paginator; the recommended path for deep pages and for SORT/NEAR result sets.
next_cursorThe response returns an opaque base64 next_cursor; resend it as {"query": "...", "cursor": "<next_cursor>"} to resume.Convenient for straight scans. Deep multi-page cursors over SORT/NEAR sets are not fully supported; use OFFSET/LIMIT for those.

The SDKs wrap the first mechanism as a query_all helper that transparently drains every page for you:

# Page by incrementing OFFSET by LIMIT until results is empty.
curl -s -X POST https://85cfad134a4a.oxid-db.com/query \
  -H 'Content-Type: application/json' \
  -d '{"query":"FIND ?x WHERE ?x IS-A Beer LIMIT 100 OFFSET 0"}'
# then resend with the returned next_cursor:
curl -s -X POST https://85cfad134a4a.oxid-db.com/query \
  -H 'Content-Type: application/json' \
  -d '{"query":"FIND ?x WHERE ?x IS-A Beer LIMIT 100","cursor":"eyJ0ZXJtIjoi..."}'
with OxidDB("https://85cfad134a4a.oxid-db.com") as db:
    for hit in db.query_all("FIND ?x WHERE ?x IS-A Beer"):
        print(hit["iri"])
const iris: string[] = [];
for await (const hit of db.queryAll({ query: "FIND ?x WHERE ?x IS-A Beer LIMIT 1000" })) {
  iris.push(hit.iri);
}
console.log(iris.length);
count := 0
for hit, err := range client.QueryAll(ctx, oxid.QueryRequest{Query: "FIND ?x WHERE ?x IS-A Beverage"}) {
	if err != nil {
		log.Fatalf("query-all: %v", err) // first error is terminal
	}
	count++
	log.Println(hit.IRI)
}
log.Printf("streamed %d hits across all pages", count)
for (Query.QueryHit hit : oxid.queryAll(Query.QueryRequest.of("FIND ?x WHERE ?x IS-A Beer"))) {
    System.out.println(hit.iri());
}
use OxidDb\Client\Model\QueryRequest;

foreach ($oxid->queryAll(new QueryRequest('FIND ?x WHERE ?x IS-A Beer')) as $hit) {
    echo $hit->iri, "\n";
}
var total = 0;
await foreach (QueryHit hit in oxid.QueryAllAsync(
    new QueryRequest("FIND ?x WHERE ?x IS-A Beverage")))
{
    total++;
    Console.WriteLine(hit.Iri);
}
Console.WriteLine($"drained {total} hit(s) across all pages");
