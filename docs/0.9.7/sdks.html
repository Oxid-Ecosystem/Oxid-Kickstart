SDKs & Clients

Official clients for Python, TypeScript/JS, Go, Java, PHP, and .NET: thin, typed wrappers over the HTTP API. Pick your language, install one package, construct a client, and connect.

New in 0.9.7 All seven SDKs (Node, Web, Python, Go, Java, .NET, PHP) are at 0.9.7 in lockstep with the server: each gains a geoSearch method, the subproperty (role-hierarchy) axiom kind, distance_m on query hits, and the new routes (/reasoner/fragment, /admin/import, /admin/export, ?format= on OWL import). The wire contract is byte-stable apart from the new routes and fields, so a 0.9.6 client still works against a 0.9.7 server; see the Changelog for the full 0.9.6 → 0.9.7 difference.

Which client?

Every official Oxid-DB client is transport-only. It speaks the same JSON HTTP wire protocol documented on the HTTP API page, nothing more. There is no embedded database, no reasoner, and no vector index inside the client library: reasoning, hybrid query planning, and vector search all run server-side in the oxd-server process. The client just marshals your calls into requests and deserializes the responses into typed models.

Because they are thin wrappers, all six clients expose the same logical surface (see Operation coverage below) and target the same base URL, https://85cfad134a4a.oxid-db.com in every example on this page. Choose the one that matches your stack; there is no functional lock-in.

Python has two packages: don't confuse them oxiddb-client (import oxiddb_client) is the remote HTTP client documented on this page: it talks to a running server. Its sibling oxiddb is a separate, embedded package: native PyO3 bindings that run the whole database in-process, with no server at all. Same logical surface, different constructor. See The embedded Python option for when to pick each.

Connect & first call

There is no connect() method in any client. Each SDK is stateless HTTP: you construct a client (which opens no connection, since construction is lazy) and then make your first real call. To confirm the server is reachable and ready, probe it explicitly with health() (a plain liveness ping, always HTTP 200) or ready() (readiness, which reports 503 until the ontology is classified).

Construct a client

Pass the base URL (for example https://85cfad134a4a.oxid-db.com), an optional bearer token, and an optional timeout. Authentication is off by default, so the token is optional until you enable it. 

from oxiddb_client import OxidDB

# No connect() factory - construct directly; the client is lazy.
with OxidDB("https://85cfad134a4a.oxid-db.com", auth="my-token", timeout=30.0) as db:
    print(db.health())   # {"status": "ok"}
import { OxidClient } from "@oxiddb/node";

// No connect() - construct then probe with a liveness ping.
const db = new OxidClient({ baseUrl: "https://85cfad134a4a.oxid-db.com" });
const h = await db.health(); // { status: "ok" }
console.log(h.status);
package main

import (
	"context"
	"log"
	"time"

	oxid "github.com/moonlight-array/oxid-go"
)

func main() {
	client, err := oxid.New("https://85cfad134a4a.oxid-db.com",
		oxid.WithBearerToken(""),         // auth off by default on loopback
		oxid.WithTimeout(30*time.Second),
	)
	if err != nil {
		log.Fatal(err)
	}
	defer client.Close()

	h, err := client.Health(context.Background())
	if err != nil {
		log.Fatalf("health: %v", err)
	}
	log.Println("status:", h.Status)
}

Probe readiness

ready() returns the body for both HTTP 200 (ready) and 503 (not-yet-classified) rather than throwing on 503, so you can inspect why the server isn't ready. A freshly loaded ontology becomes ready once it has been classified: branch on the status and call classify() if needed. 

curl -s https://85cfad134a4a.oxid-db.com/ready
with OxidDB("https://85cfad134a4a.oxid-db.com") as db:
    status = db.ready()
    print(status.get("ready"))
const r = await db.ready();
if (r.status === "ready") {
  console.log(`up ${r.uptime_seconds}s, ${r.checks.individuals} individuals`);
} else {
  console.warn("not ready yet - run classify() first");
}
r, err := client.Ready(ctx)
if err != nil {
	log.Fatalf("ready: %v", err)
}
// r.Status is "ready" (200) or "not_ready" (503).
if r.Status != "ready" {
	log.Printf("not ready yet: classified=%v consistent=%v",
		r.Checks.ClassificationCurrent, r.Checks.Consistent)
}
Health.ReadyResponse r = oxid.ready();
if (!"ready".equals(r.status())) {
    // r.checks() carries databaseLoaded / classificationCurrent / consistent
    oxid.classify();   // e.g. classify to become ready
}
$ready = $oxid->ready();                         // GET /ready (200 or 503 both parsed)
echo $ready->status, "\n";                       // "ready" | "not_ready"
echo $ready->version, "\n";
printf("uptime: %.1fs\n", $ready->uptimeSeconds);
ReadyResponse ready = await oxid.ReadyAsync();
Console.WriteLine($"{ready.Status} - {ready.Checks.Classes} classes, " +
                  $"{ready.Checks.Individuals} individuals, classified={ready.Checks.ClassificationCurrent}");

Run your first query

Once the server is ready, run an OxQL statement. Every client posts the query to POST /query and hands you back a typed page of results. 

curl -s -X POST https://85cfad134a4a.oxid-db.com/query \
  -H 'Content-Type: application/json' \
  -d '{"query":"FIND ?x WHERE ?x IS-A Lager LIMIT 20"}'
with OxidDB("https://85cfad134a4a.oxid-db.com") as db:
    page = db.query("FIND ?x WHERE ?x IS-A Beer LIMIT 20")
    for hit in page.get("results", []):
        print(hit["iri"])
const page = await db.query({ query: "FIND ?x WHERE ?x IS-A Beer LIMIT 20" });
console.log(page.results.map((r) => r.iri));
console.log(page.total_count);

Operation coverage

All six clients cover the full logical surface, but not always with a method by the same name. The table below is honest about that: ✅ means the SDK ships a first-class method (or, for connect and vector_search, the idiomatic construct), and a cell marked HTTP only would mean you must call the raw endpoint directly. Two rows deserve a footnote:

  • connect has no method in any client: you construct the client and probe with health()/ready() (see above).
  • vector_search has no method by that name either: every language expresses nearest-neighbour search as OxQL NEAR ?x TO [...] via query(), and/or an individualSimilar() call for reference-vector search. Both count as ✅ for the idiomatic path.
  • geo_search is likewise idiomatic in every language through the OxQL WITHIN / SORT DISTANCE forms via query(). Every SDK at 0.9.7 additionally ships a first-class geoSearch(collection, request) method over the typed POST /collections/{name}/geo-search route (see below).

New in 0.9.7: geo search & role hierarchies

Every SDK adds a first-class geoSearch(collection, request) method (Node first, the rest in the sdk-sync catch-up) over the typed POST /collections/{name}/geo-search route, together with three request/response types:

  • GeoSearchRequest { field, lat, lon, radius_m, nearest?, class? }
  • GeoSearchHit { iri, distance_m?, location? }
  • GeoSearchResponse { hits, count }
// Node / Web: geoSearch(collection, request)
const res = await db.geoSearch("breweries", {
  field: "location",
  lat: 52.3702,
  lon: 4.8952,
  radius_m: 5000.0,
  nearest: 5,          // optional: order nearest-first, cap to k
  class: "Brewery",    // optional: IS-A pre-filter
});
console.log(res.count, res.hits.map((h) => `${h.iri} @ ${h.distance_m}m`));

// The subproperty (role-hierarchy) axiom kind:
// AxiomKind now includes "subproperty"; AddAxiomRequest is
//   { kind, sub?, sup?, a?, b?, client_txn? }
await db.addAxiom({
  kind: "subproperty",
  sub: "https://ex.org/prop/brewedBy",
  sup: "https://ex.org/prop/producedBy",
});
use OxidDb\Client\Model\AddAxiomRequest;

// PHP ships a convenience constructor for the role-hierarchy kind.
$oxid->addAxiom(AddAxiomRequest::subproperty(
    'https://ex.org/prop/brewedBy',
    'https://ex.org/prop/producedBy',
));

In every language, the same radius search is also expressible without a dedicated method by running the OxQL WITHIN / SORT DISTANCE forms through the ordinary query() method (for example ?x.location WITHIN 5km OF (52.3702, 4.8952)). Geo results carry a distance_m field. In the typed clients (Go, Java, .NET, PHP) that field is only surfaced from client version 0.9.7 onward: an older typed client deserializes the hit into a closed model and silently drops distance_m.

Error handling

Transport and validation failures (a bad URL, a 400 for a malformed body, a 413 for a body over the 32 MiB cap, a 409 for a duplicate collection) surface as the client's normal error type: a raised exception in Python/PHP/C#, a returned error in Go, a thrown exception in TypeScript/Java. Catch and branch on the HTTP status as usual (for example, ignore a 409 when creating a collection idempotently).

In particular, a /query whose explicit LIMIT exceeds max_query_rows (default 100000) is a 400 carrying an error message, not an empty results page. Because the SDK raises, you cannot mistake the rejection for zero matches. A raw HTTP client must check the status itself: page a large extent with OFFSET/next_cursor instead of one oversized LIMIT.

A vetoed write is not an error: branch on the boolean Governed writes that pass through the reasoner's commit gate (for example an assert_typed / add_axiom that would make an individual both a Beer and a Wine when those are disjoint) return HTTP 200 whether they committed or were vetoed. The client will not raise. Inspect the response's committed / ok field and, on a veto, read the reported violations. Do not rely on catching an exception to detect a rejected write.

The embedded Python option

Python is the only language with a second, fundamentally different client. Alongside the remote oxiddb-client on this page, there is oxiddb: native PyO3 bindings that embed the entire database in your Python process. No server, no network, no HTTP: you call the engine directly.

oxiddb-client (remote) oxiddb (embedded)
What it is Pure-Python HTTP client (httpx) Native PyO3 bindings over the Rust engine
Needs a running server? Yes, talks to oxd-server No, runs in-process
Constructor OxidDB("https://85cfad134a4a.oxid-db.com") oxiddb.OxidDB(dim=4)
Best for Sharing one server across apps, agents, and the Web UI; production deployments Notebooks, scripts, tests, and single-process embedding with zero infrastructure

Reach for the remote client whenever more than one process (or the Web UI, or an MCP agent) must see the same data, or when the database is deployed as a service. Reach for the embedded package when you want a self-contained database inside one Python process: a data-science notebook, a test harness, or a script that owns its own store on disk. Both expose the same logical surface (ontology axioms, hybrid OxQL, vector search, KGE), so moving between them is mostly a constructor change.

This page documents the remote client All the code above uses oxiddb-client. The embedded oxiddb package is a separate install and API surface (in-process methods like db.save("beers.oxd") / oxiddb.OxidDB.load(...)); its bindings are built from source with maturin. Do not mix the two constructors in one file.

Note on browser use

For front-end code, use @oxiddb/web, the browser sibling of @oxiddb/node. Import OxidWebClient and construct it the same way: new OxidWebClient({ baseUrl: "https://85cfad134a4a.oxid-db.com" }). The wire types are byte-identical to the Node client and there is still no connect step. The differences are browser-shaped: there is no environment-variable layer (precedence is explicit constructor args, then defaults), POST requests are not auto-retried, and an OxidCorsError is raised for cross-origin fetch rejections. Loopback and same-origin requests work with no server-side CORS configuration.
