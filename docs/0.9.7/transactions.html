Transactions

Group multiple writes into one atomic, consistency-aware unit: several inserts, axioms, and document changes that all land together or all fail together.

Autocommit vs explicit

Every single write you make against Oxid-DB is its own transaction. When you POST /insert, POST /subclass, or push a document, the server opens a transaction, applies the change, and commits it before returning. This is autocommit. You never see the transaction; you just get your result.

Reach for an explicit transaction when several writes must succeed or fail as a group. Classic case: you insert a new individual, add the subclass axiom it depends on, and upsert its vector. If any step fails, you do not want a half-written entity left behind. An explicit transaction stages all three and commits them in one atomic step, or rolls the whole thing back so nothing is written.

Note Internally, mutations funnel through a single serialization point and hold logical locks until commit or abort, giving serializable isolation. You get ACID semantics whether you use autocommit or an explicit transaction. The explicit form just lets you span more than one write.

The transaction lifecycle

An explicit transaction has three phases:

  1. Begin

    POST /txn opens a transaction and returns a txn_id. Capture that id: you interpolate it into every subsequent path.

  2. Stage writes

    Run your mutations against the id: POST /txn/{id}/insert, /subclass, /disjoint, /upsert-vector, /object-property, /annotation, and the document mutators (/insert-document, /update-document, /delete-document, /bulk-insert-documents). Nothing is visible to other readers yet.

  3. Commit or roll back

    POST /txn/{id}/commit applies and persists everything atomically; POST /txn/{id}/rollback discards all staged work. Either way the id is settled and cannot be reused.

The full flow with cURL. Note that step 1 returns the txn_id you must substitute into steps 2 and 3. Here the id happens to be 1:

bash
# 1. Begin - capture txn_id from the response body.
curl -s -X POST https://85cfad134a4a.oxid-db.com/txn
# => {"txn_id": 1}

# 2. Stage writes against that id (repeat as needed).
curl -s -X POST https://85cfad134a4a.oxid-db.com/txn/1/insert \
  -H 'Content-Type: application/json' \
  -d '{"iri":"Heineken","class":"Pilsner","vector":[0.4,0.2,0.1,0.4]}'
# => {"term": 76}

curl -s -X POST https://85cfad134a4a.oxid-db.com/txn/1/subclass \
  -H 'Content-Type: application/json' \
  -d '{"sub":"Pilsner","sup":"Beer"}'
# => {"ok": true}

# 3. Commit - everything above lands together.
curl -s -X POST https://85cfad134a4a.oxid-db.com/txn/1/commit
# => {"ok": true, "txn_id": 1, "state": "committed"}

# ...or discard it all instead:
# curl -s -X POST https://85cfad134a4a.oxid-db.com/txn/1/rollback
# => {"ok": true, "txn_id": 1, "state": "aborted"}

A transactional insert returns {"term": <n>}, the interned term id of the new individual. The iri must be new in a transaction insert (there is no widening of an existing individual on this path). The SDKs wrap all of this in a scope helper so you rarely touch the id by hand: the block commits when it returns cleanly and rolls back if it throws. 

# 1. Begin - capture txn_id from the response.
curl -s -X POST https://85cfad134a4a.oxid-db.com/txn
# => {"txn_id": 1}

# 2. Mutate inside the txn (interpolate the id).
curl -s -X POST https://85cfad134a4a.oxid-db.com/txn/1/insert \
  -H 'Content-Type: application/json' \
  -d '{"iri":"Heineken","class":"Pilsner","vector":[0.4,0.2,0.1,0.4]}'

# 3. Commit.
curl -s -X POST https://85cfad134a4a.oxid-db.com/txn/1/commit
with OxidDB("https://85cfad134a4a.oxid-db.com") as db:
    with db.transaction() as txn:
        term = txn.insert("Heineken", "Pilsner", vector=[0.4, 0.2, 0.1, 0.4])
        txn.add_subclass("Pilsner", "Beer")
        sp = txn.savepoint()
        txn.insert_document("beers", {"name": "Heineken"})
        txn.rollback_to(sp)     # undo just the document
    # committed here on clean exit
// Auto commit/rollback.
await db.transaction(async (txn) => {
  await txn.addSubclass({ sub: "Pilsner", sup: "Beer" });
  const term = await txn.insert({ iri: "Corona", class: "Pilsner", vector: [0.2, 0.2, 0.1, 0.3] });
  await txn.addObjectProperty({ subject: "Corona", property: "brewedBy", object: "GrupoModelo" });
  return term; // resolve → commit; throw → rollback
});
err := client.Transaction(ctx, func(tx *oxid.Txn) error {
	// tx.Insert returns the interned Term (int); iri must be new.
	if _, err := tx.Insert(ctx, oxid.TxnInsertRequest{
		IRI:    "PortSaintNick",
		Class:  "Stout",
		Vector: []float64{0.8, 0.2, 0.1, 0.9},
	}); err != nil {
		return err // triggers rollback
	}
	return tx.AddSubclass(ctx, oxid.SubclassRequest{Sub: "Stout", Sup: "Beer"})
})
if err != nil {
	log.Fatalf("transaction rolled back: %v", err)
}
log.Println("transaction committed")
// Closure form - commits on return, rolls back on throw.
oxid.transaction(tx -> {
    tx.insert(Txn.TxnInsertRequest.of("Duvel", "Beer"));   // returns interned Term (int)
    tx.addSubclass(new Mutation.SubclassRequest("Tripel", "Beer"));
    return null;
});

// Manual form - try-with-resources; close() rolls back if not committed.
try (Transaction tx = oxid.beginTransaction()) {
    int term = tx.insert(Txn.TxnInsertRequest.of("Chimay", "Beer"));
    tx.addSubclass(new Mutation.SubclassRequest("Quadrupel", "Beer"));
    tx.commit();
}
use OxidDb\Client\Transaction;
use OxidDb\Client\Model\TxnInsertRequest;

// Scope helper - commits on success, rolls back on throw.
$oxid->transaction(function (Transaction $tx): void {
    $tx->insert(new TxnInsertRequest('Duvel', 'Beer', vector: [0.2, 0.4, 0.1, 0.3], collection: 'demo_beers'));
    $tx->insert(new TxnInsertRequest('Chimay', 'Beer'));
});

// Manual control - begin / rollback explicitly.
$tx = $oxid->begin();
$term = $tx->insert(new TxnInsertRequest('Ghost', 'Beer'));  // returns interned Term id
$rollback = $tx->rollback();                                 // Ghost discarded
// Callback form - auto commit/rollback.
await oxid.TransactionAsync(async tx =>
{
    await tx.InsertAsync(new TxnInsertRequest("Corona", "Pilsner",
        Vector: new[] { 0.7, 0.2, 0.4, 0.1 }, Collection: "beers"));
    await tx.AddSubclassAsync(new SubclassRequest("Pilsner", "Beer"));
    await tx.AddObjectPropertyAsync("Corona", "brewedBy", "GrupoModelo");
    // returns → COMMIT ; throws → ROLLBACK (exception re-raised)
});

// Manual form with a savepoint.
await using Transaction tx = await oxid.BeginTransactionAsync();
await tx.InsertAsync(new TxnInsertRequest("Maybe", "Stout"));
int sp = await tx.SavepointAsync();
await tx.InsertAsync(new TxnInsertRequest("Discarded", "Stout"));
await tx.RollbackToAsync(sp);   // drop "Discarded", keep "Maybe"
await tx.CommitAsync();

Savepoints & annotations

A savepoint is a marker inside an open transaction that you can roll back to without abandoning the whole thing. Call POST /txn/{id}/savepoint to create one (it returns {"ok": true, "savepoint": <n>}), then POST /txn/{id}/rollback-to/{savepoint} to undo everything staged after that marker while keeping the work done before it ({"ok": true, "rolled_back_to": <n>}). This is useful for speculative writes: stage something, check it, and drop just that part if it does not work out (see the Python and C# savepoint examples above).

Annotations attach metadata (labels, comments) to an entity as part of the same transaction via POST /txn/{id}/annotation. Because it is transactional, the annotation lands atomically with the individual it describes, with no window where the entity exists but its label does not.

bash
# Inside an open txn (id = 1): mark a savepoint, then undo back to it.
curl -s -X POST https://85cfad134a4a.oxid-db.com/txn/1/savepoint
# => {"ok": true, "savepoint": 1}

curl -s -X POST https://85cfad134a4a.oxid-db.com/txn/1/rollback-to/1
# => {"ok": true, "rolled_back_to": 1}

Consistency on commit

A plain /txn/{id}/commit does NOT auto-reject an inconsistent write Committing an explicit transaction applies and persists its staged mutations; it does not run the EL⊥ consistency check as a gate. If you need commit-time rejection (for example, to stop a write that would assert something is both a Beer and a Wine when those are declared disjoint), use a gated route instead: POST /entities with "gate": true, POST /actions/assert-typed, or POST /actions/add-axiom. These run the reasoner over the staged write and commit only if the ontology stays consistent, otherwise they write nothing and return the violation list. You can also check a write speculatively with POST /consistency/check before committing, or run POST /classify afterwards to get a consistency verdict (a verdict, not a rollback). See Reasoning (OWL 2 EL⊥) for what the consistency check actually decides.

Honest notes

  • txn_id is not deterministic. Do not hard-code or predict it. Explicit transactions share the same id counter as autocommit writes, so the number you get depends on concurrent activity. Always read it back from the POST /txn response and interpolate it into later paths.
  • Commit is atomic, not a reasoner gate. As above, a bare commit persists whatever you staged. Consistency enforcement is opt-in through the gated routes; the generic transaction path trusts your writes.
  • What is transactional. All the /txn/{id}/… mutators share one transaction: individual inserts, subclass/disjoint/object-property/annotation axioms, vector upserts, and the document mutators. The compound POST /entities (classes + properties + one vector) and an atomic:true POST /entities/batch are each wrapped in a single transaction too.
  • What is not fully atomic. POST /collections/provision is a best-effort create-then-compensate saga, not a single transaction. A crash mid-way can leave an inert orphan (an identical re-POST self-heals). A default atomic:false /entities/batch is best-effort per row, reporting each in results[], not all-or-nothing.
  • Idempotency. Send an Idempotency-Key header on POST /txn/* calls to safely retry after a network hiccup without double-applying. An unknown or already-settled txn_id returns 404 {"code":"NOT_FOUND"}.
  • Single-writer serialization. Writes across different collections hold non-conflicting logical locks but still serialize through one apply point; true parallel physical writes are a deferred step. Concurrency is correct and serializable, not yet horizontally parallel.
