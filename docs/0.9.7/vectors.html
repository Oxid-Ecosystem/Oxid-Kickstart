Vector Search

How Oxid-DB stores embeddings and finds nearest neighbors: the neural half of the model, sitting next to the reasoner over one shared identity space.

What vector search is

A vector (or embedding) is just a list of numbers that places an entity as a point in space. Each number captures one characteristic, so entities that are alike end up close together and entities that are different end up far apart. Finding "things like this" becomes a geometry problem: locate the points nearest to a query point.

For the examples on this page we use a toy 4-dimensional beverage embedding whose axes are bitterness, sweetness, acidity, alcohol. A very bitter, dry, moderately strong beer like an IPA looks like [0.9, 0.0, 0.0, 0.5]; a sweet, acidic, low-alcohol white wine sits far away at [0.0, 0.8, 0.6, 0.2]. Real embeddings are far wider (384-D from MiniLM, 1024-D from bge/e5-large, or 1536/3072-D from OpenAI), but the idea is identical at any dimension.

Oxid-DB stores one vector per individual, in a named collection. Because an individual is the same interned identity the reasoner and document store use, a vector, an ontology class, and a KGE entity that denote the same thing are literally the same entity, with no join and no separate ID space. That shared identity is what makes the hybrid symbolic + vector queries on the next page possible.

Distance metrics

To rank "nearest" you need a distance metric, a formula that turns two vectors into a single closeness number. Oxid-DB supports four, chosen per collection at creation time. For all four, lower means more similar.

MetricCanonical nameWhat it measuresUse it when
Cosine default cosine The angle between two vectors: direction only, magnitude ignored. Query vectors are normalized before search. Text embeddings and any normalized data. The right default for most workloads.
Euclidean l2 Straight-line distance between the two points. Oxid returns the squared L2. Ranking is identical to non-squared, but absolute values differ from engines that return the square root. Spatial data or raw feature values where magnitude matters.
Inner product ip The (negated) dot product, so it sorts the same "lower = closer" way as the others. Rewards vectors that reinforce each other. Pre-normalized embeddings and recommendation-style scoring.
Manhattan manhattan Sum of the per-axis absolute differences, a grid / taxicab distance (L1). Interpretable numeric features where each axis is independent.
Casing matters on the wire The canonical metric name is lowercase: send "cosine", "l2", "ip", or "manhattan". Capitalised forms like "Cosine" are not the canonical spelling. Omit the field entirely and the collection defaults to cosine.

Creating a vector collection

A collection fixes two things up front: the vector dimensions and the metric. Every vector you later add to it must have exactly that many dimensions. The wire field is dimensions (not dim), and the metric defaults to cosine when omitted.

curl -s -X POST https://85cfad134a4a.oxid-db.com/collections \
  -H 'Content-Type: application/json' \
  -d '{"name":"beers","dimensions":384,"metric":"cosine","quantization":"none"}'
with OxidDB("https://85cfad134a4a.oxid-db.com") as db:
    db.create_collection("beers", dim=4, metric="cosine")
    # creating the same shape again returns 409 - catch OxidHttpError, ignore 409
// Field is `dimensions` (not `dim`).
await db.createCollection({ name: "beers", dimensions: 4, metric: "cosine" });

const list = await db.collections();
console.log(list.collections.map((c) => `${c.name}/${c.dimensions}`));
// The field is `Dimensions` (not `dim`). Metric: cosine | l2 | ip | manhattan.
if err := client.CreateCollection(ctx, oxid.CreateCollectionRequest{
	Name:       "beverages",
	Dimensions: 4,        // 4-dim vectors
	Metric:     "cosine",
}); err != nil {
	log.Fatalf("create collection: %v", err)
}
// 4-dim vector collection for beverage embeddings (field is `dimensions`, not `dim`)
oxid.createCollection(Collections.CreateCollectionRequest.of("beverages", 4));
use OxidDb\Client\Model\CreateCollectionRequest;

// The field is `dimensions`, not `dim`.
$oxid->createCollection(new CreateCollectionRequest('demo_beers', 4, 'cosine'));
// A 4-dim collection for beverage vectors (wire key is `dimensions`, not `dim`).
await oxid.CreateCollectionAsync(new CreateCollectionRequest("beers", 4));

// With an explicit metric:
await oxid.CreateCollectionAsync(new CreateCollectionRequest("beers", 4, Metric: "cosine"));

Collections take dimensions up to a configured maximum (default 4096), which comfortably covers every common embedding width. Re-creating a collection with the same shape is a safe no-op; asking for a different shape returns 409.

Adding vectors

Vectors ride along on the individual: you insert an entity's identity, its class, and its vector in one call. The vector's length must equal the collection's dimensions, or the insert is rejected.

curl -s -X POST https://85cfad134a4a.oxid-db.com/insert \
  -H 'Content-Type: application/json' \
  -d '{"iri":"Heineken","class":"Lager","vector":[0.6,0.3,0.1,0.6]}'
with OxidDB("https://85cfad134a4a.oxid-db.com") as db:
    res = db.insert("Heineken", "Pilsner", vector=[0.4, 0.2, 0.1, 0.4])
    # res: {"iri": "Heineken", ...}
// Identity is `individual` (or alias `iri`); membership is `class` (or `classes[]`).
await db.insert({ individual: "Heineken", class: "Pilsner", vector: [0.4, 0.2, 0.1, 0.4] });
await db.insert({ iri: "Guinness", class: "Stout", vector: [0.9, 0.3, 0.0, 0.7] });
res, err := client.Insert(ctx, oxid.InsertRequest{
	Individual: "PilsnerUrquell",
	Class:      "Pilsner",
	Vector:     []float64{0.9, 0.1, 0.0, 0.2}, // 4-dim
})
if err != nil {
	log.Fatalf("insert: %v", err)
}
_ = res
// Simple: individual + single class (no vector)
oxid.insert(Mutation.InsertRequest.of("Heineken", "Pilsner"));

// Full form: individual + class + 4-dim vector into a named collection
oxid.insert(new Mutation.InsertRequest(
        "Guinness", null, "Stout", null, null,
        new double[] {0.1, 0.2, 0.3, 0.4}, "beverages"));
use OxidDb\Client\Model\InsertRequest;

$res = $oxid->insert(new InsertRequest(
    'Heineken',
    'Pilsner',
    vector: [0.6, 0.3, 0.1, 0.6],
    collection: 'demo_beers',
));
echo $res->ok ? "inserted\n" : "failed\n";
// Positional (single class) - emits {"individual","class",...}
OkResponse ok = await oxid.InsertAsync(new InsertRequest(
    "Heineken", "Pilsner",
    Vector: new[] { 0.9, 0.1, 0.5, 0.2 }));

// Multi-class via the aliases - emits {"iri","classes":[...]}
await oxid.InsertAsync(new InsertRequest(
    Individual: null, Class: null,
    Iri: "Guinness", Classes: new List<string> { "Stout" },
    Vector: new[] { 0.1, 0.8, 0.3, 0.4 }));
Dimensions must match A 4-D collection accepts only 4-D vectors; a mismatched length is a loud error, not a silent truncation. If you would rather send text and let the server embed it, use the text field instead of vector. That path is covered on the Ontologies and Hybrid Queries pages. Note that /insert writes exactly identity + class(es) + one vector or text; to also attach properties, use the compound POST /entities endpoint.

Nearest-neighbor search

There are two ways to ask for neighbors. The first is OxQL NEAR ?x TO [...] over POST /query, which is hybrid-capable: you can combine it with an IS-A class filter in the same statement. The second is a by-reference lookup, GET /individuals/{iri}/similar, which finds the nearest neighbors of an existing entity (its own stored vector becomes the query, and the entity itself is excluded).

curl -s -X POST https://85cfad134a4a.oxid-db.com/query \
  -H 'Content-Type: application/json' \
  -d '{"query":"FIND ?x WHERE ?x IS-A Beer AND NEAR ?x TO [0.9,0.1,0.5] LIMIT 5"}'
with OxidDB("https://85cfad134a4a.oxid-db.com") as db:
    # (1) literal query vector (dims must match the collection)
    hits = db.query("FIND ?x WHERE NEAR ?x TO [0.4, 0.2, 0.1, 0.4] LIMIT 5")
    for h in hits.get("results", []):
        print(h["iri"], h.get("score"))

    # (2) nearest neighbours of an existing individual
    sim = db.individual_similar("Heineken", k=3, collection="default")
    print([h["iri"] for h in sim.get("results", [])])
// 1) OxQL NEAR over /query - hybrid-capable (combine with IS-A). Rows carry `score`.
const near = await db.query({
  query: "FIND ?x WHERE ?x IS-A Beer AND NEAR ?x TO [0.9, 0.1, 0.5, 0.7] LIMIT 5",
});
for (const hit of near.results) console.log(hit.iri, hit.score);

// 2) By reference individual - top-k neighbors of an existing IRI.
const sim = await db.individualSimilar("Guinness", { k: 3, collection: "default" });
for (const hit of sim.results) console.log(hit.iri, hit.score);
// Hybrid: Beers nearest a 4-dim probe vector, top 5.
oxql := oxid.NewQueryBuilder().
	Find("x").
	IsA("Beer").
	Near([]float64{0.9, 0.1, 0.0, 0.2}).
	Limit(5).
	ToOxql()
res, err := client.Query(ctx, oxid.QueryRequest{Query: oxql})
if err != nil {
	log.Fatalf("vector search: %v", err)
}
for _, hit := range res.Results {
	if hit.Score != nil {
		log.Printf("%s score=%.4f", hit.IRI, *hit.Score)
	}
}

// Neighbors of a known individual:
sim, err := client.IndividualSimilar(ctx, "PilsnerUrquell",
	&oxid.SimilarOpts{K: 5, Collection: "default"})
_, _ = sim, err
// 1) By reference IRI - 3 nearest neighbours of Heineken in the default collection
Individuals.IndividualSimilarResponse sim = oxid.individualSimilar("Heineken", 3, null);
for (Individuals.SimilarHit hit : sim.results()) {
    System.out.println(hit.iri() + " " + hit.score());
}

// 2) By raw vector - via OxQL NEAR
String oxql = new QueryBuilder()
        .find("x").isA("Beer")
        .near(new double[] {0.9, 0.1, 0.5, 0.2})
        .limit(5)
        .toOxql();
Query.QueryResponse hits = oxid.query(Query.QueryRequest.of(oxql));
use OxidDb\Client\Model\QueryRequest;

// 1) OxQL NEAR over POST /query - literal query vector, hybrid-capable.
$near = $oxid->query(new QueryRequest(
    'FIND ?x WHERE ?x IS-A Beer AND NEAR ?x TO [0.9, 0.1, 0.5, 0.2] LIMIT 5'
));
foreach ($near->results as $hit) {
    printf("  %s  score=%s\n", $hit->iri, $hit->score);
}

// 2) By-reference nearest neighbours: GET /individuals/{iri}/similar
$similar = $oxid->individualSimilar('Heineken', k: 3, collection: 'demo_beers');
echo "reference={$similar->reference} collection={$similar->collection}\n";
// Hybrid: a Beer near this 4-dim probe vector, top 5.
string oxql = new QueryBuilder()
    .Find("x").IsA("Beer").Near(new[] { 0.9, 0.1, 0.5, 0.2 }).Limit(5)
    .ToOxql();
QueryResponse hits = await oxid.QueryAsync(new QueryRequest(oxql));
foreach (QueryHit hit in hits.Results)
{
    Console.WriteLine($"{hit.Iri}  score={hit.Score}");
}

// Nearest neighbours of an existing individual.
IndividualSimilarResponse sim = await oxid.IndividualSimilarAsync("Heineken", k: 3);
foreach (SimilarHit s in sim.Results)
{
    Console.WriteLine($"{s.Iri}  {s.Score}");
}

A pure, standalone NEAR query asks for the five beers whose vectors are closest to a bitter, dry, medium-alcohol profile:

oxql
FIND ?x WHERE ?x IS-A Beer NEAR ?x TO [0.9,0.0,0.0,0.5] LIMIT 5

Each returned row carries a score and the results come back ranked, most-similar first. The literal vector must match the collection's dimensions. Because the filter and the search live in one statement, the class filter is pushed into the graph walk rather than applied afterward. The mechanics of that are on the Hybrid Queries page.

Under the hood: HNSW + ef_search

Comparing a query against every stored vector is exact but slow at scale. Oxid-DB instead builds an HNSW index, a Hierarchical Navigable Small World graph (Malkov & Yashunin, 2016). Vectors become nodes in a layered graph of "small world" links; a search enters at the top layer and greedily hops toward the query, dropping down layers as it homes in. That makes nearest-neighbor lookup roughly logarithmic instead of linear, and the build is deterministic by default (fixed seed).

HNSW is the only user-selectable index. IVF-PQ is recognised by the API but refused at collection creation (its training path is unimplemented), so requesting it is a loud error, not a silent fallback. (An internal brute-force index exists, but only as the exact ground-truth oracle for recall gates and for tiny filtered scans; it is not a user index choice.)

Every approximate index trades recall against speed, and HNSW exposes that dial as ef_search: how many candidates the search keeps "in flight." Bigger ef_search explores more of the graph: higher recall, more work per query. The build-time default is 64, and you can override it per query in OxQL with EF <n> when a particular request needs more (or less) breadth:

oxql
FIND ?x WHERE NEAR ?x TO "crisp pale lager" EF 200 LIMIT 10

Raising EF for a single high-stakes query recovers recall without permanently paying for it on every request. (The NEAR ... TO "text" form auto-embeds the phrase, so it needs an embedder configured.)

Scale: quantization & off-RAM

Two mechanisms let a collection hold far more vectors than fit in memory, and both are on by default for ingested vectors.

First, SQ8 scalar quantization: the resident HNSW graph stores each dimension as a single u8 code (~1 byte/dim) instead of a 4-byte f32. Search runs over the compact codes, then candidates are reranked against exact vectors so accuracy holds. SQ8 is the production default. (A 1-bit Binary tier also exists but is off the default ladder: it needs far more over-fetch to hit the same recall bar on real embeddings.)

Second, off-RAM cold-f32 via memory mapping, which is default-ON in the shipped binary. The exact f32 vectors are spilled to a read-only mmap file on disk; the only resident cost is a small per-vector offset table, and exact vectors page-fault in on demand for reranking. So the resident SQ8 graph stays small while the exact copies live cold on disk. This is how Oxid-DB serves datasets larger than RAM.

Measured recall, and honest positioning

The SQ8 recall gate holds quantization within ≤ 1% absolute recall@10 of the exact-f32 HNSW baseline. On real embeddings: 1024-D bge-large measures SQ8 recall@10 = 0.9970; at 1M vectors, 1536-D real OpenAI embeddings (DBpedia), cold-f32 + SQ8 + cosine, recall@10 = 0.9839 with reopen ~0.51 s and RSS ~6.8 GB. At 10M vectors, off-RAM residency is proven (~26 GiB peak RSS with ~61 GB of exact f32 staying on disk); recall is not claimed there because exact ground truth won't fit.

These numbers put the vector tier at parity with Qdrant and Weaviate, not ahead of them. HNSW + SQ8 quantization + four metrics + mmap cold storage is a shared best practice. Oxid-DB's differentiation is neurosymbolic: running this vector tier alongside an OWL 2 EL⊥ reasoner and KGE over one identity space, so a class filter can scope the search itself, not raw ANN throughput. (macOS latency figures are indicative only; published latency comes from Linux runs.)
