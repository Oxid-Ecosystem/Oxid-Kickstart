MCP Integration

Expose Oxid-DB to AI agents via the Model Context Protocol. A running assistant can query, reason over, and (under governance) write to your database through a small set of well-typed tools.

New in 0.9.7 Version 0.9.7 brings the tool count to 13: a new geo_search tool wraps the typed POST /collections/{name}/geo-search route (a deterministic-exact read), and the add_axiom tool now also covers the subproperty (role-hierarchy) kind. See the Changelog for the full 0.9.6 → 0.9.7 difference.
Managed while Oxid-DB is closed-source The MCP server is an opt-in add-on that ships alongside your managed Oxid-DB endpoint; you do not build or self-host it. This page documents the tools it exposes and how to point a client at it. When Oxid-DB opens up, this documentation will expand with in-depth guides for building and self-hosting the surface binary.

What is MCP?

The Model Context Protocol (MCP) is an open standard that lets an LLM-based assistant (Claude Code, Cursor, Continue, or a custom agent) call external systems through a uniform tool interface. Instead of pasting query results into a chat window by hand, the agent connects to an MCP server, discovers the tools it offers, and calls them directly. Oxid-DB ships such a server, so your assistant can talk to the database the same way it talks to any other MCP-enabled tool.

The Oxid-DB MCP server

The server lives in the crates/oxd-surface-mcp crate and is called Oxid Surface MCP. It is a thin adapter: it never links the Oxid-DB core directly, but instead talks to a running database over the ordinary HTTP API (for example https://85cfad134a4a.oxid-db.com). That separation means the MCP server can run in any process or container that can reach the database endpoint.

Through it, an agent can inspect the ontology and schema, run OxQL and natural-language queries, drill into individual entities, run the description-logic reasoner, aggregate over document collections, and, under a consistency gate, assert typed individuals, add axioms, train a KGE model, and predict links. The full list is in The tools below.

Note The MCP server is an opt-in surface: it is not part of the default database build, and enabling it is a deployment choice. Everything it can do, it does through the same governed HTTP API documented on the HTTP API page.

Transports

The link between the MCP client and the Oxid-DB MCP server can run over either of two transports. The handler, the tools, and the HTTP link to the database are identical in both; only the wire between client and server differs.

stdio (default)

With the default stdio transport, the client spawns the server as a child process and speaks MCP over standard input/output. This is what local agent runners (Claude Code, Cursor, and similar) use. The server's stdout is reserved for the MCP protocol stream; its own logs go to a rolling file, never to stdout.

Streamable HTTP

The opt-in Streamable HTTP transport serves the same handler on an HTTP listener, so networked clients connect over a URL instead of spawning a process. Enable it by setting the environment variable OXID_SURFACE_TRANSPORT=http. In local development the listener binds 127.0.0.1:7879 by default and serves the endpoint at path /mcp. On a managed instance, the MCP endpoint (when enabled) is shown in your instance dashboard.

bash
OXID_SURFACE_TRANSPORT=http     # stdio (default) | http
OXID_SURFACE_HTTP_BIND=127.0.0.1:7879   # listen address for the HTTP transport
OXID_SURFACE_HTTP_PATH=/mcp             # endpoint path for the HTTP transport

The HTTP endpoint validates the inbound Host header against a loopback-only allow-list by default (localhost, 127.0.0.1, ::1) as DNS-rebinding protection, mirroring the database's loopback-by-default posture. Override it for public hostnames with OXID_SURFACE_HTTP_ALLOWED_HOSTS.

The tools

The server registers exactly thirteen tools, always available. A fourteenth tool, ask, is advertised only when an LLM API key is configured (it delegates a multi-step natural-language question to a built-in agent loop). Each result carries an epistemic tier so an agent can tell exact ground truth from a governed write or a ranked hypothesis.

ToolTierPurpose
querydeterministic-exactRun an OxQL query: raw OxQL or natural language (LLM-translated); optional hydrate returns properties in one round-trip.
explaindeterministic-exactPlan an OxQL statement (strategy, selectivity, per-stage cardinalities); optional analyze also runs it for measured numbers.
classifydeterministic-exactRun the EL⊥ reasoner and return { consistent, violations }.
schemadeterministic-exactReturn the class list, individual count, vector collections, and classified/consistent flags.
entitydeterministic-exactFetch one individual's detail: asserted and inferred classes, properties, vectors; optional nearest-neighbour list.
ontologydeterministic-exactReturn the class hierarchy, axioms, and per-individual inferred classes.
aggregatedeterministic-exactStructured aggregation over a document collection: count/sum/avg/min/max/count_distinct with optional group-by and HAVING.
geo_searchdeterministic-exactRadius search over a GeoPoint field, wrapping POST /collections/{name}/geo-search; each hit carries a distance_m.
check_consistencydeterministic-exactSpeculatively test proposed assertions against the reasoner without mutating the database.
assert_typedgoverned-writeInsert a typed individual; commits only if the staged ontology stays coherent, otherwise the change is vetoed.
add_axiomgoverned-writeAdd a subclass, disjoint, or subproperty (role-hierarchy) axiom; commits only if the staged ontology stays coherent.
train_embeddingsgoverned-writeTrain and persist a KGE model so predict_links can rank from it.
predict_linksdeterministic-inferentialKGE link prediction from the persisted model; each candidate is annotated with the reasoner's veto.
Tip The four governed-write and deterministic-inferential tools are the differentiator: an agent's proposed write (assert_typed, add_axiom) or predicted link (predict_links) is checked against the reasoner before it lands, so an assistant cannot, say, assert that duvel is both a Beer and a Wine when those classes are disjoint. See Reasoning and Link Prediction.

Connecting a client

Register the server with your MCP client the same way you would any other. For a stdio client (for example, a .mcp.json in a project root, or a global ~/.claude.json), point it at the server binary and pass the database URL through the env block:

json
{
  "mcpServers": {
    "oxid-surface": {
      "type": "stdio",
      "command": "/absolute/path/to/oxd-surface-mcp",
      "env": {
        "OXID_SURFACE_DB_URL": "https://85cfad134a4a.oxid-db.com"
      }
    }
  }
}

For a client using the Streamable HTTP transport, point it at the MCP endpoint URL instead; no process is spawned. The example below uses the local development endpoint; on a managed instance, use the MCP endpoint shown in your instance dashboard:

json
{
  "mcpServers": {
    "oxid-surface": {
      "type": "http",
      "url": "http://localhost:7879/mcp"
    }
  }
}

Once connected, the assistant can discover and call the tools by name. For example, ask it to "use the schema tool and list the classes," or "run query with FIND ?x WHERE ?x IS-A Beer LIMIT 5." Point a second registration at a different OXID_SURFACE_DB_URL to expose more than one database at once.

Honest notes

  • Authentication is inherited from the database. The HTTP endpoint probes the database's auth mode at startup. When Oxid-DB auth is enabled, every request to /mcp (including the initialize handshake) must carry a valid Authorization: Bearer <token> (an oxk_ API key or an oxs_ session token), or it is rejected with 401 before the JSON-RPC layer runs. This is the inbound credential the client presents; the outbound credential the server sends to the database on its own calls is set separately via OXID_SURFACE_API_TOKEN. The stdio transport is never gated; trust there is the parent process that spawned it.
  • Exposure gate. The HTTP server refuses to start on a non-loopback bind while auth is disabled, unless you explicitly set OXID_SURFACE_ALLOW_INSECURE (which logs a loud warning and is not for production).
  • No native TLS in the MCP binary yet. For confidentiality on a public bind, terminate TLS at a reverse proxy in front of /mcp. (The database server itself does have native TLS; see Authentication.)
  • The ask tool is conditional. It only appears when an LLM key is configured; without one, the server boots normally with the thirteen direct tools and simply omits ask.
  • Everything routes through the HTTP API. The MCP tools are governed by the same roles and consistency gates as any other client. There is no privileged back door: an agent can do only what the presented token is authorised to do.
