Web UI

An embedded browser console for exploring your data. Open a browser at https://85cfad134a4a-ui.oxid-db.com/app and you're in. No install, no build step, no extra service to run.

What it is

The Web UI is a modern Vue 3 single-page app (the web-next bundle) that ships inside the server binary. There is nothing separate to download or deploy: when the server starts with the UI enabled (the default), it opens a browser-facing listener and serves the SPA from memory. Point a browser at it and you get an interactive console for the same graph, documents, vectors, and reasoning that your applications talk to over the HTTP API.

Two hosts, one server The program-facing JSON API lives at https://<id>.oxid-db.com (API only; unknown paths return a clean JSON 404). The UI is served at https://<id>-ui.oxid-db.com (the same instance id plus -ui), which serves the SPA plus a full copy of the API, so the browser app is same-origin with everything it calls. Everything is HTTPS with no ports to configure. The UI's client-side routes all live under /app/* (for example https://85cfad134a4a-ui.oxid-db.com/app/graph), which is why they never collide with an API path such as GET /documents.
Managed while Oxid-DB is closed-source While Oxid-DB is closed-source, installation, provisioning, and the database runtime are managed for you: you receive a ready-to-use endpoint and connect with a client below. When Oxid-DB opens up, this documentation will expand with in-depth guides for self-hosting, CLI commands, and database settings (including the flag that disables the UI listener and how to change its port).
New in 0.9.7 The UI gains a geo map view at /app/geo-map, a standalone Leaflet map reached from a document whose field holds a GeoPoint. It plots a collection's points and highlights the one you opened. The first-run load-a-demo modal also gains a new installable demo, “A Reasoned Family”. See the Changelog for the full 0.9.6 → 0.9.7 difference.

Views

The app opens on the graph and switches between modes from the left sidebar. Each view is a route in the SPA under /app/*, and every action a view takes is just a call to the same HTTP API your code uses; the UI adds no private endpoints.

Graph explorer: /app/graph

The default view. Renders your ontology as an interactive graph with a hierarchical layout: pan, zoom, press f to fit, hover a node for detail, click a node to open its drawer. Click an individual to run a nearest-neighbour vector search and shade the graph by similarity. A search box (text or IRI) lists matching nodes for one-click focus, and a query run in the Query view highlights its matching nodes here.

Documents: /app/documents

A tabular browser for document collections (both ontology-mapped and standalone) with Schema, Stats, Indexes, and Bridge panels, page-by-page navigation, and per-collection NDJSON import / export. This is the fastest way to eyeball what a collection actually holds.

Query workspace: /app/query

An OxQL editor with live results, cursor-based paging, a Hydrate toggle (fetch full fields vs. just IRIs), and an Explain mode with plan / analyze switches. See it in detail below.

Predict links: /app/predict

A focused view over Knowledge-Graph Embeddings: enter a head entity, pick a relation (leave it on rdf:type to ask "what kind of thing is this?"), name a trained model, and get a ranked table of candidate links, each carrying the reasoner's ruling so impossible edges are marked, not silently suggested. Prediction never writes. Reachable by URL or from Settings.

Settings: /app/settings/*

A full-screen area with sibling pages: Data, Embeddings (plus Pipeline and Config tabs), Ontology, Security, Appearance, Danger, and Help. This is where you set the embedding provider and key, review runtime config, and manage accounts.

Login

Not a route but a full-page gate that appears in front of everything when authentication is turned on. When auth is disabled (the default), the app boots straight in and you never see it.

A shared entity drawer slides in across every mode, showing a class or individual's properties, classes, relationships, and vectors, with inline forms to add properties or wire up the document-to-ontology bridge.

Running OxQL from the browser

The Query workspace is a full OxQL scratchpad. You type a query in the editor on the left, hit Run (or the keyboard shortcut), and the results land in the pane below: the same rows your SDK would receive, because the editor posts to the very same POST /query endpoint on this port. Long result sets page with a cursor rather than loading everything at once.

What the screen looks like. Across the top of the results sits a toolbar: a Run button, stage-template pills that insert boilerplate for the next OxQL stage, an Explain checkbox (which reveals a plan vs. analyze toggle to see the query plan, optionally with real per-stage timings), and a Hydrate checkbox. With Hydrate off you get lean rows of iri (and score where the query ranks); with it on, each row is expanded with its document fields. Below the toolbar a status line reports the row count and elapsed time, then the results table, then a load-more / pagination control that walks the cursor.

oxql
FIND ?x WHERE ?x IS-A Beer LIMIT 5
Tip The Query workspace hits the identical API surface as your application code. It is the quickest way to prototype an OxQL query interactively, then paste the exact string into your app. See OxQL Overview for the language and HTTP API for the request shape.

Graph visualization

Small ontologies render every individual, exactly as you'd expect. But a large ABox (think tens of thousands of individuals) cannot be dumped into one node-and-edge graph without freezing the layout engine. So above 400 individuals the graph explorer switches to a class-first backbone: it draws the class hierarchy with a member-count badge on each class, and loads individuals only on demand.

  • Tap a class to reveal its members, up to a bounded 300 per expansion (then a re-layout). If a class has more, the UI tells you it is showing 300 of N and to narrow with search or similarity.
  • Search reveals only the (limit-bounded) matched set.
  • Similarity reveals just the top-K neighbours of the node you clicked.
  • The initial load pulls only the class backbone and counts, never the full individual list.

The mode is keyed on the server-reported total, not on how much has been fetched, so a million-individual ontology with only one page loaded is still correctly treated as class-first. The result: the browser stays responsive whether the ontology has a few hundred individuals or a million.

Note The graph's "vectors" counter and its similarity shading only see the default vector collection (its has_vector documents). Vectors stored in named collections are not surfaced in the graph view; query those through OxQL or the API.

Geo map view New in 0.9.7

When your documents carry GeoPoint fields, the UI can plot them on an interactive map. The map lives at /app/geo-map (for example https://85cfad134a4a-ui.oxid-db.com/app/geo-map). It is a standalone utility route, not a sidebar tab: you do not switch to it from the left rail. Instead you reach it in context from your data.

  • Open a document in the Documents table whose field holds a GeoPoint.
  • In the cell modal for that GeoPoint value, use the “View on map” link.
  • The map opens, plots the whole collection's points, and highlights the document you opened with a marker.

It is a Leaflet map, so it pans and zooms the way you expect. Tiles come from OpenStreetMap, with a graceful fallback if the browser is offline so the plotted points and the highlighted marker still render. Because /app/geo-map is a normal SPA route, you can also link to it directly.

Try “A Reasoned Family” The first-run load-a-demo modal ships a new installable demo, “A Reasoned Family”, that installs into an empty database. Individuals asserted only as Male/Female and Parent are realized into Father/Mother through the definitional axiom Father is equivalent to Male and Parent. It ships OpenAI 1536-dimension vectors, so you can combine the derived class with semantic search in one query.

Login & settings

Login. When the server runs with authentication on, the UI shows a full-page login gate before anything else. It adapts to the server's auth mode (advertised by a public config hint): in users mode you enter a username and password; in legacy-token mode you paste an API token. In the default disabled mode there is no login at all: the app boots straight into the graph. Once signed in, the UI attaches your bearer token to every request; a mid-session 401 drops you back to the login screen. Controls your role can't use are hidden, but that is cosmetic convenience; the server is always the real gate. See Authentication for the modes, roles, and token types.

Settings. The Embeddings screen is where you choose your embedding provider and model and enter the provider API key (for example an OpenAI key); applying it configures the running embedder that powers vector insert and search. The Config and Pipeline tabs show the live runtime configuration and derived embedding dimension as read-only previews. The Data, Ontology, Security, Appearance, and Danger pages round out account, theme, and destructive-operation controls.

Runtime vs. persisted config Config changes made from the Settings screen apply to the running process. Persisting them across a restart is part of the managed database configuration; the UI is honest about this and labels such edits as process-only.

When to use the UI vs. the API

The Web UI and the HTTP API are two doors into the same server, so the choice is about the task, not the data.

Reach for the UI when…Reach for the API / SDK when…
Exploring an unfamiliar dataset: seeing the class backbone, drilling into members, eyeballing a collection's schema.Doing anything repeatable, scripted, or in production: ingest, scheduled queries, application reads and writes.
Prototyping an OxQL query interactively before pasting it into code.Running that query from your app at scale, with cursors and error handling you control.
Sanity-checking a write, inspecting an entity, or visualizing similarity by eye.Bulk-loading documents, importing OWL/CSV, or streaming exports.
Manually training and probing link-prediction candidates with the reasoner veto.Automating training or prediction as part of a pipeline.

Both surfaces speak the exact same JSON API: nothing you can do in the browser is off-limits to your code, and vice-versa.
