Inserting & Bulk Loading

Get data into a collection: one document, many documents, or a batch of ontology facts from CSV. Pick the path that matches your payload size and shape.

Every example below targets a document collection named beers on a server at https://85cfad134a4a.oxid-db.com. A collection does not need a fixed schema to accept documents; you just POST JSON at it. If you also want a vector collection or an ontology binding, see Indexing & Schema and the Ontology Bridge. This page is only about getting bytes in.

New in 0.9.7 Documents can now carry a GeoPoint field through the ordinary insert and NDJSON import paths: set the field value to the {"$geo":{"lat": …,"lon": …}} sentinel. Coordinates are validated on ingest, so a bad pair is rejected with a clear 400. See the GeoPoint fields section below, and the Changelog for the full 0.9.6 → 0.9.7 difference.

Insert a single document

The simplest write is one JSON object POSTed to /documents/{collection} with Content-Type: application/json. The body is the document. Its keys become the document's fields. An optional top-level _iri sets the document's identity (its IRI); it is lifted out of the body before storage, so it is metadata, not a stored field. Omit it and Oxid-DB synthesises a stable id of the form {collection}#{n}.

json
{ "_iri": "Heineken", "name": "Heineken", "style": "Pilsner", "abv": 5.0 }

A successful insert returns 200 with the collection and the resolved IRI:

json
{ "ok": true, "collection": "beers", "iri": "Heineken" }
curl -s -X POST https://85cfad134a4a.oxid-db.com/documents/people \
  -H 'Content-Type: application/json' \
  -d '{"_iri":"Dave","name":"Dave","score":3}'
with OxidDB("https://85cfad134a4a.oxid-db.com") as db:
    res = db.insert_document("beers", {"name": "Heineken", "abv": 5.0}, iri="Heineken")
    # res: {"ok": true, "collection": "beers", "iri": "Heineken"}
const res = await db.insertDocument("beers", {
  _iri: "Heineken",
  name: "Heineken",
  style: "Pilsner",
  abv: 5.0,
});
console.log(res.ok, res.iri); // true "Heineken"
res, err := client.InsertDocument(ctx, "beverages", oxid.Document{
	"_iri":  "PilsnerUrquell",
	"name":  "Pilsner Urquell",
	"style": "Pilsner",
	"abv":   4.4,
})
if err != nil {
	log.Fatalf("insert document: %v", err)
}
log.Printf("ok=%v iri=%s", res.Ok, res.IRI)

        "id", "Heineken",

Identity and overwrites (upsert)

Identity is the IRI. POSTing a document whose _iri already exists overwrites the previous version, an upsert. That makes re-running a load safe: the same document lands in the same place. When you want every call to create a fresh document, omit _iri and let the server synthesise one.

Note Documents cannot carry a vector through their JSON body. Attach embeddings via a vector collection or a vector_property field mapping on the bridge. See Ontology Bridge.

Inserting a GeoPoint New in 0.9.7

A document field can hold a GeoPoint: a geographic coordinate written with the single-key $geo sentinel. Its value is an object of two numbers, and the order is always (lat, lon): latitude first, in [-90, 90] (positive north), then longitude, in [-180, 180] (positive east). It is an ordinary field, so it rides the normal insert (POST /documents/{collection}) and the NDJSON import (POST /documents/{collection}/import) unchanged.

json
{ "$id": "ams-brewery", "kind": "Brewery", "name": "Amsterdam Brewery",
  "location": { "$geo": { "lat": 52.3702, "lon": 4.8952 } } }
curl -s -X POST https://85cfad134a4a.oxid-db.com/documents/breweries \
  -H 'Content-Type: application/json' \
  -d '{"_iri":"ams-brewery","name":"Amsterdam Brewery",
       "location":{"$geo":{"lat":52.3702,"lon":4.8952}}}'
with OxidDB("https://85cfad134a4a.oxid-db.com") as db:
    res = db.insert_document("breweries", {
        "name": "Amsterdam Brewery",
        # (lat, lon): latitude first, then longitude
        "location": {"$geo": {"lat": 52.3702, "lon": 4.8952}},
    }, iri="ams-brewery")
    # res: {"ok": true, "collection": "breweries", "iri": "ams-brewery"}
const res = await db.insertDocument("breweries", {
  _iri: "ams-brewery",
  name: "Amsterdam Brewery",
  // (lat, lon): latitude first, then longitude
  location: { $geo: { lat: 52.3702, lon: 4.8952 } },
});
console.log(res.ok, res.iri); // true "ams-brewery"
Coordinates are validated on ingest A lat outside [-90, 90], a lon outside [-180, 180], or a non-finite value is rejected with 400 before the document is stored, and the error names the (lat, lon) order so a swapped pair is easy to catch. Stored GeoPoints are kept losslessly in the document bytes and the write-ahead log. GeoPoint is document-only and does not bridge into the ontology; to filter by radius or sort by distance, see Querying Documents.

Bulk loading

A loop of single inserts works, but for many documents it is slow: each request re-walks any indexes and re-checks the bridge per row. The bulk paths store every document first and defer the index work to the end of the load, so they are dramatically faster. There are two forms, distinguished by endpoint and content-type.

Form A: JSON array to /bulk

POST a JSON array of documents (or an object {"documents": [ … ]}) to /documents/{collection}/bulk with Content-Type: application/json. Each element is one document and honours _iri (or $id) exactly as a single insert does. The response reports how many were created versus overwritten, and how many indexes were rebuilt:

json
{ "ok": true, "collection": "beers", "inserted": 2, "upserts": 0,
  "indexes_built": 0, "results": [ … ], "results_truncated": false }

Form B: raw NDJSON to /import

POST newline-delimited JSON to /documents/{collection}/import. Here the body is raw text, one JSON object per line. The server reads it as a plain string, so send it as text (for example curl --data-binary), not wrapped in a JSON envelope. Per-line identity comes from $id (or _iri). This is the same format the export endpoint emits, so a round-trip is exact. The response uses imported rather than inserted:

ndjson
{"$id":"Heineken","name":"Heineken","style":"Pilsner","abv":5.0}
{"$id":"Guinness","name":"Guinness","style":"Stout","abv":4.2}
{"$id":"Chardonnay","name":"Chardonnay","style":"Wine","abv":13.0}
json
{ "ok": true, "collection": "beers", "imported": 3, "upserts": 0 }

The cURL panel below shows both forms side by side; the SDK panels show the array form first and the raw-NDJSON alternative second.

# JSON array to /bulk:

with OxidDB("https://85cfad134a4a.oxid-db.com") as db:

        {"_iri": "Heineken", "name": "Heineken", "abv": 5.0},

Why indexes_built is often 0 A fresh collection has no field indexes, so a bulk load has nothing to rebuild and queries fall back to a full scan (still correct). Once you define an index with POST /collections/{name}/indexes, later loads rebuild it and this counter reflects how many were rebuilt. See Indexing & Schema.

Importing CSV

POST /import/csv loads ontology facts (classes, individuals, axioms) rather than free-form documents. It is the fast way to seed a class hierarchy or a batch of typed individuals without building OWL. The body is the raw text of the file (the server reads it as a plain string), so send it with a text content-type such as text/csv or text/plain, not a JSON envelope. The whole import runs inside one exclusive transaction; an empty body is rejected with 400.

This is a directive format, not comma-separated columns Despite the endpoint name, the parser is whitespace-tokenised, one directive per line. It does not split on commas and there is no header row. Each line starts with a keyword: SUBCLASS a b, DISJOINT a b, EQUIVALENT a b, INSTANCE individual class, PROPERTY subject property object, or ANNOTATION subject property "value". Wrap a value containing spaces in double quotes. Lines that are blank or start with # are ignored; an unrecognised keyword is skipped with a warning (returned in warnings[]) rather than failing the whole import.

A small beverage taxonomy plus two typed individuals:

bash
# beers.txt - one directive per line, whitespace-separated
SUBCLASS Pilsner Beer
SUBCLASS Stout Beer
DISJOINT Pilsner Stout
INSTANCE Heineken Pilsner
INSTANCE Guinness Stout

The response counts what the import added and surfaces any per-line warnings:

json
{ "ok": true, "classes_added": 6, "individuals_added": 2,
  "axioms_added": 5, "warnings": [] }
curl -s -X POST https://85cfad134a4a.oxid-db.com/import/csv \
  -H 'Content-Type: text/plain; charset=utf-8' \
  --data-binary $'SUBCLASS Pilsner Beer\nINSTANCE Heineken Pilsner\n'
with OxidDB("https://85cfad134a4a.oxid-db.com") as db:
    facts = "SUBCLASS Pilsner Beer\nINSTANCE Heineken Pilsner\n"
    res = db.import_csv(facts)
    # res: {"ok": true, "classes_added": .., "individuals_added": .., ...}
const facts =
  "SUBCLASS Pilsner Beer\n" +
  "SUBCLASS Stout Beer\n" +
  "INSTANCE Guinness Stout\n";
const res = await db.importCsv(facts);
console.log(res.ok, res.classes_added, res.axioms_added);

Choosing a method

Match the tool to the payload: what shape is your data, and how much of it is there per request?

MethodEndpointContent-TypeUse it when
Single insert POST /documents/{c} application/json One document at a time: interactive writes, per-event ingest, upserting a known IRI.
Bulk array POST /documents/{c}/bulk application/json A batch you already hold in memory as objects. Deferred indexing makes it far faster than a loop. Best when the whole batch comfortably fits one request body.
NDJSON import POST /documents/{c}/import text (plain body) A line-delimited file or stream you can send as raw bytes. Same fast path as the array form, and it round-trips with /export.
CSV / directive import POST /import/csv text (plain body) Seeding ontology facts (classes, subclass axioms, disjointness, typed individuals), not free-form documents.

Body-size limit

Every request body is capped by [server.limits].max_body_mb, which defaults to 32 MiB in 0.9.7. A body over the cap is rejected with 413 before the handler even runs, carrying the code PAYLOAD_TOO_LARGE. To load a dataset larger than the cap, split it into several bulk/NDJSON requests. (The limit is a managed server setting, see Operations; it is not something you change from a client.)

Size is not the only guard Even a body under the cap can be refused if the server is out of memory headroom: admission control returns 507 (RESOURCE_EXHAUSTED) at the hard watermark and the server stays live and queryable rather than risking an OOM. Large loads are governed on their real footprint, not just their byte length.

Idempotency & errors

The autocommit write paths on this page (single insert, /bulk, /import, and /import/csv) apply immediately and return 200 on success. There is no committed flag to branch on here: unlike the gated ontology actions under /actions/* (which run the EL⊥ consistency gate before committing), document writes are not consistency-gated, so a 200 means the write landed. Re-running an insert or bulk load with the same _iri/$id values is safe by design. Matching IRIs are overwritten (counted under upserts), not duplicated. For transactional, all-or-nothing multi-step writes, use a transaction (POST /txn … /commit) instead.

Errors share one JSON envelope across the whole API, a machine-readable code plus a human error message:

json
{ "code": "BAD_REQUEST", "error": "empty import body" }
StatuscodeTypical cause
400BAD_REQUESTEmpty import body, malformed JSON, or a field the endpoint refuses.
404NOT_FOUNDUnknown collection or IRI (for path-addressed reads/deletes).
413PAYLOAD_TOO_LARGERequest body exceeds [server.limits].max_body_mb.
507RESOURCE_EXHAUSTEDMemory admission refused the write at the hard watermark.
