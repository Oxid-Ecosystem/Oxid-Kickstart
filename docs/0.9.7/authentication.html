Authentication

Accounts, roles, sessions, and API keys: off by default, on when you need it.

Managed while Oxid-DB is closed-source While Oxid-DB is closed-source, installation, provisioning, and the database runtime are managed for you. Turning auth on, bootstrapping the first admin, and TLS certificates are handled at the deployment layer (see Install, CLI & Settings). This page covers the developer-facing side: how you authenticate a client once auth is enabled.

When you need auth

Authentication is disabled by default. On a fresh instance every route is open (no header, no token, no login), so you can run the whole Quick Start against your endpoint (for example https://85cfad134a4a.oxid-db.com) without a single credential.

You turn auth on when the instance stops being just yours: the moment you expose the server beyond loopback, or share it with other people or services. At that point you want two things together: authentication (who is calling) and transport security (TLS, so credentials don't cross the wire in cleartext). They are separate switches; enable both before you go off-loopback.

Check the current mode without logging in GET /auth/config is public and reports which mode the server is in (disabled, legacy, or users). Clients, including the Web UI, read it to decide whether to prompt for a login at all.
bash
curl -s https://85cfad134a4a.oxid-db.com/auth/config
# {"mode":"disabled"}

Accounts, roles & sessions

When auth is enabled in full multi-user (users) mode, Oxid-DB gives you real accounts backed by a small set of durable primitives:

  • Users: named accounts, each with exactly one role. Credentials live in a separate CRC-framed file (users.oxa, magic OXDU), distinct from the database checkpoint.
  • Roles (RBAC): a fixed permission is required for every route; requests without it are refused. Custom roles are allowed alongside the built-ins.
  • Sessions: opaque bearer tokens prefixed oxs_, obtained by logging in, with a default hard TTL of 12 hours (no sliding renewal, so log in again when one expires).
  • API keys: long-lived bearer tokens prefixed oxk_, tied to a user, for services and scripts.
  • Audit log: a bounded, append-only ring (default 10,000 entries) recording logins, key and user changes, and permission denials.

Passwords are hashed with Argon2id (OWASP-2024 profile: m=19456 KiB, t=2, p=1), and only on login or password-set, never on the per-request path. Session and API-key tokens are 32 bytes of OS randomness stored as SHA-256 hashes and compared in constant time; a slow hash isn't needed for high-entropy random tokens. Plaintext leaves the process exactly once: in the response that mints it.

Built-in roles

The four built-in roles form a strict chain, where each one includes everything the role below it can do: reader ⊂ writer ⊂ schema ⊂ admin.

RoleIntended forCan do
readerAnalyst, dashboardRead schema and individuals, list collections, run queries, read snapshots and export.
writerApplication service accountEverything reader can, plus insert / update / delete individuals, assert properties, write documents, classify, and use transactions.
schemaOntology engineer, data stewardEverything writer can, plus manage the ontology, collections, indexes and mappings, import data, configure the embedder, and train KGE models.
adminOperator, superuserEverything schema can, plus manage users, back up, reset the database, apply runtime config, and read the audit log. Backup, ResetDatabase, user management and config-apply are admin-only.

The server is the enforcement point: every route maps to a required permission and unmapped routes fail closed. Clients (like the Web UI) hide controls a role lacks, but that is cosmetic; the authorization decision is always made server-side.

Logging in / getting a token

To act as a user, exchange a username and password for a session token at POST /auth/login, then send that token on every subsequent request in the Authorization: Bearer header. There is no X-Api-Key header; sessions and API keys both travel as bearer tokens.

bash
curl -s -X POST https://85cfad134a4a.oxid-db.com/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"hunter2hunter2"}'

# → {"token":"oxs_…","expires_at":1750000000,
#    "user":{"id":1,"username":"admin","role":"admin"}}

Take the token from that response and present it as a bearer token. The scheme keyword is case-insensitive (Bearer / bearer).

bash
curl -s https://85cfad134a4a.oxid-db.com/auth/me \
  -H 'Authorization: Bearer oxs_…'

# → {"id":1,"username":"admin","role":"admin","permissions":[ … ]}

The same header protects every other endpoint. A query, for example:

bash
curl -s -X POST https://85cfad134a4a.oxid-db.com/query \
  -H 'Authorization: Bearer oxs_…' \
  -H 'Content-Type: application/json' \
  -d '{"query":"FIND ?x WHERE ?x IS-A Beer LIMIT 5"}'
Session lifecycle A missing or invalid token returns 401; a valid token whose role lacks the required permission returns 403. Use GET /auth/sessions to list your live sessions, DELETE /auth/sessions/{id} to revoke one, and POST /auth/logout to burn the session you're currently using.

API keys

Sessions are short-lived and meant for humans. For long-running scripts and services, mint an API key instead: a bearer token (prefixed oxk_) tied to a user and carrying that user's role. Create one over HTTP with POST /auth/api-keys:

bash
curl -s -X POST https://85cfad134a4a.oxid-db.com/auth/api-keys \
  -H 'Authorization: Bearer oxs_…' \
  -H 'Content-Type: application/json' \
  -d '{"label":"ETL pipeline","expires_at":1790000000}'

# → 201 {"token":"oxk_…","key":{"id":3,"label":"ETL pipeline", … }}

Then use the oxk_ token exactly like a session token, with the same Authorization: Bearer header:

bash
curl -s -X POST https://85cfad134a4a.oxid-db.com/query \
  -H 'Authorization: Bearer oxk_…' \
  -H 'Content-Type: application/json' \
  -d '{"query":"FIND ?x WHERE ?x IS-A Beer LIMIT 5"}'

The plaintext oxk_ token is shown once, at creation; only its SHA-256 hash is stored. If you lose it, revoke it (DELETE /auth/api-keys/{id}) and mint a new one. List your keys with GET /auth/api-keys; an admin may pass ?user=ID to list, or a "user":ID field in the POST body to mint, on behalf of another user.

Transport security (TLS)

TLS is implemented, and enforced when you leave loopback Oxid-DB ships real, in-process TLS via rustls (TLS 1.2+, no OpenSSL, HSTS when on), configured with [server].tls. A non-loopback bind without TLS is a hard startup refusal unless the operator explicitly opts in with [server].allow_insecure = true / --insecure. With TLS configured, non-loopback binds are allowed. (This corrects the older "loopback-only until TLS" framing: TLS exists today; the constraint is that the server refuses to be exposed insecurely rather than that it cannot be exposed.)

The practical rule: authentication only protects you if the credentials don't leak in transit. Over plain HTTP, bearer tokens and passwords cross the wire in cleartext: fine on loopback, unsafe anywhere else. So the two go together: enable auth and TLS before binding to a public address. mTLS / client certificates are noted as a future option, not implemented in this release.

Audit log

Every security-relevant action is recorded in a bounded, append-only ring (default capacity 10,000 entries), readable by admins at GET /auth/audit. Recorded actions include LoginSuccess / LoginFailure, Logout, PasswordChange, UserCreate / Update / Disable, ApiKeyCreate / Revoke, and PermissionDenied. Only hashes are ever persisted; the log never stores a plaintext token or password.

bash
curl -s 'https://85cfad134a4a.oxid-db.com/auth/audit?limit=50' \
  -H 'Authorization: Bearer oxs_…'

Note on SDKs

The official SDKs are transport clients for the data plane: queries, documents, vectors, transactions. The /auth/* administration API (login, users, keys, audit) is currently out of SDK scope. That is why every example on this page uses curl: call the auth endpoints over HTTP directly.

What the SDKs do handle is carrying a token you already have. Because auth is a standard Authorization: Bearer header, you can attach it through each client's request-headers option (or by setting the header on the underlying HTTP client): the same token you obtained from /auth/login or minted as an API key.
