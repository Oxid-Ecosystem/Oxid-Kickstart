Storage & Durability

How Oxid-DB persists your data, keeps it crash-safe, and serves datasets that are larger than the memory of the machine running it.

New in 0.9.7 Version 0.9.7 bumps the on-disk format version to 12, which adds two things to the persisted state: GeoPoint document values and persisted spatial-index (grid) definitions over a GeoPoint field. Older files migrate forward when opened. See the Changelog for the full 0.9.6 → 0.9.7 difference.
Managed while Oxid-DB is closed-source This page explains the storage engine conceptually so you can reason about what your data guarantees are. While Oxid-DB is closed-source, backups, checkpoint and compaction scheduling, and version upgrades are operated for you. There is nothing here you need to configure to build an application. See Install, CLI & Settings for the managed operational surface.

The storage model

Under the hood, everything in Oxid-DB shares one integer identity space: an IRI, a vector, a document, and a link-prediction entity that all denote the same real-world thing are literally the same 32-bit ID. That is what lets the engine keep ontology facts, vectors, and JSON documents in one place and persist them together. When the database is written to disk, these regions are serialized side by side:

On-disk regionWhat it holds
Term dictionaryThe bidirectional map between every string name (IRIs, blank nodes, literals) and its interned integer ID. Every other region references terms by that ID, never by string.
Ontology (TBox / ABox / RBox)Class axioms (subclass, equivalence, disjointness), individual-to-class and property assertions, and single-property role-hierarchy axioms, the schema and the facts. See Ontologies.
VectorsThe embedding per entity and the collection's dimensionality and metric. Compressed SQ8 codes are held resident; the exact f32 copies live on disk (see Off-RAM residency).
DocumentsCollections and their JSON documents (including any GeoPoint field values), plus the definitions of secondary, compound, and spatial (grid) indexes. The index structures themselves are rebuilt from the data on load. See Documents.
Ontology bridgeCollection→class mappings and per-collection auto-embed configuration, re-registered into the live bridge on open. See The Ontology Bridge.
Classification cacheThe reasoner's precomputed subsumption closure and class extents, stored as sorted integer lists so the database does not have to re-classify from scratch on every open. Invalidated automatically when axioms or individuals change.

The on-disk layout carries a format version so the engine always knows how to read a file it is handed. Oxid-DB 0.9.7 writes format version 12 (OXDB_VERSION). Version 12 adds two things to the persisted state: GeoPoint document values and persisted spatial-index (grid) definitions. Older files are migrated forward through the versioned state chain when they are opened: a v11 file upgrades cleanly with an empty set of spatial-index definitions. An older (pre-12) binary handed a newer v12 file refuses it loudly rather than misreading it. The format is checked, not guessed.

Rebuilt, not stored Index definitions are persisted, but the HNSW vector graph, the BTree secondary indexes, and the spatial (grid) index are rebuilt from the underlying vectors and documents when the database opens. Persisting the recipe rather than the derived structure keeps files smaller and lets the format evolve the index internals without a migration.

GeoPoint values on disk

A document field can hold a GeoPoint, written with the sentinel {"$geo": {"lat": <number>, "lon": <number>}} and ordered (lat, lon). These values are stored losslessly in the binary document format and in the write-ahead log, and are rebuilt into the live document store on checkpoint, exactly like any other field. GeoPoint is a document-store type: it does not bridge into the ontology. An opt-in spatial (grid) index can be defined over a GeoPoint field; its definition persists in format version 12 and the index rebuilds on load. Queries such as WITHIN and SORT DISTANCE work without it (they fall back to a full scan), so the index only ever makes a query faster, never changes the answer.

Durability: WAL + snapshots

Oxid-DB is durable through a write-ahead log (WAL) plus periodic checkpoints, the same discipline used by production relational databases. Every mutation is first appended to an append-only log and flushed to disk (fsync) before the change is acknowledged. Because the intent is on stable storage first, a crash at any moment either leaves a record that recovery can safely redo, or leaves nothing applied at all.

Periodically the engine folds the log into a checkpoint (a compact snapshot of the whole database) and truncates the log. A checkpoint is not a raw memory dump: it is a CRC-framed envelope (a magic tag, a format version, a checksum, and the payload length), written to a temporary file, fsync'd, then atomically renamed over the target. On POSIX systems that rename is atomic, so an interrupted checkpoint leaves the previous good file untouched: you always open either the old state or the fully-written new one, never a half-written file.

What a commit guarantees

Under the default sync policy, a transaction's durability point is its commit: the commit's single fsync flushes every record the transaction wrote (rather than paying one flush per record), so once a write is acknowledged it will survive an abrupt process kill. There is also an optional group-commit policy that batches several transactions' flushes into one for higher throughput, trading a small, bounded window of the most recent commits on sudden power loss, a deliberate throughput/durability knob, managed for you.

Crash recovery

On open, the engine loads the last checkpoint (or starts empty), then replays the log: committed transactions are redone, a torn tail from a crash mid-write is truncated back to the last clean record boundary, and in-flight transactions that never committed are discarded. Corruption is never loaded silently: a flipped or truncated byte in the checkpoint or the log is caught by the magic tag, version check, and CRC-32 checksum, and the open is refused loudly rather than deserialized into a plausible-but-wrong database. This behavior is not merely asserted: a crash-injection test harness deliberately kills the process mid-write and mangles on-disk bytes at every fault boundary, then reopens and checks the database equals exactly what was committed.

The honest boundary A process kill proves that fsync-acknowledged data survives; it does not simulate media-level power loss of writes the OS has buffered but not yet flushed (the page cache outlives a killed process). Faithful power-loss testing needs filesystem-level fault injection and is a planned extension, so the accurate claim is ack ⇒ durable, not "no write is ever lost under any hardware failure."

MVCC snapshots

Reads in Oxid-DB see a consistent snapshot of the database, not a half-applied mixture of in-flight writes. The engine assigns a monotonic commit timestamp to every committed transaction and keeps version chains, so a query reads a coherent point-in-time view and does not block concurrent writers. This is standard multi-version concurrency control (MVCC): readers and writers do not fight over the same lock.

The commit timestamps also power time-travel reads. An OxQL query can add AS OF <commit_ts> to read the ontology as it stood at a past commit, and the same time-travel is exposed over HTTP at GET /snapshot. The commit clock is re-seeded from the log on recovery, so committed versions (and the ability to read them AS OF) survive restarts. How this interacts with the transaction lifecycle (isolation, commit, rollback) is covered in Transactions.

oxql
-- Read the ontology as it stood at commit 42
FIND ?x WHERE ?x IS-A Beer AS OF 42

crates/oxd-query/src/oxql.pest: AS OF takes an integer commit timestamp; wall-clock date strings are not yet accepted.

Off-RAM residency

Oxid-DB can serve a dataset that is larger than the memory of the machine it runs on. The mechanism is a split between a hot, resident index and cold, on-disk exact data. For vectors, the live search graph holds compact SQ8 codes (one byte per dimension) in memory, while the exact f32 vectors are spilled to a read-only, memory-mapped base on disk. The only resident cost of that base is a small offset table (eight bytes per vector); the exact vectors themselves page in from disk on demand, for example when a candidate is re-ranked for precision. This "cold-f32 / mmap" path is on by default in the shipped binary. See Vector Search for the search and recall detail.

The effect is a much higher capacity ceiling than a fully RAM-resident store. As a measured, honest data point: 10 million vectors at 1,536 dimensions (real OpenAI embeddings) run with only about 23 to 26 GiB resident while roughly 61 GB of exact f32 data stays on disk: the machine never has to hold the full vector set in memory at once.

Off-RAM is for the exact vectors The WAL and checkpoints provide durability and crash recovery, not paging. The off-RAM tier is specifically the memory-mapped exact-f32 vector base described above; the resident SQ8 graph, the ontology, and the term dictionary still live in memory. At 10M/1536-d, recall is not claimed (an exact ground truth won't fit); at 1M/1536-d the same path measures recall@10 ≈ 0.98.

Compaction

Over time, checkpoints and their incremental deltas accumulate, and the on-disk document store retains space from churned and deleted records. Compaction folds the accumulated state back into a fresh, minimal on-disk form and reclaims that space, keeping both load time and disk footprint bounded. It reuses the same crash-safe write path as a normal checkpoint, so it is safe by construction: an interrupted compaction leaves the previous good files in place.

You do not schedule or run this yourself. While Oxid-DB is closed-source, compaction is managed for you. It runs automatically as the delta chain or reclaimable space crosses a threshold. The operational surface is described in Install, CLI & Settings.

What's managed for you

Operated for you while closed-source The durability machinery on this page runs without any action from you. Backups and point-in-time recovery, checkpoint and compaction scheduling, and format-version upgrades (migrating older on-disk data forward to version 12) are all operated by the managed deployment. You connect to a ready endpoint with a client SDK and build; when Oxid-DB opens up, this page will expand with the operator-facing runbooks for running these yourself.
