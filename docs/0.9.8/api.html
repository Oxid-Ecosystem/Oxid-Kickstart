HTTP API

Every Oxid-DB endpoint is plain JSON over HTTP. The SDKs on the next page are thin wrappers over exactly these routes, so anything you can do from a client, you can do with curl.

New in 0.9.8 0.9.8 is a hardening release; the wire grows a few fields and codes rather than new routes. POST /insert/batch honours a per-entity collection and validates every vector-bearing entity up front (a dimension mismatch now 400s the whole batch naming the entity). GET /ready and GET /admin/memory gain an admission_driver field ("estimate" or "rss") that says which figure is gating writes. Changing the embedder to a different model over existing vectors is refused with 409 EMBEDDER_MODEL_MISMATCH (PUT /config/embedder; reported as applied:false on /config/apply). With the opt-in [wal].on_fsync_error = "poison" policy, writes after a failed WAL fsync return 503 UNAVAILABLE while reads keep serving. GET /demos lists a third bundled demo, tech-concepts. Through /query, OxQL accepts angle-bracketed verbatim IRIs in IS-A and resolves a bare NEAR to the sole collection. See the Changelog for the full 0.9.7 → 0.9.8 difference.

Conventions

The server speaks one protocol: JSON request bodies, JSON responses, over HTTP. There is no binary wire format and no separate admin protocol. Everything below is reachable with any HTTP client.

Base URL
The JSON API is served at https://<id>.oxid-db.com, where <id> is your 12-character instance id (for example https://85cfad134a4a.oxid-db.com). Every path in this reference is relative to that base.
Content type
Send Content-Type: application/json on every request with a body, except the raw-import endpoints (/import/csv, /import/owl, /documents/{collection}/import), which take a raw text or byte body.
API vs. Web UI
The API host https://<id>.oxid-db.com is API-only. The web UI is served at https://<id>-ui.oxid-db.com (same id plus -ui): it hosts the same full API plus the browser app, whose client routes live under /app/*. Both hosts carry the entire JSON API over HTTPS with no ports to configure; the only difference is the UI host adds the single-page-app fallback for unmatched paths. See the Web UI page.
Auth header
Authentication is disabled by default: on loopback no header is needed. When it is turned on, every request carries Authorization: Bearer <token> (there is no X-Api-Key header). See Authentication to lock the API down before exposing it.
Note Both listeners are held to the same TLS/exposure gate: a non-loopback bind without TLS is refused at startup unless you explicitly opt in. Installation, provisioning, and low-level tuning are covered in Install, CLI & Settings.

Request & response shapes

The wire uses a small, stable vocabulary of field names. Learn these five and most of the API reads the same way. The names below are copied verbatim from the server's handler structs, and there are a couple of traps where the wire name differs from what you might guess.

FieldWhereWhat it is
iriindividual / result identityThe entity's IRI (a string). This is the canonical identity field, not id. On /insert the legacy alias individual also deserializes, but wire clients should send iri.
class / classesmembershipClass membership on an individual: class (a single string) or classes (an array). Set one, not both. Not type.
vectorindividual embeddingA raw array of floats (e.g. [0.6, 0.3, 0.1, 0.6]). Not embedding. Dimensions must match the target collection.
queryPOST /queryThe OxQL text to run, as a string. Not oxql.
results[]query / similarity responseAn array of rows. Each row is {"iri": "..."}, gaining an optional score (float, for NEAR/hybrid rows) and an optional fields object (when the query uses PROJECT).
Wire traps Two field names are commonly guessed wrong. When creating a collection the field is dimensions, not dim. When predicting links the field is top_k, not k. A stray k is silently ignored (unknown fields are dropped) and the server falls back to its configured default.

Error envelope

Errors come back with a non-2xx status code and a two-field JSON body: a machine-readable code and a human-readable error message.

json
// 400 - bad OxQL
{ "code": "QUERY_ERROR", "error": "unexpected token near 'WERE'" }

// 400 - malformed request
{ "code": "BAD_REQUEST", "error": "..." }

// 404 - unknown resource or settled transaction id
{ "code": "NOT_FOUND", "error": "..." }

// 409 - a collection was already mapped to a different class
{ "code": "COLLECTION_ALREADY_MAPPED_DIFFERENT", "error": "..." }

// 409 - switching the embedder to a different model over existing vectors (0.9.8)
{ "code": "EMBEDDER_MODEL_MISMATCH", "error": "this database already holds vectors produced by embedding model \"openai:text-embedding-3-small\"; switching to \"fastembed:BAAI/bge-small-en-v1.5\" would silently mix two embedding spaces ..." }

// 503 - writes refused after a WAL fsync failure (opt-in poison policy, 0.9.8)
{ "code": "UNAVAILABLE", "error": "WAL durability is poisoned by a prior fsync failure, writes refused; restart the server to recover from the last durable record" }

Common status codes: 200 success, 400 bad request / query error, 404 not found, 409 conflict (e.g. re-creating a collection with a different shape, or since 0.9.8 switching the embedder model over a non-empty database), 503 unavailable (draining, known-inconsistent, or since 0.9.8 a write after durability was poisoned by a failed WAL fsync under the opt-in poison policy; reads still serve and a restart recovers). When auth is on you may also see 401 (unauthenticated), 403 (role lacks the permission), and 429 (rate-limited).

Core operations

The examples below are the operations you reach for day to day, each shown across every SDK that implements it. All of them run against the beverage ontology used throughout these docs (Beer, Pilsner, Stout, Wine) with 4-dimensional toy vectors, so they are copy-runnable against a fresh server.

Health & readiness

GET /health is a liveness ping that never touches the database. GET /ready is the deeper check: it reports classification state, memory, and per-collection counts, and returns 503 only while draining or when the ontology is known-inconsistent (an empty or unclassified database is still 200 ready).

The checks.memory object carries the memory governor's view of the process. Since 0.9.8 it also names the figure that is gating writes: New in 0.9.8

json
// GET /ready (excerpt)
{
  "status": "ready",
  "checks": {
    "database_loaded": true,
    "classification_current": true,
    "consistent": true,
    "classes": 4, "individuals": 3,
    "collections": { "default": { "vectors": 3, "dimension": 4 } },
    "memory": {
      "estimated_bytes": 18350080,
      "rss_bytes": 91234304,
      "budget_bytes": 1073741824,
      "admission_state": "ok",
      "admission_driver": "estimate"
    }
  },
  "uptime_seconds": 412,
  "version": "0.9.8"
}

admission_state is "ok", "soft" (bulk writes refused with 507, single writes continue) or "hard" (all writes refused with 507; reads, queries and deletes continue). admission_driver tells you what to do about it: "estimate" means the logical live-data estimate is the gating figure, so deleting data recovers headroom; "rss" means the real process RSS is the gating figure (allocator retention or an undersized container), so deleting data will not help and the fix is a larger memory budget or a restart. The 507 error message names the same driver, so a client can act on either. crates/oxd-server/src/memory.rs

Ontology writes

POST /subclass asserts a subclass axiom (sub is the child, sup the parent) and returns {"ok": true}. (The sibling POST /disjoint takes fields a/b; DELETE /subclass retracts.)

curl -s -X POST https://85cfad134a4a.oxid-db.com/subclass \
  -H 'Content-Type: application/json' \
  -d '{"sub":"Pilsner","sup":"Beer"}'
with OxidDB("https://85cfad134a4a.oxid-db.com") as db:
    db.add_subclass("Pilsner", "Beer")
    db.add_subclass("Stout", "Beer")
// Pilsner ⊑ Beer, Stout ⊑ Beer  (sub is the child, sup the parent)
await db.addSubclass({ sub: "Pilsner", sup: "Beer" });
await db.addSubclass({ sub: "Stout", sup: "Beer" });
for _, sc := range []oxid.SubclassRequest{
	{Sub: "Pilsner", Sup: "Beer"},
	{Sub: "Stout", Sup: "Beer"},
} {
	if err := client.AddSubclass(ctx, sc); err != nil {
		log.Fatalf("subclass %s ⊑ %s: %v", sc.Sub, sc.Sup, err)
	}
}
// Pilsner ⊑ Beer  (sub, sup)
oxid.addSubclass(new Mutation.SubclassRequest("Pilsner", "Beer"));
oxid.addSubclass(new Mutation.SubclassRequest("Stout", "Beer"));
use OxidDb\Client\Model\SubclassRequest;

$oxid->addSubclass(new SubclassRequest('Beer', 'Beverage'));    // Beer ⊑ Beverage

// Pilsner ⊑ Beer, Stout ⊑ Beer
await oxid.AddSubclassAsync(new SubclassRequest("Pilsner", "Beer"));
await oxid.AddSubclassAsync(new SubclassRequest("Stout", "Beer"));

POST /insert/batch writes many individuals in one request, best-effort: the body is {"entities": [...], "collection"?: "..."} where each entity has the same iri / class (or classes) / text? / vector? shape as /insert. Since 0.9.8 an entity may also carry its own collection New in 0.9.8, so one batch can target several vector collections. The effective collection of each entity is resolved as entity.collection → batch-level collection → the database default (before 0.9.8 the per-entity key was silently dropped and every vector fell back to the batch-level or default collection).

Validation is up front and covers every vector-bearing entity against its own target (0.9.7 checked only the first vector). A dimension mismatch, or an entity with no collection anywhere while the default collection does not exist yet, rejects the whole batch with a 400 that names the offending entity, so nothing is partially committed. An entity that names a collection which turns out to be missing is not a validation error: it lands on the per-row path and comes back as an errors[] entry in a 200 whose ok is false. The response is {"ok": bool, "inserted": n, "errors": [...], "results": [...], "results_truncated": bool}. crates/oxd-server/src/lib.rs

Per-entity collection and the typed SDKs The per-entity key is a wire-level field. Python's insert_batch takes plain dicts, so it passes through unchanged; the Node, Web, Go, Java, PHP and C# batch-entity types at 0.9.8 declare only iri / class / text / vector, so from those clients use the batch-level collection (one batch per collection) or call the route with a raw HTTP client until the typed shapes catch up.

POST /query runs one page of OxQL. The OxQL text goes in the query field; rows come back under results with a total_count for the page and an opaque next_cursor for resuming. Two 0.9.8 additions are reachable here with no wire change: a class IRI that is not a bare token (hyphens, ~, %) can be written verbatim in angle brackets, ?x IS-A <http://data.europa.eu/esco/occupation/0e2d-24d0-4b73>, and a bare NEAR ?x TO ... with no .collection and no default collection now searches the sole collection when exactly one exists (with an actionable 400 naming the candidates when there are several). POST /explain reports the same resolution. Both are detailed on the OxQL page.

curl -s -X POST https://85cfad134a4a.oxid-db.com/query \
  -H 'Content-Type: application/json' \

Note total_count is the number of rows in this page, not the full match count. To page deeply, keep the same query and increment OFFSET by LIMIT until results is empty, the always-correct paginator. The next_cursor resume works but is not fully supported over deep SORT/NEAR result sets.
A too-large LIMIT is a 400, not "0 results" An explicit LIMIT above [server.limits] max_query_rows (default 100000) is rejected with HTTP 400 and a {"code":"BAD_REQUEST","error":"..."} body. It does not return an empty results array. A client that reads results while ignoring the status code sees the rejection as "no matches" when the query was never run. Always check the status and surface the error field (every official SDK raises a typed error that carries it). To pull an extent larger than the cap, page with OFFSET/next_cursor, or raise max_query_rows (set it to 0 to disable the cap). See LIMIT & pagination for the paging mechanisms and the cap.

Collections & documents

Console.WriteLine($"inserted {res.Iri} into {res.Collection} (ok={res.Ok})");

Ontology import

POST /import/owl takes a raw ontology body (not JSON) and folds its classes, individuals, and axioms into the database. As of 0.9.7 it accepts more than OWL/XML: OWL Functional Syntax (.ofn), OBO 1.4 (.obo), OWL Manchester Syntax (.omn), RDF Turtle (.ttl), and N-Triples (.nt), alongside OWL/XML (.owl / .owx / .xml). The format is detected by extension and then by a content sniff; you can force it with a ?format= query parameter whose values are owx (aliases owl, xml), ofn, obo, omn, ttl, and nt. An unknown ?format= returns 400 listing the accepted values. RDF/XML is deliberately not supported. The response shape is unchanged: {"ok":true,"classes_added":N,"individuals_added":N,"axioms_added":N,"warnings":[...]}.

# Turtle, format forced via ?format=ttl
curl -s -X POST 'https://85cfad134a4a.oxid-db.com/import/owl?format=ttl' \
  -H 'Content-Type: text/turtle' \
  --data-binary @beverages.ttl
# => {"ok":true,"classes_added":4,"individuals_added":0,"axioms_added":3,"warnings":[]}
with OxidDB("https://85cfad134a4a.oxid-db.com") as db:
    with open("beverages.ofn") as f:
        res = db.import_owl(f.read(), fmt="ofn")   # OWL Functional Syntax
    print(res["classes_added"], res["axioms_added"])
// Detected by content sniff, or force with { format: "obo" | "omn" | "ttl" | "nt" | "ofn" | "owx" }
const res = await db.importOwl(oboText, { format: "obo" });
console.log(res.classes_added, res.individuals_added, res.axioms_added);

Reasoner role hierarchy (add-axiom)

POST /actions/add-axiom is the governed axiom-write route. Besides the subclass, disjoint, and equivalent kinds, 0.9.7 adds subproperty: a length-1 role hierarchy in which sub is subsumed by sup. Like every other kind it commits only if the staged ontology stays coherent, otherwise it returns the EL⊥ verdict without mutating. Role chains are not authorable through this action; author those via file import. A stored length-1 role hierarchy is reported as in-fragment and reasoned by GET /reasoner/fragment.

curl -s -X POST https://85cfad134a4a.oxid-db.com/actions/add-axiom \
  -H 'Content-Type: application/json' \
  -d '{"kind":"subproperty","sub":"https://ex.org/prop/brewedBy","sup":"https://ex.org/prop/producedBy"}'
# commits only if the ontology stays coherent; otherwise {"committed": false, ...}
with OxidDB("https://85cfad134a4a.oxid-db.com") as db:
    res = db.add_axiom(kind="subproperty",
                       sub="https://ex.org/prop/brewedBy",
                       sup="https://ex.org/prop/producedBy")
    print(res["committed"])   # False on an EL-bottom veto
// AxiomKind now includes "subproperty" (role hierarchy: sub is subsumed by sup).
const res = await db.addAxiom({
  kind: "subproperty",
  sub: "https://ex.org/prop/brewedBy",
  sup: "https://ex.org/prop/producedBy",
});
console.log(res.committed);

Geospatial search

POST /collections/{name}/geo-search finds the individuals whose GeoPoint field lies within a radius of a point. A GeoPoint is stored on a document with the JSON sentinel {"$geo": {"lat": <number>, "lon": <number>}} (latitude in [-90, 90], longitude in [-180, 180], order always (lat, lon)); a bad coordinate is a hard 400. The request takes field, lat, lon, and radius_m (all required), plus optional nearest (order nearest-first and cap to that many hits) and class (an IS-A pre-filter, which needs an ontology-mapped collection). Bad coordinates or a negative radius return 400. The route builds the same query AST as the OxQL WITHIN / SORT DISTANCE form, so the semantics are identical; every hit carries a distance_m.

curl -s -X POST https://85cfad134a4a.oxid-db.com/collections/breweries/geo-search \
  -H 'Content-Type: application/json' \
  -d '{"field":"location","lat":52.3702,"lon":4.8952,"radius_m":5000.0,"nearest":5,"class":"Brewery"}'
# => {"hits":[{"iri":"...","distance_m":0.0,"location":{"lat":52.3702,"lon":4.8952}}],"count":2}
with OxidDB("https://85cfad134a4a.oxid-db.com") as db:
    res = db.geo_search("breweries", {
        "field": "location",
        "lat": 52.3702,
        "lon": 4.8952,
        "radius_m": 5000.0,
        "nearest": 5,
        "class": "Brewery",
    })
    for hit in res["hits"]:
        print(hit["iri"], hit["distance_m"])
// GeoSearchRequest: { field, lat, lon, radius_m, nearest?, class? }
const res = await db.geoSearch("breweries", {
  field: "location",
  lat: 52.3702,
  lon: 4.8952,
  radius_m: 5000.0,
  nearest: 5,
  class: "Brewery",
});
console.log(res.count, res.hits.map((h) => `${h.iri} @ ${h.distance_m}m`));
Note The same search is expressible in OxQL: ?x.field WITHIN <d>{km|mi|m} OF (lat, lon) filters to a radius, and SORT DISTANCE(?x.field, (lat, lon)) [ASC|DESC] orders by proximity. Geo results carry distance_m either way.

Transactions

Single mutations auto-commit. For multi-statement atomicity, POST /txn to begin (capture the returned txn_id), run mutations against /txn/{id}/…, then POST /txn/{id}/commit or /rollback. Every SDK wraps this in a scope helper that commits on clean exit and rolls back on error. The deep dive lives on the Transactions page.

# 1. Begin - capture txn_id from the response.
curl -s -X POST https://85cfad134a4a.oxid-db.com/txn
# => {"txn_id": 1}

# 2. Mutate inside the txn (interpolate the id).
curl -s -X POST https://85cfad134a4a.oxid-db.com/txn/1/insert \
  -H 'Content-Type: application/json' \
  -d '{"iri":"Heineken","class":"Pilsner","vector":[0.4,0.2,0.1,0.4]}'

# 3. Commit.
curl -s -X POST https://85cfad134a4a.oxid-db.com/txn/1/commit
with OxidDB("https://85cfad134a4a.oxid-db.com") as db:
    with db.transaction() as txn:
        term = txn.insert("Heineken", "Pilsner", vector=[0.4, 0.2, 0.1, 0.4])
        txn.add_subclass("Pilsner", "Beer")
        sp = txn.savepoint()
        txn.insert_document("beers", {"name": "Heineken"})
        txn.rollback_to(sp)     # undo just the document
    # committed here on clean exit
// Auto commit/rollback.
await db.transaction(async (txn) => {
  await txn.addSubclass({ sub: "Pilsner", sup: "Beer" });
  const term = await txn.insert({ iri: "Corona", class: "Pilsner", vector: [0.2, 0.2, 0.1, 0.3] });
  await txn.addObjectProperty({ subject: "Corona", property: "brewedBy", object: "GrupoModelo" });
  return term; // resolve → commit; throw → rollback
});
err := client.Transaction(ctx, func(tx *oxid.Txn) error {
	// tx.Insert returns the interned Term (int); iri must be new.
	if _, err := tx.Insert(ctx, oxid.TxnInsertRequest{
		IRI:    "PortSaintNick",
		Class:  "Stout",
		Vector: []float64{0.8, 0.2, 0.1, 0.9},
	}); err != nil {
		return err // triggers rollback
	}
	return tx.AddSubclass(ctx, oxid.SubclassRequest{Sub: "Stout", Sup: "Beer"})
})
if err != nil {
	log.Fatalf("transaction rolled back: %v", err)
}
log.Println("transaction committed")
// Closure form - commits on return, rolls back on throw.
oxid.transaction(tx -> {
    tx.insert(Txn.TxnInsertRequest.of("Duvel", "Beer"));   // returns interned Term (int)
    tx.addSubclass(new Mutation.SubclassRequest("Tripel", "Beer"));
    return null;
});

// Manual form - try-with-resources; close() rolls back if not committed.
try (Transaction tx = oxid.beginTransaction()) {
    int term = tx.insert(Txn.TxnInsertRequest.of("Chimay", "Beer"));
    tx.addSubclass(new Mutation.SubclassRequest("Quadrupel", "Beer"));
    tx.commit();
}
use OxidDb\Client\Transaction;
use OxidDb\Client\Model\TxnInsertRequest;

// Scope helper - commits on success, rolls back on throw.
$oxid->transaction(function (Transaction $tx): void {
    $tx->insert(new TxnInsertRequest('Duvel', 'Beer', vector: [0.2, 0.4, 0.1, 0.3], collection: 'demo_beers'));
    $tx->insert(new TxnInsertRequest('Chimay', 'Beer'));
});

// Manual control - begin / rollback explicitly.
$tx = $oxid->begin();
$term = $tx->insert(new TxnInsertRequest('Ghost', 'Beer'));  // returns interned Term id
$rollback = $tx->rollback();                                 // Ghost discarded
// Callback form - auto commit/rollback.
await oxid.TransactionAsync(async tx =>
{
    await tx.InsertAsync(new TxnInsertRequest("Corona", "Pilsner",
        Vector: new[] { 0.7, 0.2, 0.4, 0.1 }, Collection: "beers"));
    await tx.AddSubclassAsync(new SubclassRequest("Pilsner", "Beer"));
    await tx.AddObjectPropertyAsync("Corona", "brewedBy", "GrupoModelo");
    // returns → COMMIT ; throws → ROLLBACK (exception re-raised)
});

// Manual form with a savepoint.
await using Transaction tx = await oxid.BeginTransactionAsync();
await tx.InsertAsync(new TxnInsertRequest("Maybe", "Stout"));
int sp = await tx.SavepointAsync();
await tx.InsertAsync(new TxnInsertRequest("Discarded", "Stout"));
await tx.RollbackToAsync(sp);   // drop "Discarded", keep "Maybe"
await tx.CommitAsync();

Gotcha: gated writes return 200 on veto

Check the body, not just the status The consistency-gated write routes (/actions/assert-typed, /actions/add-axiom, and /entities with "gate":true) return HTTP 200 even when the reasoner vetoes the write. A veto is a normal, expected outcome, not a transport error. Branch on the response body: the /actions/* routes report {"committed": false, ...} when the write was rejected as inconsistent, and gated /entities reports its outcome under ok. A 200 alone does not mean the axiom was committed.

Embedder model-mixing guard. New in 0.9.8 Two models' vectors in one collection degrade search silently, and the existing dimension check cannot see a same-dimension swap (for example one 1536-d model for another). Setting the embedder while the database already holds vectors therefore compares the stored model identity, provider:model (the Ollama endpoint URL and the dimension are deliberately not part of it), against the requested one. A different identity is refused before anything changes: PUT /config/embedder answers 409 {"code":"EMBEDDER_MODEL_MISMATCH", ...} naming both models, and POST /config/apply, which never returns a bare 4xx, reports it as {"key":"embedder","applied":false,"reason":"..."} with the top-level applied false. Re-applying the same model, switching on an empty database, and switching to a manual (model-less) embedder are all allowed. When the stored vectors have no known model identity (written manually, or before this guard existed) the change is allowed and the 200 response carries a warnings[] entry saying the no-mix guarantee holds only for vectors written from now on. The way out of a real model change is a fresh collection for the new model; a full re-embed is not yet available. crates/oxd-server/src/lib.rs
