Docs / OxQL Query Language / Aggregation

Aggregation

Count and group results with OxQL: turn a set of matching documents into summary numbers with COUNT(*), SUM, AVG, MIN, MAX and GROUP BY.

Aggregation collapses a set of matching documents into summary numbers: how many, the total, the average, the extremes, optionally broken down by a grouping key. In OxQL this is the AGGREGATE clause, and it runs over exactly the set your WHERE / NEAR filters produced. Everything on this page runs through POST /query on the server at https://85cfad134a4a.oxid-db.com.

Aggregation needs FROM An AGGREGATE query names a document collection with FROM (this switches OxQL into document mode). With FROM present, a WHERE stage is optional. A pure-aggregate over the whole collection is legal. AGGREGATE and PROJECT are mutually exclusive; you use one or the other, never both.

The examples use a beers document collection whose documents carry a style field ("Pilsner", "Stout", "Wine", "Ale") and a numeric abv field, the same shape shown on Inserting & Bulk Loading.

COUNT(*)

The simplest aggregate counts matching documents. The exact syntax is COUNT(*), the literal tokens COUNT ( * ). Writing COUNT() with empty parentheses is a parse error; use COUNT(*) to count rows, or COUNT(field) to count only documents where field is present and non-null.

oxql
FIND ?x FROM beers AGGREGATE COUNT(*)

Send it to POST /query like any other OxQL statement (the OxQL text goes in the query field of the request body):

curl -s -X POST https://85cfad134a4a.oxid-db.com/query \
  -H 'Content-Type: application/json' \
  -d '{"query":"FIND ?x FROM beers AGGREGATE COUNT(*)"}'
with OxidDB("https://85cfad134a4a.oxid-db.com") as db:
    page = db.query("FIND ?x FROM beers AGGREGATE COUNT(*)")
    agg = page["aggregation"]
    print(agg["groups"][0]["values"]["COUNT(*)"])   # e.g. 20
const page = await db.query({ query: "FIND ?x FROM beers AGGREGATE COUNT(*)" });
const total = page.aggregation.groups[0].values["COUNT(*)"];

With no GROUP BY, the result is a single group whose key is empty and whose values hold each computed function. The count lands at aggregation.groups[0].values["COUNT(*)"]:

json
{
  "aggregation": {
    "functions": ["COUNT(*)"],
    "group_by": [],
    "groups": [{ "key": {}, "values": { "COUNT(*)": 20 } }],
    "docs_scanned": 20,
    "over_filtered_subset": false
  },
  "results": [],
  "total_count": 20
}

The familiar results and total_count fields are still present; the summary rides along in an additive aggregation object. A query without an AGGREGATE clause never grows an aggregation field, so ordinary queries are unaffected.

The functions

List one or more of these after AGGREGATE, comma-separated:

FunctionReturnsField types
COUNT(*)Number of matching documents.Any (no field needed).
COUNT(field)Number of documents where field is present and non-null.Any.
SUM(field)Sum of the values.Numeric only (int / float / timestamp).
AVG(field)Mean of the values.Numeric only.
MIN(field)Smallest value.Any orderable type.
MAX(field)Largest value.Any orderable type.
COUNT_DISTINCT(field)Number of distinct values (exact).Any orderable type.
SUM/AVG on a non-numeric field is a 400 Asking for SUM(style) where style is a string returns HTTP 400 Bad Request (error code QUERY_ERROR) rather than a silent 0. An aggregate that cannot be computed is a loud error, by design.

Grouping

Add GROUP BY field to compute each function once per distinct value of that field. Groups come back sorted by key. This query summarises the catalogue by beer style:

oxql
FIND ?x FROM beers AGGREGATE COUNT(*), AVG(abv), MIN(abv), MAX(abv) GROUP BY style

Each distinct style becomes one group; its key carries the grouping field and its values carry the four measures:

json
{
  "aggregation": {
    "functions": ["COUNT(*)", "AVG(abv)", "MIN(abv)", "MAX(abv)"],
    "group_by": ["style"],
    "groups": [
      { "key": { "style": "Pilsner" }, "values": { "COUNT(*)": 3, "AVG(abv)": 4.7, "MIN(abv)": 4.4, "MAX(abv)": 5.0 } },
      { "key": { "style": "Stout" },   "values": { "COUNT(*)": 2, "AVG(abv)": 6.6, "MIN(abv)": 4.2, "MAX(abv)": 9.0 } },
      { "key": { "style": "Wine" },    "values": { "COUNT(*)": 1, "AVG(abv)": 13.0, "MIN(abv)": 13.0, "MAX(abv)": 13.0 } }
    ],
    "docs_scanned": 6,
    "over_filtered_subset": false
  }
}

Group by more than one field by listing them: GROUP BY style, brewery. Each group's key then carries both fields. Any orderable field works as a key: strings, ints, floats, booleans, timestamps; arrays and objects cannot be grouping keys.

Aggregating a filtered subset

The aggregate always reflects whatever your filters left behind. Add a WHERE stage and you summarise only the matches (here, only stronger beers):

oxql
FIND ?x FROM beers WHERE ?x.abv > 5.0 AGGREGATE COUNT(*) GROUP BY style

This matters most when a vector search is involved. If the query ranks and truncates with NEAR … LIMIT k, the aggregate is computed over those k ranked hits, not the whole collection, and the response sets over_filtered_subset to true so you can tell the numbers describe the ranked neighbourhood, not the entire collection.

Ordering & HAVING

Three post-aggregation operators run over the computed groups, and they must appear in this fixed order, HAVING then ORDER BY then TOP, always after GROUP BY:

oxql
FIND ?x FROM beers
  AGGREGATE COUNT(*), AVG(abv)
  GROUP BY style
  HAVING COUNT(*) > 1
  ORDER BY AVG(abv) DESC
  TOP 3
HAVING <fn> <op> <literal>
Keeps only groups whose measure passes the comparison (= != > < >= <=). The measure must be one of the functions you declared in AGGREGATE; groups whose measure is absent are dropped.
ORDER BY <fn> [ASC|DESC]
Sorts groups by a declared measure. Ordering is fully deterministic: ties break on ascending group key regardless of direction, and an absent measure sorts last in ASC, first in DESC.
TOP <n>
Keeps the first n groups after ordering. TOP requires ORDER BY. Truncating unordered groups would be non-deterministic, so it is rejected.
LIMIT never truncates groups LIMIT keeps its row meaning everywhere and does not cut down the group list. Group top-N is exclusively TOP. So existing aggregate queries that also carry a LIMIT are unaffected.

Reading aggregate results

The aggregation object is additive and its shape is stable. These are the fields you can rely on:

json
{
  "aggregation": {
    "functions": ["COUNT(*)", "SUM(abv)"],   // the functions you requested, in order
    "group_by": ["style"],                    // grouping fields, [] when ungrouped
    "groups": [
      {
        "key": { "style": "Stout" },          // {} for an ungrouped query
        "values": { "COUNT(*)": 2, "SUM(abv)": 13.2 }
      }
    ],
    "docs_scanned": 6,                         // documents the aggregate touched
    "over_filtered_subset": false             // true when computed over a NEAR top-k
  },
  "results": [],
  "total_count": 6
}

Read a scalar out of an ungrouped query at aggregation.groups[0].values["COUNT(*)"]; for a grouped query, iterate aggregation.groups and read each group's key and values. The SDKs return this object verbatim from query(), so the access path is the same in every language.

What the grammar does not allow
  • No aggregation without FROM. AGGREGATE is document-mode only; an aggregate query over the ontology (no FROM) is a request error.
  • No HAVING/ORDER BY/TOP outside AGGREGATE. Those three keywords exist only inside an aggregate clause, in that fixed order.
  • No COUNT(). Empty parentheses are invalid. Use COUNT(*) or COUNT(field).
  • SORT does not order the HTTP response. Over POST /query the wire order is IRI (or score, then IRI, for NEAR/hybrid rows), not any OxQL SORT. For groups, order deterministically with ORDER BY inside AGGREGATE; groups without ORDER BY come back sorted by key.
  • No OR, no parentheses, no joins. Filters are a flat AND chain over a single variable. Disjunction over one field is expressible only via ?x.field IN [...].
