Introduction

Oxid-DB is a database engine written from scratch in Rust that natively unifies OWL ontology reasoning and vector similarity search in a single system, so one query can combine class inference with semantic search, and the reasoner's filter is applied during vector traversal, not bolted on afterward.

New to Oxid-DB? The fastest path is the Quick Start: clone, make run, and query the demo ontology in about two minutes. This page explains what the engine is and how the pieces fit together.

What is Oxid-DB#

Most systems force a choice. Graph and RDF engines bolt vector search onto a SPARQL query planner; vector databases bolt metadata filters onto an ANN index. Either way there is a seam: the symbolic layer and the similarity layer live in different data structures, and every hybrid query pays to cross it.

Oxid-DB removes that seam. Every entity is a single Term(u32) shared by the reasoner, the vector index, and the document store. A query can classify entities by inferred type and rank them by vector similarity in one pass, with the ontology candidate set pruning the vector graph as it is traversed.

How it compares to Qdrant & Weaviate On pure vector search Oxid-DB is at parity, not ahead: real OpenAI-1536 recall@10 of 0.9839 at 1M vectors, served off-RAM, proven to 10M×1536-D at ~23 GiB resident. The honest difference is category: Oxid-DB is an embedded reasoning engine that runs a competitive vector tier alongside an OWL/EL⊥ reasoner, typed documents, and ACID transactions.

Key features#

Symbolic

Shared identifier space

Every entity is a Term(u32) used by the reasoner and the vector index alike. Hybrid queries become zero-copy joins.

Neural

Filter-during-traversal

The reasoner produces a candidate bitset that prunes the HNSW graph during descent, not as a wasteful post-filter.

Symbolic

OWL 2 EL⊥ reasoning

Transitive closure, conjunction, existential propagation, disjointness (⊥), type propagation, and length-2 role chains and transitivity (closed by default), all in PTime.

Neural

OxQL query language

Vector neighborhoods are first-class pipeline stages. Syntax inspired by SPARQL and Cypher, not a bolt-on extension.

Beyond the four pillars, Oxid-DB ships a schema-free JSON document store whose records can be typed into your ontology, geospatial support (a GeoPoint field type with WITHIN radius filtering and SORT DISTANCE nearest-first ordering, backed by an opt-in grid index), off-RAM vector residency (serve far more than fits in memory), crash-safe ACID storage with MVCC snapshots, and KGE training (TransE / RotatE) for link prediction.

Getting access

Managed while Oxid-DB is closed-source While Oxid-DB is closed-source, installation, provisioning, and the database runtime are managed for you: you receive a ready-to-use endpoint (for example https://85cfad134a4a.oxid-db.com) and connect with one of the clients below. When Oxid-DB opens up, this documentation will expand with in-depth guides for self-hosting, CLI commands, and database settings. See Access & Hosting.

Once you have an endpoint, jump to the Quick Start to run your first hybrid query, or pick your language on the SDKs & Clients page.

A taste of OxQL#

OxQL is the query language that makes the seam disappear. The query below finds everything classified as Beer (including subclasses like Pilsner and Stout reached by transitive inference) and then ranks the survivors by vector similarity to a flavor profile:

oxql hybrid-query 
FIND ?x
  WHERE ?x IS-A Beer
  NEAR ?x TO [0.9, 0.0, 0.0, 0.5]
  LIMIT 5

The ontology filter (IS-A Beer) and the similarity ranking (NEAR … TO) execute together: the inferred class membership prunes the vector graph before and during traversal. Documents typed into the ontology fall out of the same machinery:

oxql document + inference 
# A JSON doc inserted into the "beers" collection, found by an inferred superclass
FIND ?x WHERE ?x IS-A Drink
OxQL essentials A query always begins with FIND ?x and needs at least one WHERE stage. Use COUNT(*) (not COUNT()) for aggregation, and reference fields as ?x.field. Full grammar in the OxQL reference.

Talking to the server#

Everything the CLI and web UI do is available over a plain HTTP JSON API. A minimal query request looks like this:

bash curl 
curl -X POST https://85cfad134a4a.oxid-db.com/query \
  -H 'Content-Type: application/json' \
  -d '{"oxql": "FIND ?x WHERE ?x IS-A Beer LIMIT 5"}'

The most commonly used endpoints:

MethodPathPurpose
POST/queryExecute an OxQL query
POST/individualsInsert an individual with class + vector
POST/importStream a large ontology / dataset import
POST/collections/:name/bulkBulk-load JSON documents
GET/readyReadiness probe for orchestration

See the HTTP API reference for the full surface, or the Python SDK and MCP integration for higher-level clients.

Architecture#

Oxid-DB is a Cargo workspace of focused crates. The core of the engine:

CrateResponsibility
oxd-coreTerm dictionary, ontology model, OWL/CSV import
oxd-reasonerOWL 2 EL classification (CR1 to CR8, including role chains and transitivity), consistency checking
oxd-vectorHNSW & flat indexes, SIMD distance kernels, off-RAM cold-f32
oxd-documentSchema-free JSON document store with secondary indexes
oxd-storageCrash-safe persistence, WAL, MVCC snapshots, classification cache
oxd-querypest OxQL parser, hybrid filter-then-search executor
oxd-serverHTTP REST API (axum + tokio), embedded web UI

Additional crates cover embeddings (oxd-embed), KGE training (oxd-train), auth (oxd-auth), the CLI (oxd-cli), and Python bindings (oxd-python). See System Design for the full map and Storage Engine for the durability model.
