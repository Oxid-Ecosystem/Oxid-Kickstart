Hybrid Queries

Combine symbolic reasoning and vector similarity in a single query, evaluated in one pass. A hybrid query asks the reasoner which entities qualify and the vector index how similar they are, at the same time, over the same identifiers, with no glue code between them.

New in 0.9.8 The symbolic axis now reaches real-world vocabularies verbatim. IS-A accepts an angle-bracketed IRI (?x IS-A <http://data.europa.eu/esco/occupation/0e2d-24d0-4b73>), so a hybrid query can gate on an ESCO, CPV, or NUTS class whose IRI carries hyphens or other characters a bare identifier cannot, and then rank the members by NEAR or filter them by WITHIN in the same statement. A bare NEAR ?x also resolves to the sole collection when the database holds exactly one, so the simplest hybrid query needs no .<collection> qualifier. See Real-world class IRIs below, and the Changelog for the full 0.9.7 → 0.9.8 difference.

This is the page to read if you only read one. Reasoning (OWL 2 EL⊥) and vector search are each useful on their own, but the reason Oxid-DB exists is that it runs both inside the same query planner. That fusion is what the rest of these docs build toward.

The seam problem

Most systems make you choose a side, then pay a tax to reach the other.

Symbolic RDF / graph engines

Reason about class hierarchies and relationships: they know a Pilsner is a Beer is a Beverage. But they have no notion of "closest" or "most like this": an entity either matches a pattern or it does not. Vector similarity is bolted on as a side index.

Neural vector databases

Find similar items by comparing embeddings. But they have no concept of a class hierarchy. "Only beers" becomes a flat metadata tag with no logical depth: the store does not know that a Lager is a Beer, so it cannot include inferred members or exclude disjoint ones.

To answer a question that needs both ("the most bitter beers, including every subtype of beer, ranked by flavour similarity") you normally wire two systems together and shuttle results across the boundary between them. That boundary is the seam: an RDF engine post-filters a vector list it fetched elsewhere, or a vector DB applies a metadata predicate it cannot reason over. Every hybrid answer pays to cross it: extra round-trips, wasted distance computations, and results that silently go missing.

Oxid-DB removes the seam by giving the reasoner and the vector index a shared identifier space. Every IRI, individual, document, and vector that denotes the same thing is interned to the same integer Term, so a class extent computed by the reasoner is the candidate set for the vector search, with no join, no separate ID space, and no crossing.

Filter-during-traversal

The key idea is where the class filter is applied. Oxid-DB does not run the vector search over everything and then discard the misses (post-filter), and it does not narrow the graph up front into a smaller index (pre-filter). It carries the reasoner's candidate set into the HNSW walk and applies it while the graph is being traversed.

Concretely: the reasoner hands the planner the class extent as a TermBitSet, a compact bitmap where a set bit means "this individual is in the class (asserted or inferred)". The HNSW search then uses every node as a routing waypoint to steer the walk, but only nodes whose Term is in the bitset are allowed into the result heap. Routing quality is preserved (the whole graph still guides navigation) while the returned k are guaranteed to be in-class.

StrategyWhen the class filter runsCost / failure mode
Pre-filter Before search: build/scan a sub-index of only the matching members. Correct, but throws away the shared HNSW graph; a fresh structure per filter is expensive and defeats the point of one index.
Post-filter After search: run ANN over the whole graph, then drop non-matching hits. Wastes distance computations on entities you discard; for a rare class the top-k comes back mostly empty (the recall cliff). You must over-fetch by an unknown factor and may still miss the true 4th-nearest member.
During-traversal (Oxid-DB) During search: the bitset gates which nodes enter the result heap as the graph is walked. Every returned hit is a valid class member; no over-fetch guessing, no wasted results. This is the default for selective filters.

The planner picks a strategy by estimated selectivity of the filter. A selective filter (roughly half the corpus or less) takes the filter-during-traversal path just described. A very selective filter drops to an exact brute-force scan over just the bitset members, cheaper than walking the graph when the candidate set is tiny. A broad filter (most of the corpus passes) instead over-samples the vector search and filters the results, because when almost everything qualifies the whole-graph walk is already efficient and gating adds no value. All three paths return the same rows; only the cost differs.

Note The selectivity switch is a cost optimization, not a correctness switch: a mis-estimate picks a slower plan, never a wrong answer. And the filter must come from an ontology-backed stage (an IS-A class or a relation): the planner pushes that into traversal, not arbitrary post-hoc predicates.

A hybrid query

In OxQL a hybrid query is one FIND statement whose WHERE chain contains both a symbolic stage and a NEAR stage. Here is the canonical shape, over the beverage ontology with a 4-dimensional flavour vector:

oxql
FIND ?x
WHERE ?x IS-A Beer
NEAR ?x TO [0.9, 0.0, 0.0, 0.5]
LIMIT 5

Reading it clause by clause:

FIND ?x
The single result variable. OxQL binds exactly one variable; there are no joins or second variables.
WHERE ?x IS-A Beer
The symbolic stage. It resolves to the reasoner's class extent of Beer: every member of Beer and all of its subclasses, transitively (Lager, Ale, Stout, IPA, Pilsner…), including individuals never asserted directly as Beer. This is the candidate bitset.
NEAR ?x TO [0.9, 0.0, 0.0, 0.5]
The vector stage. It ranks candidates by distance to the query vector (here a "bitter" flavour profile). The bitset from the previous stage prunes the HNSW traversal, so only beers are ever scored. Each result row carries a score field.
LIMIT 5
Return the five nearest in-class members. Omitting LIMIT defaults to 10.
Tip Stages are chained by whitespace; the connector AND is optional, so IS-A Beer NEAR ?x TO […] and IS-A Beer AND NEAR ?x TO […] are equivalent. There is no OR and no grouping; the chain is a flat conjunction. You can also pass a text query to NEAR ?x TO "crisp pale lager" (auto-embedded when an embedder is configured) and widen the HNSW search with EF <n>.

The same query from application code: pass the OxQL string to the standard query endpoint and read the score on each row:

curl -s -X POST https://85cfad134a4a.oxid-db.com/query \
  -H 'Content-Type: application/json' \
  -d '{"query":"FIND ?x WHERE ?x IS-A Beer AND NEAR ?x TO [0.9,0.0,0.0,0.5] LIMIT 5"}'
with OxidDB("https://85cfad134a4a.oxid-db.com") as db:
    # literal query vector (dims must match the collection)
    hits = db.query("FIND ?x WHERE ?x IS-A Beer AND NEAR ?x TO [0.9, 0.0, 0.0, 0.5] LIMIT 5")
    for h in hits.get("results", []):
        print(h["iri"], h.get("score"))
// OxQL NEAR over /query - hybrid-capable (combine with IS-A). Rows carry `score`.
const near = await db.query({
  query: "FIND ?x WHERE ?x IS-A Beer AND NEAR ?x TO [0.9, 0.0, 0.0, 0.5] LIMIT 5",
});
for (const hit of near.results) console.log(hit.iri, hit.score);
// Hybrid: Beers nearest a 4-dim probe vector, top 5.
oxql := oxid.NewQueryBuilder().
	Find("x").
	IsA("Beer").
	Near([]float64{0.9, 0.0, 0.0, 0.5}).
	Limit(5).
	ToOxql()
res, err := client.Query(ctx, oxid.QueryRequest{Query: oxql})
if err != nil {
	log.Fatalf("hybrid query: %v", err)
}
for _, hit := range res.Results {
	if hit.Score != nil {
		log.Printf("%s score=%.4f", hit.IRI, *hit.Score)
	}
}

A response looks like this: ranked, in-class, and scored:

json
{
  "results": [
    { "iri": "SierraIPA", "score": 0.0042 },
    { "iri": "Guinness",  "score": 0.0891 },
    { "iri": "Heineken",  "score": 0.1247 },
    { "iri": "BlueMoon",  "score": 0.3562 }
  ],
  "total_count": 4
}

Note what is absent: a Riesling (a WhiteWine) never appears, even if its embedding happened to be close to the bitter probe. Wine is not a subclass of Beer, so wines were never in the bitset and were never scored. Flip the class and the vector (FIND ?x WHERE ?x IS-A Wine NEAR ?x TO [0.0, 1.0, 0.3, 0.1] LIMIT 5) and the reverse holds: every beer is excluded before the search begins.

Three axes in one query

The same fusion extends past two stages. Because every stage in the WHERE chain constrains the one bound variable, a single OxQL statement can compose symbolic membership (IS-A), a geospatial radius (WITHIN), and vector similarity (NEAR) at once. Picture a “pediatric clinics near me, ranked by how well they match this need” query over a bridged clinics collection whose documents carry a GeoPoint location field:

oxql
FIND ?x FROM clinics
WHERE ?x IS-A PediatricClinic
AND ?x.location WITHIN 10km OF (52.0907, 5.1214)
AND NEAR ?x TO "after-hours care for infants"
LIMIT 5

Read as a single pipeline: the IS-A PediatricClinic stage resolves to the reasoner's class extent (every subclass of PediatricClinic, transitively), the WITHIN stage keeps only those inside a 10 km great-circle radius of the point (here Utrecht, written (lat, lon)), and the NEAR stage ranks the survivors by vector distance to the auto-embedded text. It is one statement over one shared identifier space, not three services stitched together; the symbolic and geospatial predicates prune the candidate set before the vector search ever scores a row. Each result carries both a score (from NEAR) and a distance_m (from the geo clause).

Swap the domain freely: “IS-A CraftBrewery, WITHIN 5km of downtown, NEAR a hop-forward flavour probe” is the same shape. The ordering still comes from vector distance alone; IS-A and WITHIN are hard membership gates, not blended into the score (see Scoring & Ranking).

Real-world class IRIs New in 0.9.8

The examples above use short class names from the beverage ontology. Production ontologies name classes with full IRIs, and many of those IRIs contain characters that OxQL's bare identifier alphabet ([A-Za-z0-9_:/#.], starting with a letter) does not allow: ESCO occupation IRIs carry hyphenated UUID segments, CPV codes carry tildes and percent-encoding. Since 0.9.8, wrap such a class in angle brackets and IS-A takes it verbatim. The hybrid pipeline is unchanged: the reasoner still resolves the bracketed class to its transitive extent, and the vector stage still scores only in-class members.

oxql
-- every occupation under this ESCO concept (subclasses included), ranked by fit to the text
FIND ?x
WHERE ?x IS-A <http://data.europa.eu/esco/occupation/0e2d-24d0-4b73>
AND NEAR ?x TO "builds and maintains data pipelines"
LIMIT 3

Over HTTP the query is the same string in the query field of POST /query, escaped like any other JSON string. Every SDK passes it through as a raw OxQL string; the Go, Java, and .NET query builders concatenate the class you give isA(...) verbatim, so isA("<http://…>") with the brackets included works too:

curl -s -X POST https://85cfad134a4a.oxid-db.com/query \
  -H 'Content-Type: application/json' \
  -d '{"query":"FIND ?x WHERE ?x IS-A <http://data.europa.eu/esco/occupation/0e2d-24d0-4b73> AND NEAR ?x TO \"builds and maintains data pipelines\" LIMIT 3"}'
ESCO = "<http://data.europa.eu/esco/occupation/0e2d-24d0-4b73>"

The brackets are needed only when the IRI cannot be written bare: IS-A http://oxid.example/onto#Beer and IS-A <http://oxid.example/onto#Beer> are the same query. The rules, including what a bare token may contain and why IS-A <> is rejected, are on the OxQL page.

Why it matters

Fusing the two stages buys three things at once:

Correctness

IS-A uses the reasoner's inferred class membership, not a stored tag. An individual asserted only as Lager is still returned by IS-A Beer, because classification places it in Beer's extent. Disjoint classes are excluded for the same reason. A tag-based filter would miss the inferred members and could not enforce the disjointness.

Efficiency

Distances are computed only for candidates that survive the filter. On a corpus that is 10% beers, a post-filter would spend ~90% of its distance work on entities it then discards; filter-during-traversal simply never scores them.

No recall cliff

Ask for the top 5 and you get the true 5 nearest class members, not "however many of the global top 5 happened to match". No over-fetch guessing, no fewer-than-requested pages, no true-nearest member lost below an arbitrary fetch depth.

When to use it

Reach for a hybrid query whenever a similarity search needs to respect meaning, or a symbolic result needs to be ranked:

  • Semantic search scoped by type: "documents similar to this one, but only support tickets" or "images like this, restricted to products still in the catalogue". The IS-A stage scopes; NEAR ranks.
  • Recommendations within a taxonomy: "wines like this Barolo, staying inside RedWine", so subtypes are included and disjoint categories are excluded automatically.
  • Constrained retrieval for RAG: fetch the nearest passages that also satisfy an ontology constraint (jurisdiction, clearance level, product line) in one call, instead of retrieving broadly and re-checking afterwards.
  • Attribute-bounded similarity: combine the class filter with data-property predicates, e.g. ?x IS-A Beer AND ?x.abv > 4.5 AND NEAR ?x TO […], and let the planner prune before it ranks.

When you need only class members (no ranking) use a pure logical query; when there is no meaningful class to scope by, a pure vector query is fine. The hybrid form is for the questions that genuinely need both.

Honest scope Oxid-DB's pure-ANN performance is at parity with dedicated vector engines such as Qdrant and Weaviate (HNSW with SQ8 quantization and cosine/L2/inner-product/L1 metrics); it is not faster on raw vector search. The differentiator is the fused reasoning + vector query described here: the class filter is a hard, inference-aware membership gate, and the vector stage supplies the ordering. The logical and vector sides are not blended into one tunable weighted score; ranking within a single hybrid query comes from vector distance, and reciprocal-rank fusion is used only to merge results across multiple vector collections. See Scoring & Ranking for the exact model.
