Document Store

Schema-free JSON documents that live in named collections, and, when you want it, become typed ontology individuals the reasoner and vector search can see.

Oxid-DB is best known as a neurosymbolic engine: it reasons over an OWL 2 EL⊥ ontology and searches vector embeddings in one process. The document store is the third pillar. It holds the kind of JSON you already have (from an API, a log, or an export) with no schema to declare up front. You drop documents into a collection, query them with field filters, and (optionally) type them into your ontology so the same reasoner and hybrid search work over them for free.

You don't need ontologies to start The document store works as a plain JSON database on its own. The reasoning and vector parts are opt-in. Every example on this page runs against a server at https://85cfad134a4a.oxid-db.com. Start there, add the clever bits when you want them.
Since 0.9.7 Documents can now carry a GeoPoint field: a latitude/longitude pair written with the {"$geo":{"lat": …,"lon": …}} sentinel and stored losslessly. Once your documents hold coordinates you can filter by radius and sort by distance in OxQL, add an opt-in spatial index for large collections, and view a collection on a map in the Web UI. See the Changelog for the full 0.9.6 → 0.9.7 difference.

The JSON document model

A document is just a JSON object. It can be as small as {"name":"Heineken"} or deeply nested (up to 16 levels). Documents live in collections (named buckets like beers or breweries) and there is no fixed schema: two documents in the same collection may carry completely different fields. Oxid-DB discovers the shape of your data as it arrives.

Every document has an IRI, a stable string id. You supply your own with the top-level _iri field; if you omit it, the store synthesises one as {collection}#{n} (a per-collection counter). That IRI is the same id the ontology and vector layers use, which is what makes the bridge below possible.

Here is a single beer document as you would send it:

json
{
  "_iri": "Duvel",
  "name": "Duvel",
  "style": "Belgian Strong Ale",
  "abv": 8.5,
  "brewery": "Duvel Moortgat",
  "tags": ["belgian", "bottle-conditioned"],
  "released": { "$timestamp": 1716500000000 }
}

Internally each value is one of eleven typed variants. Seven map straight to and from ordinary JSON; the other four are engine-native and use a single-key tagged object form. You rarely think about the list (you just send JSON) but it explains what the engine can store, index, compare, and aggregate.

TypeJSON you sendNotes
String"Duvel"Text. Supports prefix (range) matching when indexed.
Int564-bit signed integer.
Float8.564-bit double. 5 and 5.0 are different stored types. See the note below.
BooltrueTrue or false.
NullnullAn explicit null is still a present field.
Array["belgian","ale"]Ordered list of values.
Object{"city":"Puurs"}Nested document. Reach inner fields with dotted paths, e.g. address.city.
Timestamp{"$timestamp": 1716500000000}Epoch milliseconds. Orderable. Single-key tagged object.
Binary{"$binary": [0,1,2,255]}Opaque bytes as a JSON array of integers 0 to 255. Stored, not indexed.
Vector{"$vector": [0.12, 0.90, 0.31, 0.07]}An embedding. Must use this tagged form. A bare array stores an Array, not a Vector. See the limits note at the end.
GeoPoint 0.9.7{"$geo": {"lat": 52.3702, "lon": 4.8952}}A geographic point. Order is always (lat, lon): latitude in [-90, 90] (positive north), longitude in [-180, 180] (positive east). See the note below.
Int vs Float: filters coerce, sort/group don't Comparisons treat Int and Float as one numeric domain. A filter ?x.abv = 5 matches both the integer 5 and the float 5.0. But SORT and GROUP BY order by the stored type, so an Int 5 and a Float 5.0 land in different groups. Encode a numeric field consistently across a collection if you intend to group or sort on it.

GeoPoint fields 0.9.7

A GeoPoint is a geographic coordinate stored as a document field. You write it with the single-key $geo sentinel, whose value is an object with lat and lon numbers. The order is always (lat, lon): latitude comes first, in [-90, 90] with positive values north; longitude comes second, in [-180, 180] with positive values east.

json
{
  "_iri": "ams-brewery",
  "kind": "Brewery",
  "name": "Amsterdam Brewery",
  "location": { "$geo": { "lat": 52.3702, "lon": 4.8952 } }
}

Coordinates are validated on insert: an out-of-range or non-finite lat/lon is rejected with 400, and the error names the (lat, lon) order so a swapped pair is easy to spot. A stored GeoPoint is kept losslessly in the binary document format and the write-ahead log, and rebuilt on checkpoint. GeoPoint is a document-only type: it does not bridge into the ontology. Once your documents carry GeoPoints you can filter by radius and sort by distance in OxQL (see Querying Documents) and, for large collections, add an opt-in spatial index (see Indexing & Schema).

Collections

A collection is a named bucket of documents. There are two ways one comes into existence, and the difference matters:

  • Document collections auto-create. The first time you POST a document to /documents/beers, the beers collection springs into being. You never have to declare it.
  • Vector collections are created explicitly with POST /collections. This is a separate concept: it provisions an HNSW similarity index with a fixed dimension and distance metric. Those two settings describe the collection's vectors, not its documents.

You only need POST /collections when you want a dedicated, searchable vector index (for example the target of an embedding pipeline, or the destination the ontology bridge upserts into). A pure document collection carries no vectors and needs no dimensions/metric at all. Create a vector collection like this:

curl -s -X POST https://85cfad134a4a.oxid-db.com/collections \
  -H 'Content-Type: application/json' \
  -d '{"name":"beers","dimensions":384,"metric":"cosine","quantization":"none"}'
with OxidDB("https://85cfad134a4a.oxid-db.com") as db:
    db.create_collection("beers", dim=4, metric="cosine")
    # creating the same shape again returns 409 - catch OxidHttpError, ignore 409
// Field is `dimensions` (not `dim`).
await db.createCollection({ name: "beers", dimensions: 4, metric: "cosine" });

const list = await db.collections();
console.log(list.collections.map((c) => `${c.name}/${c.dimensions}`));
// The field is `Dimensions` (not `dim`). Metric: cosine | l2 | ip | manhattan.
if err := client.CreateCollection(ctx, oxid.CreateCollectionRequest{
	Name:       "beverages",
	Dimensions: 4,        // 4-dim vectors
	Metric:     "cosine",
}); err != nil {
	log.Fatalf("create collection: %v", err)
}
// 4-dim vector collection for beverage embeddings (field is `dimensions`, not `dim`)
oxid.createCollection(Collections.CreateCollectionRequest.of("beverages", 4));
use OxidDb\Client\Model\CreateCollectionRequest;

// The field is `dimensions`, not `dim`.
$oxid->createCollection(new CreateCollectionRequest('demo_beers', 4, 'cosine'));
// A 4-dim collection for beverage vectors (wire key is `dimensions`, not `dim`).
await oxid.CreateCollectionAsync(new CreateCollectionRequest("beers", 4));

// With an explicit metric:
await oxid.CreateCollectionAsync(new CreateCollectionRequest("beers", 4, Metric: "cosine"));

The wire field is dimensions (some SDKs surface it as dim for brevity). metric is one of cosine (default), l2, ip, or manhattan; for all four, lower distance means more similar. Re-creating a collection with the same shape is a safe no-op that returns 409. Catch and ignore it. See Vector Search for what these settings do under the hood.

Your first document

Inserting is a single POST to /documents/{collection} whose body is the raw JSON document. An optional top-level _iri sets the id; leave it out and the store synthesises one. The response echoes the collection and the resolved IRI.

curl -s -X POST https://85cfad134a4a.oxid-db.com/documents/people \
  -H 'Content-Type: application/json' \
  -d '{"_iri":"Dave","name":"Dave","score":3}'
with OxidDB("https://85cfad134a4a.oxid-db.com") as db:
    res = db.insert_document("beers", {"name": "Heineken", "abv": 5.0}, iri="Heineken")
    # res: {"ok": true, "collection": "beers", "iri": "Heineken"}
const res = await db.insertDocument("beers", {
  _iri: "Heineken",
  name: "Heineken",
  style: "Pilsner",
  abv: 5.0,
});
console.log(res.ok, res.iri); // true "Heineken"
res, err := client.InsertDocument(ctx, "beverages", oxid.Document{
	"_iri":  "PilsnerUrquell",
	"name":  "Pilsner Urquell",
	"style": "Pilsner",
	"abv":   4.4,
})
if err != nil {
	log.Fatalf("insert document: %v", err)
}
log.Printf("ok=%v iri=%s", res.Ok, res.IRI)
import java.util.Map;

Documents.InsertDocumentResponse res = oxid.insertDocument("beverages", Map.of(
        "id", "Heineken",
        "name", "Heineken",
        "style", "Pilsner",
        "abv", 5.0));
System.out.println(res.iri());
$res = $oxid->insertDocument('beer_catalog', [
    '_iri'  => 'Heineken',
    'name'  => 'Heineken',
    'style' => 'Pilsner',
    'abv'   => 5.0,
]);
print_r($res);
InsertDocumentResponse res = await oxid.InsertDocumentAsync("beers",
    new Dictionary<string, object?>
    {
        ["name"]  = "Pilsner Urquell",
        ["style"] = "Pilsner",
        ["abv"]   = 4.4,
    });
Console.WriteLine($"inserted {res.Iri} into {res.Collection} (ok={res.Ok})");

The curl call returns {"ok":true,"collection":"people","iri":"Dave"}. Inserting again with the same IRI is an upsert. It replaces the stored document rather than erroring. For loading many documents at once, or streaming NDJSON in and out, see Inserting & Bulk Loading.

The bridge (preview)

So far this is a plain JSON store. The payoff comes when you type a collection into an ontology class. You register a mapping that says "documents in beers are individuals of class Beer, field brewery is the object property producedBy, field abv is a data property," and turn on auto_type. From then on, every document you insert automatically becomes a typed individual with those facts, so after the next classification it lands in the Beer class extent, and the same hybrid IS-A Beer … NEAR query works over your ingested JSON with zero extra machinery.

This is the neurosymbolic payoff A mapped document's IRI is the same id the reasoner and vector index use, so no join and no separate ID space are involved. The document simply is the individual. Mappings are persisted and survive restarts; you register them once. Full walkthrough on The Ontology Bridge.

Honest limits

A document can carry an embedding inline via the tagged {"$vector": [...]} field, but storing it inside the document does not by itself make it searchable. Similarity search runs over a vector collection (the HNSW index you create with POST /collections); the document byte-store and the vector index are separate. To make a document's embedding searchable, either map the field through the ontology bridge as a vector_property (which upserts it into a named vector collection) or upsert the vector directly. A bare JSON array ([0.1, 0.9]) is stored as an Array field, never as a vector; only the $vector tagged form is treated as an embedding.

Two smaller gotchas worth knowing early: a $binary field is stored but never indexed, and (as noted above) Int and Float sort and group as distinct types even though filters compare them as numbers.
