System Design

How Oxid-DB is put together (a Rust workspace of focused crates layered around one engine), and why the reasoner, the vector index, and the document store all share a single identifier space. That shared space is what lets a hybrid query run in one pass with no glue code between the symbolic and the neural halves.

New in 0.9.8 0.9.8 is a production-hardening release; the shape of the system is unchanged and no crate moved layers. Four things were added underneath: a durability latch shared by the WAL writer, group committer, and transaction manager that decides what happens when fsync itself fails; a new leaf crate, oxd-io, that puts an injectable clock and filesystem seam under every durability-critical write so disk faults can be tested rather than assumed; a restore drill that rehearses backup restore end-to-end; and a memory governor that names which figure drives admission (live-data estimate or real RSS). See the Changelog for the full 0.9.7 → 0.9.8 difference.

The big idea

Every named thing that enters Oxid-DB (a class, an individual, a property, a document, a vector's owner, a KGE entity) is interned once into a shared dictionary and represented internally by a single opaque Term, a 32-bit integer. The reasoner's class extents, the vector index's point identifiers, and the document store's row identities are all the same Term values, so a class extent computed by the reasoner is the candidate set for a vector search: no join table, no ID translation layer, no second namespace to reconcile. This one decision is what removes the seam that forces most stacks to bolt a vector database onto a graph engine and shuttle results across the boundary. Everything else in the workspace is organised around keeping that Term space authoritative and cheap to operate on.

Note A Term is not tagged as class-vs-individual. That distinction is membership in the ontology's classes / individuals bitsets, maintained as axioms are added. IDs 0..32 are reserved well-known terms (owl:Thing = Term(0), owl:Nothing = Term(1), rdf:type = Term(2), …); user terms start at 32. The dictionary is persisted with the database, so IDs are stable across sessions.

The crates

Oxid-DB is a single Rust workspace. The crates split along clear responsibilities: a dependency-light core holds the shared spine, focused crates layer reasoning, vectors, documents, and query planning on top, the storage engine composes them behind one write path, and thin server / surface / tooling crates expose the result. A plain cargo build compiles the database-only default members; the agentic oxd-surface-* crates are an opt-in add-on and are excluded from that default build.

The life of a query

A single OxQL statement travels a fixed path from HTTP request to JSON response. Following it end to end shows how the crates cooperate and where the shared Term space does its work. Trace a hybrid query, FIND ?x WHERE ?x IS-A Beer AND NEAR ?x TO [0.9, 0.0, 0.0, 0.5] LIMIT 5:

  1. Parse the OxQL

    oxd-server receives POST /query with the text in the query field and hands it to oxd-query. The pest grammar (oxql.pest) parses it into a Query AST: one result variable and a flat chain of stages: here an IS-A class stage and a NEAR vector stage. Invalid text returns a 400 with a QUERY_ERROR code before any work is done.

  2. Plan by selectivity

    The planner estimates how selective each stage is and chooses one of four strategies (logical-only, vector-only, filter-then-search, or search-then-filter) using System-R-style heuristics. A mis-estimate picks a slower plan, never a wrong answer. For a selective class filter it plans to push the class extent into the vector traversal.

  3. Build the reasoner candidate set

    oxd-reasoner supplies the extent of Beer as a TermBitSet: every member of Beer and all its subclasses, transitively (Lager, Ale, Stout, Pilsner…), including individuals never asserted directly as Beer. Classification runs automatically first if it is stale. Because document / individual IDs are already Terms, this bitset needs no translation to be used as a filter.

  4. Vector traversal, filtered during the walk

    oxd-vector runs the HNSW search with the bitset as a live filter: every graph node still steers the walk (routing quality is preserved), but only nodes whose Term is in the bitset enter the result heap. Nothing outside Beer is ever scored, so a rare class does not collapse recall. For a very selective filter the planner instead scans the bitset members directly; for a broad filter it over-samples then filters.

  5. Hydrate the results

    The surviving top-k Terms are resolved back to IRIs through the dictionary, and (when the request asks for it via hydrate or PROJECT) their data-property fields or document fields are inlined. Each row from a NEAR stage carries a score.

  6. Serialize to JSON

    oxd-server returns the page as { "results": [ { "iri": …, "score": … } ], "total_count": … }, with an opaque next_cursor when more rows remain. The whole path ran in one pass over one identifier space: no cross-system round-trip.

Tip A pure logical query skips step 4 (just enumerate the bitset); a pure vector query skips step 3 (no filter). The hybrid form uses both, which is the point of the engine. Hybrid Queries walks the same query in depth, and OxQL Overview covers the full grammar.

How the layers compose

Read top to bottom: a request enters through a surface, is planned and executed by the query layer, which calls into the three domain engines, all of which sit on the storage engine and, ultimately, on the one dictionary that gives every layer the same identifiers.

Dependencies point downward: surfaces depend on the query and storage layers, which depend on the domain engines, which all depend on oxd-core, never the reverse. The core has no I/O and no workspace dependencies, so it is testable in isolation and every layer above it speaks the same Term vocabulary. The one other leaf is oxd-io, which sits beside the core rather than in the diagram: it is the single interception point through which the persistence, vector, and storage layers touch the disk and the clock, so production runs a plain std passthrough while tests can make any fsync fail. The ontology↔document bridge lives in oxd-storage: when a document collection is mapped to a class, each insert atomically becomes a typed individual with its properties (and optionally a vector), so ingested JSON lands directly in the reasoner's Term space and the same hybrid query works over it.

Index types

Three kinds of index sit over the shared Term space, each accelerating a different shape of query while never changing the answer a full scan would give:

Neural

HNSW vector index

The approximate nearest-neighbor graph in oxd-vector: SQ8 / binary quantization for the resident graph and a memory-mapped cold-f32 base for datasets larger than RAM. Powers NEAR similarity ranking.

Symbolic

Ontology classifier

The EL⊥ reasoner in oxd-reasoner precomputes per-class extents as TermBitSets (cached to disk and invalidated on change), so an IS-A filter is a ready bitset rather than a query-time traversal.

Spatial (grid) index

An opt-in equirectangular grid over a GeoPoint field. It generates a candidate superset of documents near a query point, then refines with exact great-circle (Haversine) distance. The superset invariant means it only makes WITHIN and SORT DISTANCE queries faster, never changes their result, so a query still works (by full scan) with no index defined. See GeoPoint values on disk.

Extending: the ways in

Every entry point is a thin surface over the same Database: they differ in transport, not in capability.

HTTP API →

The axum JSON API at https://<id>.oxid-db.com is the ground truth every other client speaks to. Ontology, vector, document, transaction, training, and admin endpoints; the web UI adds an SPA fallback on its own -ui host.

SDKs & clients →

Typed clients over the same wire contract (Python, TypeScript/Node, Go, Java, PHP, and C#), each with a query builder for OxQL and full transaction support.

MCP integration →

The opt-in oxd-surface-mcp add-on exposes the engine to AI agents as MCP tools (query, classify, predict-links, and more) over stdio or Streamable HTTP.

Embedded Python

oxd-python runs the engine in-process (no server, no network hop) for notebooks and scripts that want the database as a library.
