The Ontology Bridge

Type a JSON collection into your ontology so its documents become reasoned individuals, and answer questions about classes they never mention.

Since 0.9.7 Version 0.9.7 adds the GeoPoint document field type, queried with OxQL WITHIN and SORT DISTANCE. It is document-only data: a GeoPoint does not bridge into the ontology (it is not a class or individual assertion and does not participate in reasoning). By contrast, a role-hierarchy edge does reason, an edge asserted under a sub-property counts under its super-property. See the Changelog for the full 0.9.6 → 0.9.7 difference.

This is the feature that makes Oxid-DB's document store unlike an ordinary one. A document is schema-free JSON. An ontology is a structured world of classes, properties, and inference rules. The ontology bridge connects the two: you declare once how a collection maps onto a class, and from then on every document you insert becomes a full ontology individual: classified, reasoned over, and queryable by inferred type. Facts (the JSON) and meaning (the ontology) live in one store and answer one query.

Why a bridge?

You usually have two things: real data as JSON documents, and an ontology that describes what that data means. Without a bridge they sit in separate worlds: you can filter documents by their fields, but the reasoner has no idea they exist, so none of your class hierarchy or inference applies to them.

The bridge makes a document be an individual of a class. Once that link exists, everything the engine can do to an ontology individual, it can now do to your JSON:

  • Reasoning applies. If your ontology says Beer is a subclass of Drink, a beer document is inferred to be a Drink, even though the JSON never contained the word "Drink".
  • Hybrid queries apply. The same query can filter by inferred class (IS-A) and by document fields and by vector similarity, in one pass.
The neurosymbolic payoff A plain document database can tell you which documents have abv > 4. With the bridge, Oxid-DB can also tell you which documents are Drinks (because the reasoner infers it from the class hierarchy) and rank them by vector similarity at the same time.

Mapping a collection to a class

POST /collections/map tells the engine: documents in this collection are individuals of this class, and these JSON fields correspond to these ontology properties. Here we bridge a beers document collection onto the ontology class Beer, mapping the name and abv fields to data properties:

curl -s -X POST https://85cfad134a4a.oxid-db.com/collections/map \
  -H 'Content-Type: application/json' \
  -d '{"collection":"beers","class":"Beer","field_mappings":[{"field":"name","property":"name","type":{"kind":"data_property"}},{"field":"abv","property":"abv","type":{"kind":"data_property"}}],"auto_type":true}'
# => {"changed":true,"replaced":false}
with OxidDB("https://85cfad134a4a.oxid-db.com") as db:
    db.register_mapping(
        "beers",
        "Beer",
        [
            {"field": "name", "property": "name", "type": {"kind": "data_property"}},
            {"field": "abv",  "property": "abv",  "type": {"kind": "data_property"}},
        ],
        auto_type=True,
    )

The request has four parts:

collection
The document collection to bridge.
class
The ontology class that every document in the collection becomes an instance of.
field_mappings
How JSON fields map to ontology properties. Each entry is { field, property, type }, where type.kind is one of data_property, object_property, or vector_property (explained below).
auto_type
When true (the default), the bridge fires automatically on every insert, update, and delete into the collection. When false, the mapping is recorded but not applied automatically.

Which fields become which kind of property

Each field mapping declares one of three kinds. Choosing the right one is the whole art of the bridge:

type.kindUse it forWhat the field becomes
data_propertyScalar fields: string, number, bool, timestamp.A data-property assertion, e.g. abv = 5.0. A literal value hanging off the individual.
object_propertyFields whose value is the IRI of another individual.An object-property assertion: a relationship (edge) to that other individual.
vector_propertyAn embedding field (a FieldValue::Vector).The vector is routed into a named vector collection. Add "collection":"<name>", and optionally "store_inline":false to strip the vector from the stored document so it lives only in the vector index.
GeoPoint fields do not bridge into the ontology The GeoPoint document field type (new in 0.9.7, queried with OxQL WITHIN and SORT DISTANCE) is document-only data. A GeoPoint is stored on the document and searched geospatially, but it is not a class or individual assertion: it does not become an ontology property, it does not type the document, and it does not participate in reasoning. There is no field-mapping kind for it. If you need location to influence inference, model it as an explicit EL axiom or an object-property edge instead. This is the honest contrast with a role-hierarchy edge, which does reason: an edge asserted under a sub-property counts under its super-property (see Reasoning).

Documents become individuals

Now insert a document exactly as you would into any collection. Because beers is mapped with auto_type, the bridge fires on the way in:

curl -s -X POST https://85cfad134a4a.oxid-db.com/documents/beers \
  -H 'Content-Type: application/json' \
  -d '{"_iri":"Heineken","name":"Heineken","abv":5.0}'
# => {"ok":true,"collection":"beers","iri":"Heineken"}
with OxidDB("https://85cfad134a4a.oxid-db.com") as db:
    res = db.insert_document("beers", {"name": "Heineken", "abv": 5.0}, iri="Heineken")
    # res: {"ok": true, "collection": "beers", "iri": "Heineken"}
const res = await db.insertDocument("beers", {
  _iri: "Heineken",
  name: "Heineken",
  abv: 5.0,
});
console.log(res.ok, res.iri); // true "Heineken"
res, err := client.InsertDocument(ctx, "beers", oxid.Document{
	"_iri": "Heineken",
	"name": "Heineken",
	"abv":  5.0,
})
if err != nil {
	log.Fatalf("insert document: %v", err)
}
log.Printf("ok=%v iri=%s", res.Ok, res.IRI)

Behind that single call, and inside one atomic mutation, the engine has:

  1. Stored the document

    Heineken now lives in the beers collection like any JSON document, queryable with FROM beers.

  2. Asserted the individual

    Heineken is declared an instance of Beer in the ontology (one AddIndividual plus a class assertion).

  3. Mapped the fields

    name and abv become data-property assertions on Heineken. You can confirm them at GET /properties.

Asserting facts is not the same as drawing conclusions. Run the reasoner once (after your batch of inserts, not per row) to compute inferences (subclass inheritance, consistency, disjointness):

bash
curl -s -X POST https://85cfad134a4a.oxid-db.com/classify
# => {"ok":true,"consistent":true,"violations":0}

Now the document answers questions about classes it never mentioned. Given an ontology where Beer is a subclass of Drink, a query for Drink returns the beer, purely by inference. IS-A matches every instance of a class and all of its subclasses, transitively:

oxql
FIND ?x WHERE ?x IS-A Drink LIMIT 20
json
{ "results": [ { "iri": "Heineken" } ], "total_count": 1, "next_cursor": "eyJ0ZXJtIjoi..." }
Classify after loading, not per insert The bridge asserts facts on every insert, but it does not re-run the reasoner each time. Classification is comparatively expensive. The pattern is: insert or bulk-load your documents, call POST /classify once, then query. Classification is also triggered automatically on the next query if the ontology has changed since the last run.

Data vs object properties

The difference between the two property kinds is the difference between a value and a relationship, and it decides how the reasoner can use the field.

  • abv is a data property. abv = 5.0 is a literal attached to Heineken. Data properties are how you filter on document fields in a query (?x.abv > 4).
  • pairsWith is an object property. If a beer document carries {"pairsWith": "Cheese"} and you map that field as an object_property, the string value Cheese is interned as an individual and the bridge asserts the edge Heineken pairsWith Cheese, a real relationship the reasoner can traverse and that link prediction can learn from. An object-property value must be a valid IRI string; a non-IRI value is rejected loudly rather than stored as a broken edge.

Field values are turned into assertions by a fixed policy: a scalar becomes one assertion; an array fans out to one assertion per element (a multi-valued property); a null value produces no assertion (absence of a fact, not a null fact); nested objects and binary blobs are rejected rather than silently dropped; and a vector is accepted only through a vector_property mapping.

Persistence

Mappings survive restarts Bridge mappings are persisted, not held in memory only. A registered CollectionTypeMapping is part of the database state, written into the checkpoint, and reloaded when the database reopens, so you register a mapping once and it stays in effect across restarts. You do not need to re-register mappings on every boot.

A mapping is bound to a collection name, not to the collection's data: dropping and recreating a collection deliberately leaves its mapping in place, so a rebuild-in-place keeps its typing. Registration is idempotent and safe to retry. Re-posting the identical mapping is a quiet no-op ({"changed":false}); posting a different mapping for an already-mapped collection returns 409 COLLECTION_ALREADY_MAPPED_DIFFERENT unless you pass ?replace=true, so a retry can never accidentally overwrite a mapping. DELETE /collections/map/{collection} unregisters. Inserting into an unmapped collection is always fine: the document is simply stored with no ontology side-effects. The bridge is opt-in, collection by collection.

Putting it together

Once a document is typed, it is fair game for the full hybrid engine. Because the document's identity, its class membership, and its vector are all the same internal term, a single query can filter by inferred meaning, filter by document fields, and rank by vector similarity in one pass, with no join and no second round-trip:

oxql
FIND ?x FROM beers WHERE ?x IS-A Drink AND ?x.abv > 4 AND NEAR ?x TO [0.9, 0.1, 0.5, 0.2] LIMIT 5

"Beverages (by inference) in the beers collection, stronger than 4% ABV, ranked by similarity to this taste vector" is a question that needs the reasoner, the document fields, and the vector index at once, answered in a single call. That combination, not raw search speed, is what the bridge buys you.
