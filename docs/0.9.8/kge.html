Link Prediction (KGE)

Train a knowledge-graph embedding model over your ontology and use it to predict likely missing relationships, with the reasoner vetting each guess against your disjointness rules.

What KGE is

A knowledge graph stores facts as entities joined by labelled relations: Heineken pairsWith Fish, Guinness brewedBy GuinnessBrewery. A raw database treats each name as an opaque string; it has no built-in sense that two beers are similar even when they play the same role in many facts.

Knowledge-graph embedding (KGE) fixes that by learning a short vector for every entity and every relation, so that a true fact (head, relation, tail) places head + relation close to tail in vector space. Once those vectors exist you can score any candidate fact (including facts nobody asserted) by how well it fits the learned geometry. That is link prediction: "given this entity and this relation, what are the most plausible missing tails?" For example, if most Pilsners in your graph carry pairsWith Salad, the model will rank Salad highly as a missing pairsWith tail for a Pilsner that has no such edge yet.

The training signal is the graph's structure alone: no text and no embedding API key are needed. Oxid-DB draws its training triples from three places: rdf:type class assertions (each individual and the classes it belongs to), object-property assertions (relations like brewedBy), and rdfs:subClassOf axioms from the TBox. This is a different kind of embedding from the text vectors used in Vector Search: KGE learns from how things are connected, not from what any text about them means.

The embedding proposes; the reasoner disposes A plain embedding library hands you a ranking and stops. Oxid-DB checks each type prediction against the built-in EL⊥ reasoner: a statistically plausible guess that would contradict your ontology (say, making something both a Beer and a Wine when you declared them disjoint) is marked vetoed, with the exact rule it breaks. You get a fast guesser and an exact validator in one answer.

TransE and RotatE

Oxid-DB ships two embedding models; you pick one at training time. Both are distance-based, so a lower score means a more plausible fact.

TransE

TransE is the simple, fast default. It models a relation as a translation: a fact (head, relation, tail) is good when head + relation ≈ tail, i.e. when the tail vector is close to the head vector shifted by the relation vector. Each relation becomes a consistent direction on the map. TransE is a strong baseline and is plenty for most graphs, but its translation geometry can't cleanly represent some relationship patterns (for instance symmetric relations).

RotatE

RotatE represents each relation as a rotation in complex space rather than a translation. That richer geometry lets it capture patterns TransE struggles with (symmetry, inversion, and composition of relations) at the cost of being a little heavier to train. Reach for RotatE when your relations have that kind of structure and TransE's predictions feel too coarse.

Training a model

Training is a managed, potentially long-running operation Training runs on the server. On a small graph it finishes in well under a second; on a large one it can take a while, so treat POST /train as asynchronous and poll GET /train/status for progress. Runtime tuning and provisioning are managed for you while Oxid-DB is closed-source; see Install, CLI & Settings.

You train a model by name: the collection name is the model name, and that same name is what you pass back to /predict-links later. Train over the current ABox with POST /train. The request body carries the model kind and hyperparameters (all optional; the defaults below are sensible for a first run):

bash
curl -s -X POST https://85cfad134a4a.oxid-db.com/train \
  -H 'Content-Type: application/json' \
  -d '{"model":"transe","collection":"structural","dim":4,"epochs":100}'

Training defaults (verified in oxd-train): dim = 128, epochs = 100, learning rate 0.01, margin 1.0, seed = 42 (so a fixed seed over the same, canonically-sorted triples trains reproducibly). The example uses dim: 4 to match this page's 4-dimensional toy beverage vectors; leave it at 128 for real graphs.

Poll training progress with GET /train/status:

bash
curl -s https://85cfad134a4a.oxid-db.com/train/status

A trained model is persisted alongside the database (under <data_dir>/kge-models/) and survives restarts. Oxid-DB also fingerprints the triples it trained on: if the graph changes afterwards, predictions come back flagged stale: true so you know to re-train. Re-training is just another POST /train under the same name.

Predicting links

With a model trained, call POST /predict-links. You give a head entity, an optional relation (defaults to rdf:type, i.e. "what kind of thing is this?"), the model name you trained into, and how many candidates you want. The SDK panels below are paste-ready: 

# Train first (collection name = model name), then predict.
# The field is top_k, NOT k (a stray "k" is silently ignored).
curl -s -X POST https://85cfad134a4a.oxid-db.com/predict-links \
  -H 'Content-Type: application/json' \
  -d '{"head":"Heineken","relation":"brewedBy","model":"default","top_k":5}'
with OxidDB("https://85cfad134a4a.oxid-db.com") as db:
    db.train(model="default", dim=4, epochs=50)   # collection == model name
    preds = db.predict_links("Heineken", relation="similarTo", k=5)
    for p in preds.get("results", []):
        print(p)
const pred = await db.predictLinks({
  head: "Guinness",
  relation: "pairsWith",
  top_k: 5,
  only_consistent: true, // veto inconsistent tails
});
for (const c of pred.candidates) {
  console.log(`${c.t}  score=${c.score.toFixed(3)}  consistent=${c.consistent}`);
}
res, err := client.PredictLinks(ctx, oxid.PredictLinksRequest{
	Head:           "PilsnerUrquell",
	Relation:       "pairsWith",
	TopK:           5,
	OnlyConsistent: true, // keep only reasoner-consistent candidates
})
if err != nil {
	log.Fatalf("predict-links: %v", err)
}
log.Printf("tier=%s model=%s stale=%v", res.Tier, res.Model, res.Stale)
for _, c := range res.Candidates {
	log.Printf("  (%s %s %s) score=%.4f consistent=%v verdict=%s",
		c.H, c.R, c.T, c.Score, c.Consistent, c.Verdict)
}
// Optional: train a KGE model over the ABox first
oxid.train(Ops.TrainRequest.defaults());

// Predict tails for (Heineken, ?relation, ?) - wire field is top_k, not k.
Kge.PredictLinksRequest req =
        new Kge.PredictLinksRequest("Heineken", "similarTo", null, 5, true);
Kge.PredictLinksResponse pred = oxid.predictLinks(req);
for (Kge.LinkCandidate c : pred.candidates()) {
    System.out.println(c.h() + " -" + c.r() + "-> " + c.t()
            + " score=" + c.score() + " verdict=" + c.verdict());
}
use OxidDb\Client\Model\TrainRequest;
use OxidDb\Client\Model\PredictLinksRequest;

$oxid->train(new TrainRequest());                    // POST /train (defaults)

    head: 'Heineken',
    relation: 'pairsWith',
    topK: 5,
    onlyConsistent: true,
));
printf("model=%s tier=%s stale=%s\n", $pred->model, $pred->tier, $pred->stale ? 'true' : 'false');
foreach ($pred->candidates as $c) {
    printf("  %s -%s-> %s  score=%.4f verdict=%s\n", $c->h, $c->r, $c->t, $c->score, $c->verdict);
}
PredictLinksResponse pred = await oxid.PredictLinksAsync(
    new PredictLinksRequest("Heineken", Relation: "similarTo", TopK: 5, OnlyConsistent: true));

Console.WriteLine($"tier={pred.Tier} model={pred.Model} stale={pred.Stale}");
foreach (LinkCandidate c in pred.Candidates)
{
    Console.WriteLine($"  {c.H} -{c.R}-> {c.T}  score={c.Score} rank={c.Rank} " +
                      $"consistent={c.Consistent} verdict={c.Verdict}");
}

Reading the request and response

The prediction request uses top_k to control how many candidates come back, not k. This is an easy mistake: a stray k field is silently ignored by the server and you fall back to the configured default. The Python panel above passes k=5 because that SDK maps its own k argument onto the wire field for you; over raw HTTP, always send top_k.

head
The entity you are asking about, e.g. Heineken. Required.
relation
Which relation to predict tails for. Defaults to rdf:type ("what kind of thing is this?"), the only relation the reasoner can veto.
model
The trained model / collection name. Defaults to "default". A missing model returns a 400 telling you to POST /train first.
top_k
How many candidates to return. The wire field is top_k, not k.
only_consistent
When true, vetoed candidates are dropped from the result entirely: the "safe autocomplete" mode.

Each returned candidate carries the triple it scores (h, r, t), the model's score (lower = more plausible), its rank, a boolean consistent flag, and a verdict that carries the reasoner's ruling. The response also reports the model, its provenance/tier, the number of trained_abox_triples, and whether the model is stale.

The reasoner veto is the differentiator

When the relation is rdf:type, every predicted class is checked against the ontology's disjointness axioms via vet_prediction. A guess that would make an individual a member of two disjoint classes (the classic Beer ⊥ Wine case) is rejected, with the exact rule it violates recorded in its verdict. The embedding supplies the ranking; the reasoner supplies the ruling. This pairing of a statistical guesser with an exact logical validator is what sets Oxid-DB's link prediction apart from a standalone embedding library.

The veto only applies to rdf:type predictions, because that is where the reasoner has disjointness rules to check against. For other relations (like pairsWith or brewedBy) there is no such lever, so those candidates come back as honestly-labelled ranked suggestions, not vetted facts. Setting only_consistent: true gives you a stream that an automated agent can safely act on: it can never launder a high-scoring-but-illegal type into a stored fact.

Single-shot predict + vet, not the full ReasonKGE loop The online /predict-links endpoint does single-shot prediction followed by disjointness vetting (predict_tails then vet_prediction). It does not run the full iterative ReasonKGE retrain loop, the variant that feeds vetoed predictions back as hard negatives and re-trains over several iterations. That loop exists in the engine as a library routine, but the HTTP path here is a single pass: predict, then filter. Predictions are statistical leads to verify, never ground truth; the veto tells you what is impossible, not what is true.
