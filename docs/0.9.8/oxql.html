OxQL Overview

OxQL is one language for ontology, vector, and hybrid queries. A single FIND statement can ask the reasoner which entities qualify, ask the vector index how similar they are, and filter on document fields, all in one pass, over one shared set of identifiers.

New in 0.9.8 Two lexer-level conveniences, no new clauses. IS-A accepts an angle-bracketed verbatim IRI (?x IS-A <http://data.europa.eu/esco/occupation/0e2d-24d0-4b73>), so a class IRI carrying hyphens or other characters outside the bare identifier alphabet can be named SPARQL-style; the bare form is unchanged. And a bare NEAR ?x with no configured default collection now resolves to the sole collection when the database holds exactly one; with zero or several collections it fails with an actionable message that names the available collections and the NEAR ?x.<collection> qualifier. POST /explain reports the same resolved collection. See Verbatim IRIs in IS-A and Which collection NEAR searches below, and the Changelog for the full 0.9.7 → 0.9.8 difference.

This page is the developer reference for the language itself: how a query is shaped, every clause you can write, how to run and paginate queries from your app, and, just as important, what the grammar deliberately does not support. It is grounded in the actual pest grammar the engine parses, not on aspirational syntax.

Anatomy of a query

Every OxQL query starts with FIND ?x and, in the common case, needs at least one WHERE stage. The simplest complete query is a single class membership test:

oxql
FIND ?x WHERE ?x IS-A Beer LIMIT 20

Read left to right, the full statement has this shape (square brackets mark optional parts):

oxql
FIND ?x
     [FROM <collection>]
     [WHERE <stage> ( (EXCEPT | [AND]) <stage> )* ]
     [ PROJECT <field>,... | AGGREGATE <fn>,... [GROUP BY ...] ]
     [SORT <field> [ASC|DESC]]
     [LIMIT n] [OFFSET m] [AS OF <commit_ts>]

Variables

OxQL binds exactly one variable, written with a leading question mark (?x, ?beer, ?item: any of letters, digits, and underscores after the ?). That variable is the thing you are searching for; every stage in the WHERE chain constrains or ranks it, and each result row comes back as that one bound entity. There is no second variable and there are no joins; OxQL is a single-subject filter-and-rank language, not a graph pattern language like SPARQL.

Note The WHERE chain is a flat conjunction. Stages are separated by whitespace, or by the optional keyword AND: ?x IS-A Beer NEAR ?x TO […] and ?x IS-A Beer AND NEAR ?x TO […] are identical. WHERE plus at least one stage is mandatory unless the query uses FROM with a pure AGGREGATE (counting over a whole document collection). Comments run from -- to end of line.

Clauses

Each stage in the WHERE chain is one clause. Below is every clause the grammar accepts, with a minimal standalone example. The examples use the beverage ontology and 4-dimensional flavour vectors used throughout these docs.

IS-A: class membership (with inference)

?x IS-A <Class> returns every instance of that class including instances of all subclasses, transitively. The set is computed by the reasoner's classification closure, so ?x IS-A Beer returns members of Pilsner, Stout, IPA, Lager, and WheatBeer even if none was ever asserted directly as a Beer. Classification runs automatically on the first query if it is stale.

oxql
-- returns subclass members too (Lager, Stout, Pilsner, …)
FIND ?x WHERE ?x IS-A Beer LIMIT 20

Verbatim IRIs in IS-A New in 0.9.8

The class after IS-A is normally a bare token. A bare token must start with an ASCII letter and may then contain only letters, digits, and _ : / # ., which is enough for a short name (Beer) or a hash/slash IRI (http://oxid.example/onto#Beer). Real-world vocabularies break that rule: an ESCO occupation IRI contains hyphens, a CPV code may carry ~ or percent-encoding, and none of those characters is legal in a bare identifier. Wrap the IRI in angle brackets and it is taken verbatim, SPARQL-style; the brackets are stripped and the class is matched exactly as written.

oxql
-- bare form, unchanged: letters, digits, _ : / # . only
FIND ?x WHERE ?x IS-A http://oxid.example/onto#Beer LIMIT 5

-- verbatim form: the hyphens would be rejected as a bare token
FIND ?x WHERE ?x IS-A <http://data.europa.eu/esco/occupation/0e2d-24d0-4b73>
  AND NEAR ?x TO "data engineer" LIMIT 3
  • Brackets are required whenever the IRI contains a character outside [A-Za-z0-9_:/#.] or does not start with a letter; they are optional otherwise (both spellings of http://oxid.example/onto#Beer parse to the same query).
  • Everything between < and > is taken literally, so the IRI may not itself contain >, and the empty form IS-A <> is a parse error.
  • Only the lexer widened: the class is still matched against the ontology exactly as written, and the same subclass-transitive semantics apply. The bracket form is accepted only in IS-A position; relation triples and field names still use bare identifiers.
  • Rendering is round-trip safe: when the engine prints a query back (for example from POST /explain) a class that needs brackets is re-bracketed, and one that does not stays bare.

Relation triples: object-property filter

?x <property> <object> matches individuals that have the given object-property assertion pointing at the named object. For example, ?x brewedBy HeinekenNV returns every individual whose brewedBy relation targets HeinekenNV.

oxql
FIND ?x WHERE ?x brewedBy HeinekenNV LIMIT 10

NEAR: vector search

NEAR ?x TO <vector> ranks candidates by vector distance. The right-hand side is either a literal vector (whose dimensionality must match the target collection) or a quoted text string that is auto-embedded when an embedder is configured. Append NEAR ?x.<collection> TO … to target a named collection; a bare NEAR ?x searches the default collection, or the only collection when there is exactly one (see below). Rows returned by a NEAR stage carry a score field.

oxql
-- literal query vector (4-dim, must match the collection)
FIND ?x WHERE NEAR ?x TO [0.9, 0.1, 0.5, 0.7] LIMIT 5

-- text query (needs a configured embedder)
FIND ?x WHERE NEAR ?x TO "crisp pale lager" LIMIT 5

Because NEAR is just another stage, you can put it in the same WHERE chain as an IS-A filter to get a hybrid query: the reasoner's class extent scopes the vector walk so only in-class members are ever scored. That single-pass fusion is the core of Oxid-DB; it has its own page at Hybrid Queries. A related clause, LIKE ?x TO <EntityName>, uses an existing entity's stored vector as the query, "find things similar to Guinness" without knowing its vector.

NEAR without a qualifier: collection resolution New in 0.9.8

The .<collection> qualifier is optional, so the engine has to decide what an unqualified NEAR ?x means. The resolution order is fixed:

  1. An explicit qualifier wins. NEAR ?x.flavor TO … searches flavor, and still fails with vector collection not found: flavor if that name does not exist.
  2. The configured default collection, when it exists.
  3. The sole collection. If no default is configured but the database holds exactly one collection, a bare NEAR ?x is unambiguous and searches that one. Before 0.9.8 this case failed with a misleading vector collection not found: default.
  4. Otherwise an error, with an actionable message. Zero collections: no vector collection to search: this database has no collections yet, create one, then qualify the search as NEAR ?x.<collection> TO .... Several collections and no default: no default vector collection: name the one to search with NEAR ?x.<collection> TO ... (available: aroma, flavor), listing every collection in sorted order.

The same resolution is used by LIKE ?x TO … and by POST /explain, so a plan report names the collection the query will actually search rather than a phantom default.

Field predicates: ?x.field <op> value

?x.<field> <op> <literal> filters by a data-property value (ontology mode) or a document field (document mode). The left side is the variable, a dot, and the field name; the right side is a quoted string, a number, or true/false. The supported comparison operators are =, !=, >, <, >=, and <=.

oxql
-- beers with ABV strictly between 4.5 and 6.0
FIND ?x WHERE ?x IS-A Beer AND ?x.abv > 4.5 AND ?x.abv < 6.0 LIMIT 10

In document mode (see Querying Documents) three more field clauses are available: EXISTS ?x.<field> (the document has a value at that path), ?x.<field> CONTAINS <literal> (array membership), and ?x.<field> IN [ … ] (see below).

IN: set membership

?x.<field> IN [lit, lit, …] matches when the field equals any listed literal: the union of per-value = matches in one stage. The list must be non-empty. This is the only way to express a disjunction over a single field, because OxQL has no OR. There is no NOT IN.

oxql
FIND ?x WHERE ?x IS-A Beer AND ?x.abv IN [4.5, 7.0] LIMIT 10

EXCEPT / NOT: negation

A stage may be negated with NOT, and A EXCEPT B is exact shorthand for A AND NOT B: both compile to the identical query. Negation is closed-world: NOT ?x IS-A C means "not provably an instance of C in this database" (asserted or inferred), evaluated over the known individuals.

oxql
-- beverages that are not beers (the two lines are identical)
FIND ?x WHERE ?x IS-A Beverage EXCEPT ?x IS-A Beer LIMIT 100
FIND ?x WHERE ?x IS-A Beverage AND NOT ?x IS-A Beer LIMIT 100

NOT is v1-scoped: the negated leaf must be an IS-A or a relation stage, and only in ontology-mode (no FROM) queries. Negating a field predicate, a NEAR stage, or any document-mode stage is rejected with a clear error rather than guessed.

LIMIT and OFFSET: paging

LIMIT n caps the page size; if omitted it defaults to 10. OFFSET m skips the first m rows (default 0). Increment OFFSET by LIMIT to page through a large result set. An explicit LIMIT above the server's configured maximum row cap is rejected with a 400.

oxql
-- page 2 of 100-row pages
FIND ?x WHERE ?x IS-A Beverage LIMIT 100 OFFSET 100

EF: per-query recall / speed

EF <n> follows a NEAR stage to override the HNSW search breadth (ef_search) for that one query. A larger EF widens the graph traversal: higher recall, more work; a smaller value is faster with a bit less recall. The engine default is 64.

oxql
FIND ?x WHERE NEAR ?x TO "crisp pale lager" EF 200 LIMIT 10

Geospatial queries

A document field typed as a GeoPoint is directly queryable in OxQL. Two clauses cover the common cases: a radius filter (WITHIN) and a nearest-first ordering (SORT DISTANCE). Both operate on the stored (lat, lon) and compute great-circle (Haversine) distance. Coordinates are always written in the order (latitude, longitude): latitude in [-90, 90] (positive north), longitude in [-180, 180] (positive east).

Order is (lat, lon), never (lon, lat) This is the classic geospatial footgun. Every coordinate pair in a WITHIN or DISTANCE(...) is latitude first, longitude second. Amsterdam is (52.3702, 4.8952), not (4.8952, 52.3702). A swapped pair is a valid point somewhere in the ocean, so it will not error, it will just return the wrong rows.

WITHIN: radius filter

?x.<field> WITHIN <distance><unit> OF (<lat>, <lon>) keeps only the individuals whose GeoPoint lies within the given great-circle distance of the origin point. The <unit> is one of km (kilometres), mi (miles), or m (metres).

oxql
-- breweries within 5 km of central Amsterdam (lat, lon)
FIND ?x FROM breweries WHERE ?x.location WITHIN 5km OF (52.3702, 4.8952)

SORT DISTANCE: nearest-first ordering

SORT DISTANCE(?x.<field>, (<lat>, <lon>)) [ASC|DESC] orders results by their distance from the origin point; ASC (nearest first) is the usual choice. Combine it with a WITHIN filter and a LIMIT for a classic “nearest N” query:

oxql
-- the 5 nearest breweries within 25 km of Amsterdam
FIND ?x FROM breweries
WHERE ?x.location WITHIN 25km OF (52.3702, 4.8952)
SORT DISTANCE(?x.location, (52.3702, 4.8952)) ASC LIMIT 5

When a query carries a geo clause, each result hit gains a numeric distance_m field: metres from the origin point. Non-geo queries omit it, so the wire response stays compatible. A GeoPoint is document-only data; it does not bridge into the ontology, so geo clauses run against a document collection (a FROM query). If a spatial (grid) index exists on the field it accelerates the filter; without one, the query falls back to a full scan and still returns the same rows.

For a convenience without hand-writing OxQL, a typed route POST /collections/{name}/geo-search builds the identical query AST from a small JSON body (field, lat, lon, radius_m, optional nearest and class). It is documented on the HTTP API page.

COUNT(*) and grouping: aggregation

An AGGREGATE clause replaces the row list with computed values: COUNT(*), COUNT(f), SUM(f), AVG(f), MIN(f), MAX(f), or COUNT_DISTINCT(f), optionally followed by GROUP BY, HAVING, ORDER BY, and TOP. Note that COUNT(*) is the literal token; COUNT() is invalid. Aggregation has its own page; see Aggregation.

oxql
FIND ?x FROM people AGGREGATE COUNT(*) GROUP BY manager HAVING COUNT(*) > 1 ORDER BY COUNT(*) DESC TOP 5

Running a query

All OxQL runs through one endpoint, POST /query, with the OxQL text in the query field. A response is one page: results (rows, each at least {"iri": …}, plus score for NEAR/hybrid rows), a total_count for this page, and an opaque next_cursor. Below are the paste-ready calls across every SDK.

Run one query

  -H 'Content-Type: application/json' \
  -d '{"query":"FIND ?x WHERE ?x IS-A Lager LIMIT 20"}'
with OxidDB("https://85cfad134a4a.oxid-db.com") as db:
    page = db.query("FIND ?x WHERE ?x IS-A Beer LIMIT 20")
    for hit in page.get("results", []):
        print(hit["iri"])

Page through every result

There is no server-side "fetch all". The correct way to drain a large result is to keep the same query and increment OFFSET by LIMIT until a page comes back empty (or shorter than LIMIT). Most SDKs wrap this in a query_all iterator. A response also returns an opaque next_cursor you can resend, but for deep pages over SORT/NEAR result sets prefer OFFSET/LIMIT, which recompute the true top-N each call.

# Page by incrementing OFFSET by LIMIT until results is empty.
curl -s -X POST https://85cfad134a4a.oxid-db.com/query \
  -H 'Content-Type: application/json' \
  -d '{"query":"FIND ?x WHERE ?x IS-A Beer LIMIT 100 OFFSET 0"}'
# then resend with the returned next_cursor:
curl -s -X POST https://85cfad134a4a.oxid-db.com/query \
  -H 'Content-Type: application/json' \
  -d '{"query":"FIND ?x WHERE ?x IS-A Beer LIMIT 100","cursor":"eyJ0ZXJtIjoi..."}'
with OxidDB("https://85cfad134a4a.oxid-db.com") as db:
    for hit in db.query_all("FIND ?x WHERE ?x IS-A Beer"):
        print(hit["iri"])
const iris: string[] = [];
for await (const hit of db.queryAll({ query: "FIND ?x WHERE ?x IS-A Beer LIMIT 1000" })) {
  iris.push(hit.iri);
}
console.log(iris.length);
count := 0

	if err != nil {

	}
	count++
	log.Println(hit.IRI)
}
log.Printf("streamed %d hits across all pages", count)

}

Vector and hybrid search

Vector search is expressed as OxQL: a NEAR stage over POST /query, optionally combined with an IS-A filter for a hybrid query. Rows carry a score. For neighbours of an existing entity, the SDKs also expose a by-reference call (GET /individuals/{iri}/similar).

curl -s -X POST https://85cfad134a4a.oxid-db.com/query \
  -H 'Content-Type: application/json' \
  -d '{"query":"FIND ?x WHERE ?x IS-A Beer AND NEAR ?x TO [0.9,0.1,0.5] LIMIT 5"}'
with OxidDB("https://85cfad134a4a.oxid-db.com") as db:
    # (1) literal query vector (dims must match the collection)
    hits = db.query("FIND ?x WHERE NEAR ?x TO [0.4, 0.2, 0.1, 0.4] LIMIT 5")
    for h in hits.get("results", []):
        print(h["iri"], h.get("score"))

    # (2) nearest neighbours of an existing individual
    sim = db.individual_similar("Heineken", k=3, collection="default")
    print([h["iri"] for h in sim.get("results", [])])
// 1) OxQL NEAR over /query - hybrid-capable (combine with IS-A). Rows carry `score`.
const near = await db.query({
  query: "FIND ?x WHERE ?x IS-A Beer AND NEAR ?x TO [0.9, 0.1, 0.5, 0.7] LIMIT 5",
});
for (const hit of near.results) console.log(hit.iri, hit.score);

// 2) By reference individual - top-k neighbors of an existing IRI.
const sim = await db.individualSimilar("Guinness", { k: 3, collection: "default" });
for (const hit of sim.results) console.log(hit.iri, hit.score);
// Hybrid: Beers nearest a 4-dim probe vector, top 5.
oxql := oxid.NewQueryBuilder().
	Find("x").
	IsA("Beer").
	Near([]float64{0.9, 0.1, 0.0, 0.2}).
	Limit(5).
	ToOxql()
res, err := client.Query(ctx, oxid.QueryRequest{Query: oxql})
if err != nil {
	log.Fatalf("vector search: %v", err)
}
for _, hit := range res.Results {
	if hit.Score != nil {
		log.Printf("%s score=%.4f", hit.IRI, *hit.Score)
	}
}

// Neighbors of a known individual:
sim, err := client.IndividualSimilar(ctx, "PilsnerUrquell",
	&oxid.SimilarOpts{K: 5, Collection: "default"})
_, _ = sim, err
// 1) By reference IRI - 3 nearest neighbours of Heineken in the default collection
Individuals.IndividualSimilarResponse sim = oxid.individualSimilar("Heineken", 3, null);
for (Individuals.SimilarHit hit : sim.results()) {
    System.out.println(hit.iri() + " " + hit.score());
}

// 2) By raw vector - via OxQL NEAR
String oxql = new QueryBuilder()
        .find("x").isA("Beer")
        .near(new double[] {0.9, 0.1, 0.5, 0.2})
        .limit(5)
        .toOxql();
Query.QueryResponse hits = oxid.query(Query.QueryRequest.of(oxql));

    printf("  %s  score=%s\n", $hit->iri, $hit->score);

    .ToOxql();

{
    Console.WriteLine($"{hit.Iri}  score={hit.Score}");

    Console.WriteLine($"{s.Iri}  {s.Score}");
}

Limitations (be honest)

Grammar limits worth knowing before you build
  • No OR. The WHERE chain is a flat conjunction; OR is a reserved word but not a grammar production. The only disjunction available is ?x.field IN [ … ] over one field.
  • No parentheses or grouping. There are no nested boolean expressions, just an AND/EXCEPT fold.
  • No joins and no second variable. A query binds exactly one ?var.
  • NOT only negates IS-A and relation leaves, and only in ontology mode. Negating a field predicate, a document-mode stage, or a NEAR stage is rejected loudly.
  • SORT is a no-op over HTTP. It parses and applies to document-mode projections in-engine, but the /query JSON response is ordered by IRI (or score-then-IRI for NEAR/hybrid rows), not by SORT. Do not rely on it to order the wire response.
  • AS OF takes an integer commit timestamp only: wall-clock date strings are not yet supported.

Keyword reference

KeywordMeaning
FIND ?xMandatory. Declares the single result variable.
FROM <collection>Switches to document mode; predicates route to the document store instead of the ontology.
WHEREBegins the stage chain. Required unless FROM + AGGREGATE (pure-aggregate).
ANDOptional stage connector; whitespace alone works too. Semantics are conjunction.
IS-A <Class>Class membership, including all subclasses transitively (reasoner-inferred). The class is a bare token, or (0.9.8) an angle-bracketed verbatim IRI such as IS-A <http://…/0e2d-24d0-4b73> when it carries characters outside [A-Za-z0-9_:/#.].
<property> <object>Object-property (relation) filter, e.g. brewedBy HeinekenNV.
NEAR ?x TO <vec|"text">Vector search; literal vector or auto-embedded text. ?x.<collection> targets a named collection; bare ?x means the default collection, or the sole collection when exactly one exists (0.9.8).
LIKE ?x TO <Entity>Vector-by-reference: use another entity's stored vector as the query.
EF <n>Per-query HNSW search breadth override (follows a NEAR stage). Default 64.
?x.<field> <op> <lit>Field/data-property predicate; ops = != > < >= <=.
<field> IN [ … ]Set membership: union of equalities over one field. Non-empty list; no NOT IN.
<field> CONTAINS <lit>Array membership (document mode).
EXISTS ?x.<field>Document has a value at that path (document mode).
NOT <stage>Closed-world negation of an IS-A/relation leaf (ontology mode only).
EXCEPT <stage>Shorthand for AND NOT <stage>.
PROJECT <field>,…Return selected document fields in each row's fields object (document mode).
AGGREGATE <fn>,…COUNT(*), COUNT/SUM/AVG/MIN/MAX(f), COUNT_DISTINCT(f). Mutually exclusive with PROJECT.
GROUP BY · HAVING · ORDER BY · TOPGrouping modifiers, valid only inside an AGGREGATE clause, in that order.
SORT <field> [ASC|DESC]Sorts document-mode projections in-engine. Does not order the HTTP response.
?x.<field> WITHIN <d><unit> OF (lat, lon)Great-circle radius filter on a GeoPoint field; <unit> is km/mi/m. Coordinates are (lat, lon).
SORT DISTANCE(?x.<field>, (lat, lon)) [ASC|DESC]Orders geo results by distance from the point (nearest-first with ASC). Each hit gains distance_m.
LIMIT nPage size. Defaults to 10 when omitted.
OFFSET mSkip the first m rows. Defaults to 0.
AS OF <commit_ts>Time-travel read at a commit timestamp (integer only).

Reserved words that cannot be used as identifiers (uppercase-exact): EXCEPT, HAVING, ORDER, NOT, TOP, OR. Everything else (including IS-A, AND, IN, CONTAINS, EXISTS, NEAR, LIKE, TO, FROM, EF) is contextual, so a class or field named, say, in keeps working.
